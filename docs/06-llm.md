---

## 1. 方針

- 推論は外部の llama-server (llama.cpp) に任せる。evorag は llama-server を起動・更新・管理しない (確定、[ADR-0010](10-decisions.md#adr-0010-外部の-llama-server-だけを使う))。
- 通信は HTTP で、既定はループバックだけ (§9)。`evorag-llm` は TLS を持たない。
- 足りない能力に応じて縮退して動く (§3)。

## 2. 役割と接続

役割ごとに、接続先とモデル名を設定で持つ。

| 役割 | 使う API | 必須か | 無いとき | 版 |
|---|---|---|---|---|
| chat | `/v1/chat/completions` (逐次表示、SSE) | 必須 | 起動しない (`evorag setup` の案内を出す) | v0.1 |
| embed | `/v1/embeddings` | 推奨 | ベクトルの検索を止め、語彙の検索だけで答える | v0.2 |
| rerank | `/v1/rerank` (サーバ側に `--reranking` が要る) | 任意 | 候補の順位を RRF のまま使う | v0.2 |

- 役割ごとに別のサーバ (またはルーターモードの別のモデル) が要る。chat のサーバは `/v1/embeddings` を、embed のサーバは `/v1/rerank` を 501 で断る (S-02)。

```toml
[llm.chat]
url = "http://127.0.0.1:8080"
model = "qwen3-32b"            # ルーターモードのときだけ意味を持つ
api_key_env = "EVORAG_LLM_KEY" # 環境変数の名前 (直接書くなら api_key)

[llm.embed]
url = "http://127.0.0.1:8081"

[llm.rerank]
url = "http://127.0.0.1:8082"
```

- 設定のキーの一覧は [07 §4](07-tui-config.md#4-設定)。モデルの候補 (`/model` で切り替える先) は `[[llm.chat.models]]` に並べる。
- **ルーターモード** (1 つの URL で複数のモデルを扱う) は v0.2 で対応する (Should、FR-511、提案、[OQ-13](10-decisions.md#oq-13-ルーターモードへの対応))。GET の要求は問い合わせ文字列の `?model=`、POST は本文の `model` でモデルを選ぶ。`/slots` と `/tokenize` の選び方は未確認 (S-02)。

## 3. 起動時の確認と縮退

1. `/health` で動いているかを確かめる (API キーなしで呼べる)。
2. `/props` (API キーが要る) で、`build_info`、`model_path`、`total_slots`、`default_generation_settings.n_ctx` を読む。`n_ctx` は **スロットごとの値** (サーバの `-c` を `-np` で割った値) で、文脈の予算 (05 §4.1) はこの値で計算する。
3. `/v1/models` で、モデルの名前と `data[0].meta` (`n_params`・`size`・`n_ctx_train`・`n_embd`) を読む。
4. 前回の接続のときの model_key・`model_path` と照合し、違えば状態の行と起動時の通知で知らせる (02 §8.2)。

| 状態 | 動き |
|---|---|
| chat に繋がらない | TUI を開かずに案内を出して終わる (終了コード 3)。`evorag setup` に誘導する |
| chat が途中で切れた | 状態の行を「未接続」にし、生成中なら失敗として記録する (§7)。5 秒ごとに `/health` で再接続を試みる |
| embed が無い | ベクトルの検索を止め、判定点に Skip を記録する |
| rerank が無い | RRF の順位のまま使う |
| `/slots` が無い (サーバの `--no-slots`) | 譲る判定を省き、裏の処理は利用者の操作が無いときだけ動かす |

## 4. スロットと譲り方

- llama-server はスロットを役割ごとに予約しない。そのため、chat のサーバのスロットが 2 つ以上あるときは、**応答の要求も裏の処理の要求も `id_slot` を明示する**。応答は最初のスロット、裏の処理は最後のスロットを使う (`/v1/chat/completions` で `id_slot` が効くことを S-02 で確かめた)。
- スロットが 1 つしか無ければ、裏の処理は利用者が操作していないときだけ動かす。
- 裏の要求を出す前に `/slots` の `is_processing` を見て、応答のスロットが処理中なら出さない。
- 利用者の要求が来たら、裏の要求の接続を切って止める。llama-server は接続が閉じると生成を取り消し、0.2 秒ほどで止まる (S-02。逐次表示でもそうでなくても止まる)。**応答の本体を捨てて TCP の接続を確実に閉じる** こと (応答の読み取りのオブジェクトがソケットを持ったままだと、接続は閉じず、生成は最後まで続く)。裏の要求は、止めたところまでの結果を捨てやすいように逐次表示 (stream) で出す。
- スロットのキャッシュの消去 (`/slots/{id}?action=erase`) は、サーバを `--slot-save-path` 付きで起動したときだけ使える (既定では 501)。`--slot-save-path` は KV キャッシュをディスクに書くので、evorag の案内では勧めない。スロットのキャッシュは次の要求で上書きされる (04 §7.3)。
- 裏の処理には長いプロンプトを一度に送らない (1 回 2,048 トークンまで、04 §4)。
- 埋め込みとリランクは別のサーバなので、上の規則は chat のサーバにだけ当てる。

## 5. model_key

モデルを識別する値。ターンに記録し、埋め込みと学習したものは model_key ごとに分ける (v0.1 で定義を固める)。

- 作り方: `/props` の `model_path` のファイル名 (フォルダを除く) と、`/v1/models` の `data[0].meta` の `n_params`・`size`・`n_vocab` (返さない版ではモデルの名前) を連結し、SHA-256 の先頭 16 バイトを 16 進で書く。
- evorag は `model_path` のファイルを読まない (llama-server が別のコンテナ・権限で動いていることがあるため)。
- 定義を変えるときは新しい種類の値として足し、古い値も読み続ける (03 §4)。

## 6. 出力の型縛り

- 補助の判定と抽出 (ノート、事実の候補、訂正の検証、言い換え、precept の提案、採点) は、Rust の型から `schemars` で作った JSON Schema を `response_format` (`{"type": "json_schema", ...}`) で送る (v0.2)。
- 受け取った JSON は型で検証し、合わなければ 1 回だけやり直し、それでも合わなければその手順を失敗として `job` に記録する。
- 型縛りの呼び出しは temperature 0 と固定の seed で出し、`id_slot` を固定する (スロットを固定すると同じ入力から同じ出力が得られ、固定しないと割り当てられたスロットで出力が変わることを S-02 で確かめた)。
- 思考の部分を出すモデル (Qwen3.5 など) は、補助の呼び出しで思考を切る設定 (`chat_template_kwargs: {"enable_thinking": false}` など) が要る。モデルごとに設定 `llm.chat.aux_request_extra` (要求に足す JSON) で持つ。

## 7. 再試行と失敗の扱い

- 接続の失敗と 5xx だけを、指数バックオフ (0.5 s、1 s、2 s) で 3 回まで再試行する。4xx は再試行しない。
- **逐次表示の途中で切れたら再試行しない**。受け取ったところまでを「失敗」の状態で保存し、理由を示して、利用者が再送できるようにする (FR-106)。
- リランクと言い換えは締切 (300 ms) を過ぎたら諦め、再試行しない。
- 生成の設定 (temperature、top_p、max_tokens など) は設定で持ち、ターンに記録する。

## 8. トークン数

- 文脈の予算は `/tokenize` で数える (05 §4.1)。システムプロンプト・precept・確定したターンの数はキャッシュする (キーは本文のハッシュと model_key)。
- `/tokenize` が使えないときは、文字数からの見積もり (日本語 1 文字 = 1 トークン、英数字 4 文字 = 1 トークン、暫定) に縮退し、予算を 2 割減らす。

## 9. 接続の安全

- 既定では接続先をループバック (`127.0.0.1`、`::1`、`localhost`) に限る。それ以外は設定 `llm.allow_remote = true` と `https` が要る (確定、[OQ-23](10-decisions.md#oq-23-ループバック以外の-llama-server-を許すか))。
- API キーは `config.toml` (所有者だけの権限) か環境変数に置き、ログ・書き出し・`doctor` の出力に出さない。
- `evorag setup` が示す llama-server の起動例には、`--host 127.0.0.1` と `--api-key` を付ける。
- Unix ソケットでの接続は v1.0 までに検討する。

## 10. 対応する llama-server の版

- 対応する版の範囲は、公式の配布物の `build_info` の build 番号の下限で表し、リリースノートに書く。範囲を外れたら起動時に知らせる (動作は止めない)。
- 手元でビルドした llama-server は `build_info` が `b1-<commit>` の形になり、build 番号が版の目安にならない (S-02)。このときは範囲の確認を省き、`doctor` に `build_info` を表示するだけにする。
- 実際の llama-server を使う試験 (`cargo xtask live-llm`) で、対応する版の下限と最新を確かめる (09 §3.4)。

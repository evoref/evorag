## 1. 方針

- 推論は外部の llama-server (llama.cpp) に任せる。evorag は llama-server を起動・更新・管理しない (確定、[ADR-0010](10-decisions.md#adr-0010-外部の-llama-server-だけを使う))。
- 通信は HTTP で、既定はループバックだけ (§9)。`evorag-llm` は TLS を持たない。
- 足りない能力に応じて縮退して動く (§3)。
- 使うモデルは、役割ごとにデータ根に記録し、記録と違うモデルでは動かさない。切り替えは `evorag setup` でだけ行う (確定、[ADR-0018](10-decisions.md#adr-0018-モデルは-setup-で記録し切り替えは-setup-でだけ行う))。
- LLM の補助の呼び出しは、応答の経路に入れない。利用者が操作していない間に裏で動かす (確定、[ADR-0019](10-decisions.md#adr-0019-想起はリランカーの値で決めllm-の判断を応答の経路に入れない))。

## 2. 役割と接続

役割ごとに、接続先を設定で持つ。小さな埋め込みのモデルとリランカーの両方を使う構成を、**勧める構成** にする (ADR-0019。どちらも任意のままで、無ければ縮退する)。

| 役割 | 使う API | 必須か | 無いとき | 版 |
|---|---|---|---|---|
| chat | `/v1/chat/completions` (逐次表示、SSE) | 必須 | 起動しない (`evorag setup` の案内を出す) | v0.1 |
| embed | `/v1/embeddings` | 推奨 | ベクトルの検索を止め、語彙の候補だけでリランクする (05 §3.5) | v0.2 |
| rerank | `/v1/rerank` (サーバ側に `--reranking` が要る) | 推奨 | 添えるかどうかを v0.1 の語彙の規則で決める (05 §3.5) | v0.2 |
| memory | `/v1/chat/completions` (型縛り、逐次表示) | 任意。**既定は chat と同じモデル** (設定しなければ chat のサーバとモデルを使う) | chat のサーバとモデルで呼ぶ (縮退として記録する、§2.1) | v0.5 |

- 役割ごとに別のサーバ (またはルーターモードの別のモデル) が要る。chat のサーバは `/v1/embeddings` を、embed のサーバは `/v1/rerank` を 501 で断る (S-02)。memory は chat と同じ API なので、chat のサーバをそのまま使える。
- 役割は、足すだけで広げられる形にする (後の版の提案と採点のモデル、コーディングの応答のモデル)。

```toml
[llm.chat]
url = "http://127.0.0.1:8080"
model = "qwen3-32b"            # ルーターモードのときだけ意味を持つ
api_key_env = "EVORAG_LLM_KEY" # 環境変数の名前 (直接書くなら api_key)

[llm.embed]
url = "http://127.0.0.1:8081"

[llm.rerank]
url = "http://127.0.0.1:8082"

# v0.5。書かなければ chat と同じサーバとモデルを使う (§2.1)
# [llm.memory]
# url = "http://127.0.0.1:8083"
```

- 設定のキーの一覧は [07 §4](07-tui-config.md#4-設定)。`llm.embed`・`llm.rerank`・`llm.memory` の表は、chat と同じキー (`url`・`model`・`api_key`・`api_key_env`) を持つ。`llm.memory` は、補助の呼び出しに足す JSON (`request_extra`) も持つ (memory の呼び出しはすべて補助の呼び出しなので、chat の `aux_request_extra` に当たる)。`llm.memory` の表を足すときの設定の版の扱いは 07 §4.1。
- v0.1 の `[[llm.chat.models]]` (`/model` で切り替える候補) は、v0.2 から読んで無視し、通知を出す (キーを消すと、このキーを書いた設定で起動を拒むため。OQ-37 の 6)。
- **ルーターモード** (1 つの URL で複数のモデルを扱う、v0.2 で対応する、Should、FR-511、[OQ-13](10-decisions.md#oq-13-ルーターモードへの対応)): S-15 で、1 つの llama-server のプリセット (`--models-preset`) に chat・embed・rerank を置け、照合 (§3.1) と譲り方 (§4) を同じ規則で動かせることを確かめた。
  - **見分け方**: `/props` (`model` なし) の `role` が `router` なら、ルーターモードとして扱う。
  - **名前**: 役割ごとに、設定の `llm.<役割>.model` (プリセットの節の名前) を、すべての要求に付ける。POST は本文の `model`、GET は `?model=` (`/props`・`/slots`・`/tokenize` も。付けないと 400 で断られる)。名前を設定していない役割は、そのルーターでは無いものとして縮退する。
  - **照合**: model_key の計算は変えない (`/props?model=…` の `model_path` と、`/v1/models` のそのモデルの `meta`)。読み込んでいないモデルは `meta` を返さないので、照合の前に読み込みを待つ (`/props?model=…` で読み込みが始まる。待つ間は「接続待ち」)。
  - **降ろされたモデル**: ルーターは、数 (`--models-max`) や主記憶の余裕で、使っていないモデルを降ろす。次の要求は読み込み直し (数秒) を待つ。応答の経路の埋め込みとリランクが締切を過ぎたら縮退する (05 §3.5)。autoload を切ったルーターの 400 (`model is not loaded`) は、その役割が無いものとして縮退し、状態の行で知らせる。
  - **スロット**: スロットはモデルごと。`id_slot` と `/slots?model=…` を、モデルごとに使う。
  - 記録したモデルの名前 (§3.1) を常に送り、起動中にモデルを選び替える用途には使わない (ADR-0018)。
  - setup は、ルーターを見つけたら `/v1/models` の名前から役割の候補を出して選ばせる。勧める構成 (3 つの役割) を 1 つのプロセスで動かす手段として、プリセットの例を示す (S-15 §2)。

### 2.1 `memory` の役割 (v0.5)

裏の処理で、区切りごとの 1 回の呼び出し (B2。検索の鍵・単位・訂正の判定をまとめて出させる、04) に使うモデル ([ADR-0021](10-decisions.md#adr-0021-メモリの新エンジンを段階に分けて入れる) の決定 2、提案書 §2.3)。v0.7 の話題の見出しと v0.8 の気づきの提案も、この役割で呼ぶ。応答の経路では使わない。

- **既定は chat と同じモデル**: `llm.memory` を設定しなければ、chat のサーバ・モデル・記録 (§3.1) で B2 を呼ぶ。主記憶の少ない機械で、別のモデルの読み込みが chat の KV キャッシュを追い出し、次の応答で先頭の処理し直し (7〜14 秒) が起きるのを避けるため (S-15: ルーターは使っていないモデルを降ろし、chat の読み込み直しは 3.6 秒)。
- **速いモデルを選べる**: 裏の生成の速さは書かせる量とモデルの生成の速さで決まる (提案書 §1.2。Qwen3.5-9B で毎秒 10〜12 トークン、LFM2.5-8B-A1B で 33.5)。主記憶に余裕のある機械では、`llm.memory` に別のサーバかルーターのモデルを置ける。
- **勧めるモデルの候補**: 既定は chat と同じモデル。chat のモデルが遅い機械では Qwen3-4B-Instruct-2507 (単位の正しさは gemma-4-12b と同じで、生成は約 3 倍速い)。LFM2.5-8B-A1B と LFM3-1.7B は勧めない。LFM2.5-8B-A1B のように要求の `chat_template_kwargs` で思考を切れないモデルは、llama-server の `--reasoning-budget 0` が要る (§3.3 の点検で思考を切れないと分かったときの案内に書く) (S-17 の 4・5・6 で決めた、2026-11-26。spikes/S-17/REPORT.md §5〜§7)。決まるまでは、手順書でも chat と同じモデルを勧める。
- **文脈の長さ** (2026-11-28): B2 の 1 回の呼び出しは、要求の上限 3,584 トークンと生成の上限 (`max_tokens`) 2,048 トークンを合わせた 5,632 トークンを、使うスロットの文脈の長さ (`/props` の `n_ctx`。サーバの `-c` を `-np` で割った値、§3) に要する。足りない構成では B2 を呼ばず、`evorag doctor` で知らせる (04 §5.2.1 の「数え方」)。chat と同じサーバで呼ぶときも同じで、例えば `-np 2` なら `-c` を 11,264 以上にする。
- **縮退**: memory のサーバに繋がらない・記録と違うモデル・点検 (§3.3) に通らないときは、chat のサーバとモデルで呼ぶ。そのとき作った台帳は、使ったモデル (`model_key`) と縮退で作ったこと (`inputs` の `role_fallback`・`role_model_key`) を記録する。縮退の間は、縮退で作った台帳を今の選択の台帳とみなして呼び直さず、役割が戻ったら直前の選択の台帳として使う (04 §5.2.1。縮退の入りと出のたびに呼び直しが揺れないため)。状態の行と `evorag doctor` で知らせる。chat も使えないときは B2 を止める (会話は続く)。
  - **細目** (2026-11-27): `role_model_key` は、`llm.memory` を設定しないときは chat の model_key (memory の役割が chat と同じモデルなので、`role_fallback` は偽)、縮退の間は memory の記録の model_key (まだ記録が無い、つまり一度も繋がっていなければ null)。「chat も使えない」は、B2 を出す先 (既定と縮退の間は chat) の点検 (§3.3) に通らないことを指し、そのときは B2 を止めて状態の行と `evorag doctor` で知らせる。繋がらない・途中で切れたときは、呼び出しの失敗として 04 §5.2.1 の失敗の扱いに従う。B2 を出す先のモデルの点検がまだのときは、済むまで B2 を出さない (ノートの鍵と同じ。点検は裏の処理の最初の手順で流れる)。使っている memory のサーバに B2 の呼び出しが繋がらなかったときは「接続待ち」に戻し、繋がるまで chat で代行して 30 秒ごとに試す (§3 の表)。B2 の呼ぶ側は、区切りのまとまりを呼ぶ前ごとに、呼ぶ先の `/props` の model_key が選んだ時の model_key と同じかを確かめる (動いている間に llama-server のモデルが差し替わったときに、違うモデルで台帳を作らないため。違えば呼ばずに選び直す。2026-11-28)。まとまりは区切り 1 つ (分けた呼び出しを含む) にする。設定した memory のサーバのモデルが違った・繋がらなかったときは、どちらも「接続待ち」に戻して記録と照合し直し (§3 の表)、その間は chat で代行する。chat (既定と縮退の間の呼ぶ先) のモデルが違ったときは、B2 を呼ばずに応答の経路の照合 (§3) に任せる。確かめたスロットの文脈の長さが B2 に足りなければ呼ばない (M5.2 で決めた、2026-11-28)。
- **学習の結果の持ち方**: 選んだ変種 (v0.7) と開発側の表 (v0.6) は、memory の役割の model_key ごとに持つ (提案書 §9.5)。

## 3. 起動時の確認と縮退

1. `/health` で動いているかを確かめる (API キーなしで呼べる)。
2. `/props` (API キーが要る) で、`build_info`、`model_path`、`total_slots`、`default_generation_settings.n_ctx` を読む。`n_ctx` は **スロットごとの値** (サーバの `-c` を `-np` で割った値) で、文脈の予算 (05 §4.1) はこの値で計算する。
3. `/v1/models` で、モデルの名前と `data[0].meta` (`n_params`・`size`・`n_vocab`・`n_ctx_train`・`n_embd`) を読む。
4. model_key (§5) を作り、データ根のモデルの記録 (§3.1) と照合する。
5. model_key か llama-server の `build_info` が前回の点検 (§3.3) と違えば、点検を裏で流す。

| 状態 | 動き |
|---|---|
| chat に繋がらない | TUI を開かずに案内を出して終わる (終了コード 3)。`evorag setup` に誘導する |
| chat のモデルが記録と違う | TUI を開かずに、下の「記録と違うときの案内」を出して終わる (終了コード 6) |
| chat が途中で切れた | 状態の行を「未接続」にし、生成中なら失敗として記録する (§7)。5 秒ごとに `/health` で再接続を試みる |
| 再接続したら chat のモデルが記録と違う | 送信を止め、下の案内を画面に出す。入力欄の文章は残す (下書きとして保存される、04 §3) |
| embed・rerank に繋がらない | その役割が無いものとして縮退する (05 §3.5)。30 秒ごとに `/health` で再接続を試み、繋がって照合が通れば使い始める (llama-server を同時に起動して、モデルの読み込みが evorag の起動に間に合わなかったときのため)。状態の行に「接続待ち」を出す |
| embed が記録と違う | ベクトルの検索を止める (05 §3.5 の `no_embed`)。状態の行で知らせる |
| rerank が記録と違う | v0.1 の語彙の規則で添える (05 §3.5 の `no_rerank`)。状態の行で知らせる |
| memory に繋がらない・記録と違う (v0.5、`llm.memory` を設定したとき) | memory のサーバを使わず、chat のサーバとモデルで B2 を呼ぶ (§2.1 の縮退)。繋がらないときは embed・rerank と同じく 30 秒ごとに再接続を試み、繋がって照合が通れば使い始める。状態の行で知らせる |
| `/slots` が無い (サーバの `--no-slots`) | 譲る判定を省き、裏の処理は利用者の操作が無いときだけ動かす |

**記録と違うときの案内** (chat、NFR-604):

- 記録したモデルのファイル名と、今繋がっているモデルのファイル名を並べて示す。
- 会話のデータには触れていないので、無事であることを示す。
- 取れる手を、そのまま打てる形で示す。
  1. 記録したモデルで llama-server を起動し直す。
  2. `evorag setup` で切り替える。応答のモデルの切り替えでは、やり直すものが無いことを添える (§3.2)。
  3. 試すだけなら、別のデータ根を使う (`evorag --data-root <別のフォルダ>`)。
- ファイル名だけが違い、`meta` の値 (`n_params`・`size`・`n_vocab`) がすべて同じときは、「同じモデルの可能性が高い。`evorag setup` で『同じモデルとして扱う』を選べます」と言い分ける。

### 3.1 モデルの記録と照合 (v0.2)

確定 ([OQ-37](10-decisions.md#oq-37-モデルの記録照合切り替えの手順) の 1・2)。

- **記録**: 「役割 → model_key」の表をデータ根に記録する (03 §3.3 の `model_binding`。役割ごとに 1 件)。違いの中身を見せられるように、model_key の元の値 (`model_path` のファイル名、`/v1/models` の名前と `meta` の値、`build_info`) も残す。切り替えの前の model_key は、その記録の履歴に残す。
- **いつ記録するか**:
  - 新しいデータ根: `evorag setup` (または最初の TUI の起動) で、繋がっている役割のモデルを記録する。
  - v0.1 のデータ根 (記録が無い): v0.2 の最初の起動で、繋がっているモデルを記録する (プロンプトの言語と同じ規則、07 §6.1)。記録したことを起動時の通知で知らせる。chat は、過去の応答のターンで最も多く使われた model_key と比べ、違えば「いつもと違うモデルを記録しました。違うなら `evorag setup` で直せます」と示す (たまたま試しのモデルで初めて起動したときのため)。
  - 記録の無い役割 (後から embed や rerank の接続を足した): 次の起動で、繋がっているモデルを記録し、通知で知らせる。リランカーなら、しきい値をまだ持たないので、TUI を開いた後に裏で求める (05 §3.7)。
  - `memory` の役割 (v0.5): `llm.memory` を設定したときだけ記録を作る。設定しなければ記録を作らず、chat の記録を使う (chat と同じモデルなので、別に照合しない)。`llm.memory` を後から足したときは、記録の無い役割と同じく次の起動で記録し、通知で知らせる。
- **照合**: 起動と再接続のたびに、繋がっているモデルの model_key を記録と比べる。違うときの動きは §3 の表。
- 照合は llama-server のふりをする別のプロセスへの送信を止める対策も兼ねる (02 §8.2)。

### 3.2 setup での切り替え (v0.2)

確定 (OQ-37 の 3〜5・8)。

1. **ロックを先に確かめる**: setup は、最初にデータ根のロックを確かめる。TUI が動いていれば、問いを始める前に「設定だけを書けます。モデルの記録を書き換えるには、evorag を閉じてから実行してください」と示す (記録を書き換える setup は DB に書くので、TUI を閉じてから実行する、03 §9)。
2. **サーバを探す**: 既定の接続先 (8080〜8082) と設定の接続先を調べ、API で役割を見分ける (`/v1/embeddings` と `/v1/rerank` が 501 で断られるかどうか、S-02)。足りない役割ごとに、llama-server の起動の例 (役割に要る引数、ポート、`--host 127.0.0.1`、`--api-key`) を示す。v0.1 の設定で `/model` の候補にしていたサーバ (8081 など) が chat のサーバなら、そのことを示す。
3. 役割ごとに、記録したモデルと繋がっているモデルの違い (ファイル名、名前、`meta` の値、量子化の違い) を示す。
4. 違うときは、やり直しになるものと時間の目安を示す。
   - chat: v0.2 では、やり直すものは無い (学習した成果の確かめ直しは v0.4 から、13 §8)。chat だけが違うときは、確認 1 回で終わる短い流れにする (言語の問いやサーバの探索をやり直させない)。
   - embed: ベクトルの索引の作り直し (件数と、点検で測った速さからの目安)。作り直しは裏の処理で、利用者が操作していない間だけ進むことを添える (04 §4)。その間は語彙の候補とリランクで答える。
   - rerank: しきい値の求め直し (05 §3.7)。setup の中でその場で行い、進み具合を出す。「後で」を選ぶと job に登録し、TUI の裏で行う。
   - memory (v0.5): 古い区切りの台帳は自動では作り直さない (確定、2026-11-26、04 §5.2.1)。新しい区切りから新しいモデルで台帳を作り、古い区切りは前のモデルの台帳 (直前の選択) で導いた単位を使い続ける。作り直したいときは `evorag rebuild --ledgers` (07 §5) で明示し、そのときに区切りの数と、点検で測った生成の速さからの時間の目安を示す。前のモデルの台帳は、次の採用が落ち着くまで残す。chat と同じモデルに戻す (`llm.memory` を消す) ときも同じ。`llm.memory` を設定していないときは B2 を chat のモデルで呼ぶので、**chat のモデルを切り替えると、台帳の選択も替わる** (上と同じく、古い区切りは前のモデルの台帳を使い続ける)。主記憶の少ない機械で別のモデルを置くと、chat の KV キャッシュを追い出しうることを示す (§2.1)。
5. 利用者が明示に確かめたときだけ、記録を書き換える。確かめなければ、設定 (`config.toml`) だけを書く。chat が違うまま終えるときは、「このままでは次の起動で止まります。llama-server を <記録したファイル> で起動し直してください」と示す。
6. 記録の更新と、やり直しの手順の一覧 (`job`) は、同じコミットで書く。途中で落ちたら、起動時に続きを行う。job を失っても、要る作り直しは状態から求め直す (04 §4)。
7. **同じモデルとして扱う**: model_key は、ファイル名の変更や llama-server の更新でも変わる (§5)。setup で「同じモデルとして扱う」を選ぶと、記録の model_key と元の値だけを直し、やり直しをしない。この選択は、次のすべてを満たすときだけ出す。
   - `meta` の `n_params`・`size`・`n_vocab` がすべて同じ (どちらかで値が得られないものは比べない)。量子化の違いは、別のモデルとして扱う。
   - embed は、次元 (`n_embd`) が同じで、さらに保存したチャンクの一部 (既定 8 件) を新しいサーバで埋め込み直し、保存したベクトルとの cosine が 0.99 以上 (暫定) で一致する (重みが違うのに「同じ」を選ぶと、想起が黙って悪くなるため。OQ-43 の 1 と同じ確かめ方)。
   - rerank には、v0.2 ではこの選択を出さない。しきい値は同梱の事例から求め直せて、利用者の入力も要らないので、切り替えのたびに求め直す (05 §3.7)。利用者の信号で動かしたしきい値を持つ v0.4 で、確かめ方を決める。
8. **前のモデルに戻した**: 埋め込みは前の世代の索引が残っていれば使う (05 §2.2)。リランカーは、そのモデルのしきい値の記録が残っていれば使う。成果は model_key ごとに持つ (ADR-0020)。
9. **新しいモデルを試す**: 記録を変えずに別のモデルを試したいときは、別のデータ根 (`--data-root`) を使うよう案内する。起動中の切り替えと、記録を変えずに一時的に使う機能は持たない (ADR-0018)。

### 3.3 モデルの性質の点検 (v0.2)

確定 (OQ-37 の 7)。モデルとサーバの組み合わせで、使える機能と速さが違う (S-13 §4・§5)。

| 役割 | 確かめること | 通らないときの動き |
|---|---|---|
| chat | プロンプトの処理と生成の速さ (トークン毎秒)。補助の呼び出しで思考を切れるか (`llm.chat.aux_request_extra`、§6)。型縛りの出力が空にならないか | 思考を切れない・型縛りの出力が空になる: v0.4 から、設定の `aux_request_extra` に `chat_template_kwargs` が無ければ、`chat_template_kwargs = { enable_thinking = false }` を足してもう一度確かめる (OQ-52)。通ったら、その指定を点検の結果に記録して補助の呼び出しに足し、`evorag doctor` で自動で足したことを示す。それでも通らないときは、型縛りの補助の呼び出し (ノートの鍵・抽出など) を止め、状態の行と `evorag doctor` に理由を出す。会話は続く |
| embed | 次元の数、問い 1 件の埋め込みの時間 | 失敗: 埋め込みが無いものとして動く |
| rerank | 往復 6 件のリランクの時間、値が数として返るか | 締切 (05 §3.4) に 3 ターンでも収まらない: 応答の経路でリランクを使わない (05 §3.5 の `rerank_slow`)。失敗: リランカーが無いものとして動く |
| memory (v0.5、`llm.memory` を設定したとき) | 生成の速さ (トークン毎秒)。思考を切れるか (`llm.memory.request_extra`。chat と同じく、無ければ `chat_template_kwargs` の指定を足して確かめ直す、OQ-52)。B2 の型 (04) で小さな固定の区切りを呼び、型縛りの出力が空にならず型に合うか | 通らない: memory のサーバを使わず、chat のサーバとモデルで B2 を呼ぶ (§2.1 の縮退)。理由を状態の行と `evorag doctor` に出す |

- chat の点検 (v0.5): chat の行に、B2 の型での小さな固定の区切りの呼び出しを足す (memory を設定しないときは chat で B2 を呼ぶため)。スロットの文脈の長さが B2 に足りない構成 (§2.1 の「文脈の長さ」) では、点検の呼び出しをせずに B2 を止め、理由を示す。通らないときは B2 を止める (区切りの台帳を作らない。会話と想起は続く)。
- **B2 の型の点検の細目** (M5.2 で決めた、2026-11-28): v0.5 の根の chat と memory の点検で、型縛りの確かめと速さの後に流す。区切りは固定の 1 往復 (利用者の発話 1 文、応答なし。日本語のデータ根は「私は大阪に住んでいて、週末は将棋を指します。」) で、要求は B2 と同じ形 (システムのメッセージ・利用者のメッセージの形・JSON Schema・temperature 0・固定の seed・使うスロット・要求の付け足し) にし、生成の上限だけを 512 にする。出力の読み取り (04 §5.2.1 の「書くときの読み取り」) で `complete` になれば通る。結果は点検の結果の `b2_ok` に書く (型縛りの確かめに通らなければ呼ばずに偽、文脈の長さが足りなければ呼ばずに偽と理由)。繋がらない・締切切れで結果が出なかったら保存しない。`b2_ok` の無い v0.5 の根の chat・memory の結果は、点検し直す。B2 を出す先の役割は、`b2_ok` が真の結果のときだけ使う。通らないことは、状態の行と `doctor` で型縛りの出力が使えないこととして示す。

- 小さな固定の課題 (作った文) で確かめ、結果を model_key と `build_info` ごとに保存する (03 §3.3 の `model_probe`。作り直せる派生の記録)。chat と memory の結果は、点検に渡した要求の付け足し (設定の `aux_request_extra`・`request_extra`) のハッシュも持つ (v0.5)。
- 行うのは、`evorag setup` のときと、model_key か `build_info` が前回の点検と違うときだけ。起動のたびには行わない (NFR-101)。**例外** (2026-11-28): chat と memory は、要求の付け足しのハッシュが前回の点検と違うときも点検し直す (案内どおりに設定を直したら、model_key が同じでも確かめ直すため)。また、型縛りの確かめが接続の失敗や締切切れで終わり、結果が出なかった点検は保存せず、次の機会に点検し直す (一時の失敗で「点検に通らない」に固定しないため)。llama-server の起動の引数 (`--reasoning-budget 0` など) だけを直したときは、model_key と `build_info` が同じなので自動では点検し直さない。`evorag setup` で点検し直す (setup は、前回の結果が通らなかった chat と memory を点検し直す)。起動のときに流すときは、TUI を開いてから裏で流し (04 §4 の「起動後の点検」)、終わるまでは既定の値で動く。
- 点検の結果は `evorag doctor` で見られる。

## 4. スロットと譲り方

- llama-server はスロットを役割ごとに予約しない。そのため、chat のサーバのスロットが 2 つ以上あるときは、**応答の要求も裏の処理の要求も `id_slot` を明示する**。応答は最初のスロット、裏の処理は最後のスロットを使う (`/v1/chat/completions` で `id_slot` が効くことを S-02 で確かめた)。次のターンの分を先に処理する要求 (05 §4.5) は、応答のスロットを使う。
- スロットが 1 つしか無ければ、裏の処理は利用者が操作していないときだけ動かす。
- 裏の要求を出す前に `/slots` の `is_processing` を見て、応答のスロットが処理中なら出さない。
- 利用者の要求が来たら、裏の要求の接続を切って止める。llama-server は接続が閉じると生成を取り消し、0.2 秒ほどで止まる (S-02。逐次表示でもそうでなくても止まる)。**応答の本体を捨てて TCP の接続を確実に閉じる** こと (応答の読み取りのオブジェクトがソケットを持ったままだと、接続は閉じず、生成は最後まで続く)。裏の要求は、止めたところまでの結果を捨てやすいように逐次表示 (stream) で出す。
- **埋め込みとリランカーのサーバにも同じ規則を当てる** (OQ-42 の 4): 裏で埋め込みを作っている間、同じ GPU を使う応答のプロンプトの処理は 28〜42% 遅くなった (S-13 §5)。利用者が入力している間と、応答を生成している間は、裏の埋め込みとリランクの要求を出さず、出ているものは切る。応答の経路の埋め込みとリランク (05 §3) は止めない。
- 優先の順: 利用者の要求 (応答の経路) > 先に済ませる処理 (05 §4.5) > 裏の処理 (04 §4)。
- **キャッシュの残り方**: llama-server は、上書きした会話のプロンプトのキャッシュを主記憶 (`--cache-ram`、既定 8192 MiB) に持ち続ける (S-13 §3)。消えるのは llama-server を再起動したとき (または `--cache-ram 0`)。スロットのキャッシュの消去 (`/slots/{id}?action=erase`) は、サーバを `--slot-save-path` 付きで起動したときだけ使える (既定では 501)。`--slot-save-path` は KV キャッシュをディスクに書くので、evorag の案内では勧めない。忘れる・削除のときは、飛んでいる先読みと裏の要求 (B2・埋め込み・リランク) を止めて止まったことを確かめてから (04 §7.2)、構成を見分けずに、応答 (`chat`) と `memory` (v0.5。`llm.memory` を設定したとき) の役割のモデルごとに、すべてのスロット (`/slots` で数える。数えられなければ `/props` の `total_slots`、上限 64) へ消去を要求し、断られたら (501 など) 無視する。消去の要求は再試行しない (§7 の再試行の外。501 を繰り返さないため)。ルーターの構成では本文にモデルの名前を付ける。1 つの要求と `/slots` の照会にそれぞれ 5 秒、全体に 10 秒の上限を置き、超えたら残りを諦める (終了を止めないため)。ログには結果の種類だけを書き、応答の本文は書かない。忘れる・削除の約束の範囲は 04 §7.2・§7.8。
- 裏の処理には長いプロンプトを一度に送らない (1 回 2,048 トークンまで、04 §4)。v0.5 の B2 の 1 回の入力の上限は、区切りの大きさ (04) から決まる (暫定 2,048 トークン)(B2 は 3,584 トークンまで、04 §4。2026-11-28 に 3,072 から上げた、spikes/S-17/REPORT.md §5.6) (S-17 の 4・5・6 で決めた、2026-11-26。spikes/S-17/REPORT.md §5〜§7)。
- **memory の役割** (v0.5): chat と同じサーバとモデルのときは、chat の裏の処理と同じく最後のスロットを使い、同じ規則で譲る。別のサーバのときも、同じ GPU を使いうるので、embed・rerank と同じく、利用者が入力している間と応答を生成している間は要求を出さず、出ているものは切る (1 秒以内に止める、NFR-105)。ルーターの構成で別のモデルを置くときは、B2 の要求がモデルの入れ替えを起こし、chat の読み込み直しを待たせうる (§2.1)。B2 は逐次表示で出し、止めたときは、受け取った分のうち型の上で完結した要素を `partial` の台帳に残す (04 §5.2.1、確定、2026-11-26)。

## 5. model_key

モデルを識別する値。ターンに記録し、記録 (§3.1)・埋め込み・しきい値・学習したものは model_key ごとに分ける (v0.1 で定義を固めた)。

- 作り方: `/props` の `model_path` のファイル名 (フォルダを除く。`/` と `\` のどちらも区切りとみなす) と、`/v1/models` の `data[0].meta` の `n_params`・`size`・`n_vocab` を、この順に改行 (`\n`) で区切って連結し (UTF-8、数は 10 進)、SHA-256 の先頭 16 バイトを小文字の 16 進 (32 文字) で書く。
  - `meta` を返さない版、または 3 つの値のどれかが無いときは、3 つの値の代わりに `data[0].id` (モデルの名前) を 1 行で使う (ファイル名 `\n` 名前)。
- evorag は `model_path` のファイルを読まない (llama-server が別のコンテナ・権限で動いていることがあるため)。
- ファイル名に含めるので、ファイル名を変えると model_key も変わる。llama-server の版で `meta` の返し方が変わったときも変わりうる。中身が同じモデルなら、setup の「同じモデルとして扱う」(§3.2) で記録を直す。
- model_key は公開の値から計算できるので、偽れる。照合は「うっかり違うモデルで動かす」ことを防ぐもので、悪意のある偽装を防ぐものではない (02 §8.2)。
- 定義を変えるときは新しい種類の値として足し、古い値も読み続ける (03 §4)。

## 6. 出力の型縛り

- 補助の判定と抽出 (v0.4 まではノートの検索の鍵、事実の候補、訂正の検証。v0.5 からは区切りごとの B2 (04) の 1 回の呼び出し。v0.7 から話題の見出し) は、Rust の型に合わせた JSON Schema を `response_format` (`{"type": "json_schema", ...}`) で送る (v0.2)。型は小さい (鍵の並びなど) ので、Schema は呼び出しの隣に手で書き、`schemars` は使わない (推移的な依存を増やさない、NFR-203。2026-11-12)。
- 受け取った JSON は型で検証し、合わなければ 1 回だけやり直し、それでも合わなければその対象 (ノートなら区切り) を飛ばしてログに残す。進み具合を状態から求める手順 (04 §4) は `job` を書かないので、飛ばした対象はこのプロセスの間だけ覚え、次の起動でもう一度試す (2026-11-12)。v0.5 の B2 は、飛ばさずに `failed` の台帳を書く (失敗の扱いと、続けて失敗したときに止めることは 04 §5.2.1)。
- 型縛りの呼び出しは temperature 0 と固定の seed で出し、`id_slot` を固定する (スロットを固定すると同じ入力から同じ出力が得られ、固定しないと割り当てられたスロットで出力が変わることを S-02 で確かめた)。
- **B2 の要求の先頭** (v0.5): 指示・辞書・型の説明は、プロンプトの言語と変種ごとにバイト列まで同じにし、区切りの本文をその後ろに置く (裏のスロットのキャッシュを区切りの間で使い回すため、提案書 §5.1)。JSON Schema は、`s` と `id` の列挙 (その呼び出しの文番号と候補の番号) と `corrections` の `maxItems` (候補の数) だけが呼び出しごとに変わる (文法は出力の縛りで、プロンプトのキャッシュには掛からない)。既存の単位はプロンプトに入れない。型 (`keys`・`units`・`corrections`) の正本は 04 §5.2 と OQ-53。上限 (`keys` の 8 個、`units` の数) と `s`・`id` の列挙は JSON Schema で縛り (`maxItems`・`enum`)、書くときの型 (すべて必須) と、台帳を読むときの型 (寛容) を分ける (04 §5.2)。型が合わない節は、その節だけを理由とともに台帳に残し (04)、やり直しは呼び出しごとに 1 回までにする (区切りを分けて呼んだときは、分けた呼び出しが独立に失敗するので呼び出しごと。上の「1 回だけやり直し」と同じ。04 §5.2.1 の「分けた呼び出しのまとめ方」)。
- 思考の部分を出すモデル (Qwen3.5 など) は、補助の呼び出しで思考を切る設定 (`chat_template_kwargs: {"enable_thinking": false}` など) が要る。モデルごとに設定 `llm.chat.aux_request_extra` (要求に足す JSON。memory の役割を別に置いたときは `llm.memory.request_extra`、v0.5) で持つ。設定に無いときは、点検 (§3.3) が `chat_template_kwargs` の指定を試し、通ったことを点検の結果に記録して、補助の呼び出しに自動で足す (v0.4、OQ-52。v0.3.0 の受入で、設定が無いために抽出が止まっていた)。設定ファイルは書き換えない。`evorag setup` と `evorag doctor` は、自動で足していることと、設定に書くときの形を示す。応答の要求で思考を切りたいときは、`llm.chat.request_extra` で同じように持つ (思考を出すモデルは、思考が終わるまで本文が流れ始めないため)。
- 思考を切れないモデルでは、思考を切る指定と型縛りを併せると出力が空になることがある (S-13 §4)。点検 (§3.3) で見つけたら、型縛りの補助の呼び出しを止める。

## 7. 再試行と失敗の扱い

- 接続の失敗と 5xx だけを、指数バックオフ (0.5 s、1 s、2 s) で 3 回まで再試行する。4xx は再試行しない。
- **逐次表示の途中で切れたら再試行しない**。受け取ったところまでを「失敗」の状態で保存し、理由を示して、利用者が再送できるようにする (FR-106)。
- 応答の経路の埋め込みとリランクは、締切 (05 §3.4) を過ぎたら諦め、再試行しない。
- 生成の設定 (temperature、top_p、max_tokens など) は設定で持ち、ターンに記録する。

## 8. トークン数

- 文脈の予算は `/tokenize` で数える (05 §4.1)。システムプロンプト・precept・確定したターンの数はキャッシュする (キーは本文のハッシュと model_key)。
- `/tokenize` が使えないときは、文字数からの見積もり (日本語 1 文字 = 1 トークン、英数字 4 文字 = 1 トークン、暫定) に縮退し、予算を 2 割減らす。

## 9. 接続の安全

- 既定では接続先をループバック (`127.0.0.1`、`::1`、`localhost`) に限る。それ以外は設定 `llm.allow_remote = true` と `https` が要る (確定、[OQ-23](10-decisions.md#oq-23-ループバック以外の-llama-server-を許すか))。embed と rerank と memory (v0.5) の接続先にも同じ規則を当てる。memory がループバック以外のときは、発話の本文 (private の値を含む、04) が裏の呼び出しで外の機械に出ることを、setup と `/private` の確認で示す。
- `llm.allow_remote = true` のときは、入力が止まったときに先に済ませる処理を既定で切る (05 §4.5)。
- API キーは `config.toml` (所有者だけの権限) か環境変数に置き、ログ・書き出し・`doctor` の出力に出さない。
- `evorag setup` が示す llama-server の起動例には、`--host 127.0.0.1` と `--api-key` を付ける。
- Unix ソケットでの接続は v1.0 までに検討する。

## 10. 対応する llama-server の版

- 対応する版の範囲は、公式の配布物の `build_info` の build 番号の下限で表し、リリースノートに書く。範囲を外れたら起動時に知らせる (動作は止めない)。
- 手元でビルドした llama-server は `build_info` が `b1-<commit>` の形になり、build 番号が版の目安にならない (S-02)。このときは範囲の確認を省き、`doctor` に `build_info` を表示するだけにする。
- 実際の llama-server を使う試験 (`cargo xtask live-llm`) で、対応する版の下限と最新を確かめる (09 §3.4)。

## 1. ビジョン

evorag は、**手元の llama-server だけで動く、覚えていて、少しずつ良くなる対話の相手** である。

- 会話はすべて利用者の PC の中に残り、外へ出ない。
- 以前の会話と、そこから取り出した利用者についての事実を、出典つきで応答に添える。
- 利用者の評価と訂正から、短い指示 (precept) を学び、悪化しないことを確かめてから使う。モデルの重みは学習しない。
- 後の版で、利用者が持ち込む文書の束 (カートリッジ) からも引けるようにする。

TUI 版を最小核 (v0.1) から段階的にリリースしながら進化させる。本体は OSS (Apache-2.0) で公開する。

## 2. 目標 (Goals)

| # | 目標 |
|---|---|
| G1 | 手元の llama-server に接続して、日本語で快適に会話できる (IME、逐次表示、中断、再生成) |
| G2 | 会話を失わない。強制終了・電源断・DB の破損からも、会話の本文と利用者の明示の操作を戻せる |
| G3 | 以前の会話と利用者についての事実を、別のセッションでも思い出して応答に添える |
| G4 | 利用者が「忘れて」と言ったものを、約束した範囲から確実に消す |
| G5 | 利用者の強い信号 (評価・検証済みの訂正) から precept を学び、回帰しないことを確かめてから使う |
| G6 | 版を上げても、古い版のデータを失わずに読み続け、巻き戻せる |
| G7 | 外部の llama-server の能力の違い (埋め込み・リランクの有無、スロット数) に応じて縮退して動く |

## 3. 非目標 (Non-Goals)

| # | 非目標 | 理由 |
|---|---|---|
| N1 | モデルの重みの学習 (LoRA・アダプタを含む) | 不採用 ([ADR-0012](10-decisions.md#adr-0012-重みを学習しない))。学ぶのはプロンプトに足す文字列だけ |
| N2 | LLM の推論エンジンを内蔵すること | llama-server を外部のプロセスとして使う。evorag は llama-server を更新・管理しない |
| N3 | クラウドの LLM・外部の検索サービスへの接続 | 会話を外へ出さない (P2)。必要になれば別の ADR で検討する |
| N4 | テレメトリ・自動の更新確認 | 外へ通信するのは、利用者が明示した更新の確認と取得だけ ([ADR-0011](10-decisions.md#adr-0011-外へ通信するのは-llama-server-と手動の更新だけ)) |
| N5 | 複数の利用者・共有のサーバとしての運用 | 1 人で使う PC を前提にする (脅威モデル、[02 §8](02-architecture.md#8-脅威モデル)) |
| N6 | v1.0 までのコーディングモード・道具の実行・エディタ連携専用のモード | チャットとメモリを先に固める ([08 §2.8](08-roadmap.md#28-v06-より後))。構想は [15](15-coding.md) |

## 4. 設計原則 (優先順位付き)

原則同士が衝突した場合は **番号の小さい方を優先** する。各 ADR はどの原則に基づくかを明記する。

| 優先 | 原則 | 意味 | 衝突時の例 |
|---|---|---|---|
| P1 | **会話を失わない** | 会話の本文と利用者の明示の操作は、確定したら必ずディスクに残す。壊れたら戻せる経路を持つ | 応答を速くするために、発話の保存を後回しにしない |
| P2 | **利用者の同意なく外へ出さない** | 通信先は設定した llama-server と、利用者が打った更新の確認・取得だけ。ログにも会話の本文を出さない | 便利な自動の更新確認より、通信しないことを優先する |
| P3 | **利用者の意思を守る** | 忘れる・private・削除は、約束した範囲で即時に効かせる。約束できない範囲は正直に伝える | 退避の都合より、忘れる操作を優先する |
| P4 | **悪くしない** | 学習・検索の変更は、回帰しないことを確かめてから使う。確かめられないものは採用しない | 改善の見込みがあっても、回帰の判定ができなければ採らない |
| P5 | **利用者を待たせない** | 応答の経路で重い処理をしない。裏の処理は利用者の要求に譲る | sleep-time の進みより、応答の速さを優先する |
| P6 | **後方互換を守る** | ディスク上の形式・書き出しの形式は、v0.4 までに最適な構成に固め、v0.5 を互換の起点にして以後は足すだけで広げる。それまでも、直前の版のデータは必ず移行する | 内部の作りやすさより、古いデータが読めることを優先する |
| P7 | **依存は少なく、理由を持って選ぶ** | C を含む依存は 0 を原則にする。新しい依存は理由・代替・ライセンスを記す | 便利でも重い依存は避ける |
| P8 | **小さく始め、拡張点だけ先に決める** | 初期の版では使わない機能を作らないが、後で足す場所 (記録の種類・索引の種類・コアの API) は先に決める | 汎用の仕組みを先に作り込まない |

## 5. 想定ユーザー (ペルソナ)

| ペルソナ | 状況 | 求めること |
|---|---|---|
| A: ローカル LLM を常用する個人 | 64 GB 前後の PC で llama-server を動かしている。日本語で日々の相談・調べものをする | 以前話したことを覚えていてほしい。会話を外に出したくない |
| B: 手元の文書を引きたい人 (v0.5〜) | 社内の手順書・自分のメモを持っている | 出典つきで答えてほしい。無いものは無いと言ってほしい |
| C: 開発に関わる人 | Rust で寄稿したい・自分の環境で試したい | 仕様が読める。決定的な試験で確かめられる |

### 7.1 文書運用ルール

1. **正の情報源**: 決定事項の状態は 10-decisions が正。状態の表記は「確定」「確定 (ユーザー回答)」「一部提案中」「提案中」(定義は 10 §0.1)。他文書は ADR・OQ の番号で参照する。概念ごとの正本は [README §4](README.md#4-正本マップ) に従い、正本でない文書は定義を再掲せず参照する。
2. **ID の不変性**: FR / NFR / ADR / OQ / AC は一度振ったら再利用・振り直しをしない。廃止した ID は「廃止」と明記して残す。
3. **矛盾を見つけたとき**: 10 に OQ として起票し、解決後に両方の文書を直す。
4. **確定手続き**: PO が ADR・OQ を確認して状態を「確定」に変える。PO が確認する前の ADR・OQ を「確定」と書かない。
5. **PO の判断が要る変更の書き方**: 本文は推奨案で書き、判断が要る箇所に「(提案、OQ-<番号>)」を付ける。代替案は 10 の該当 OQ に置く。
6. **版の書き方**: 時期は版名 (v0.1〜v0.6、v1.0、v1.x) で書く (08)。日付ではなくゲートで区切る。
7. **自己完結**: 仕様書の本文は docs/ の中で完結させる。作業用のメモやレビューの記録を参照しない。改訂の経緯は本文に書かず、git で追う。
8. **用語集の書き方**: 用語集 (§6) の各行は定義 1 文と正本の節へのリンクだけにする。
9. **数値**: 特記のない数値は目安で、計測で確定させる値には「(暫定)」を付ける。確定の手段 (ベンチ・試作) を 09 に置く。

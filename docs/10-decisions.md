## 0. 運用ルール

### 0.1 状態

| 状態 | 意味 |
|---|---|
| **提案中** | 推奨案として記載。変わりうる。実装着手の根拠にしない |
| **確定** | PO が決めた (指示または確認)。変えるには新しい ADR を起こす |
| **確定 (ユーザー回答)** | PO が推奨案 (または示した選択肢) に回答して確定したもの。扱いは「確定」と同じ |
| **一部提案中** | 一部が確定し、細目や残りが提案中のもの。確定した部分と提案中の部分を書き分ける |
| **条件付き確定 (S-nn)** | PO が確定し、スパイク S-nn の結果が合否の基準を満たすことを条件とするもの。実装着手の根拠にしてよい。満たさなかったときは、その節の「条件を満たさないとき」の代替を採り、本書に記録する |

### 0.2 書式

- 各 ADR は「状態 / 決定 / 根拠 (どの設計原則に基づくか) / 影響」を持つ。最終的な決定 (提案中のものは推奨案) だけを書き、検討の経緯は書かない。
- 各 OQ は「件名 / 推奨 / 代替 / 区分 / 期限」を持つ。

### 0.3 確定手続き

1. PO が本書をレビューし、ADR ごとに「確定 / 修正 / 不採用」、OQ ごとに回答する (まず上の「PO が決める事項」)。
2. 回答に基づき本書と関連の文書を直す。
3. 着手のゲートに要る ADR・OQ は、PO の 1 回の承認でまとめて推奨どおり確定してよい (状態は「確定 (ユーザー回答)」)。

### 0.4 OQ の区分

| 区分 | 意味 | 扱い |
|---|---|---|
| **PO** | 製品の方針・安全・互換・範囲に関わる | PO の回答で確定する。回答が無ければ着手のゲートで止まる |
| **裁量** | 推奨案が明確で、変えても局所的 | 推奨案で本文を書いた。期限までに PO の異議が無ければ推奨で確定する |
| **スパイク** | 技術的な事実で決まる | 08 §3 のスパイクの結果で確定し、本書に記録する |

### ADR-0001: 仕様書駆動での開発

- **状態**: 確定 (ユーザー回答)
- **決定**: 仕様書 (docs/) の **その版の範囲** を確定してから、その範囲の実装 (Cargo.toml を含む) を作る。docs/ を正本にし、実装中に仕様と食い違う判断が要るときは、仕様書を先に直す。対象外: 技術検証のスパイク (`spikes/`、使い捨て)、開発運用の文書・設定 (`CLAUDE.md`・`.claude/`・11)、開発用の道具 (`xtask`)。
- **根拠**: P6、P8。
- **影響**: 着手の条件は 08 §5。運用は 11。

### ADR-0002: リリース最優先の段階リリース

- **状態**: 確定 (ユーザー回答)。版の割り当ての中身は OQ-03 (確定 (ユーザー回答))。
- **決定**: v0.1 で「ある程度は使える」最小核を出し、その後の版で少しずつ機能を足す。版は日付ではなくゲートで区切る。後の版で足すものは、v0.1 で決めた形式と公開面を壊さない (足すだけの) 形で入れる。機能リリースは `0.y.0`、bugfix はパッチ版。
- **根拠**: P6、P8。
- **影響**: 08。ブランチと版の運用は 11 §9.1。

### ADR-0003: TUI とコアを 1 つのプロセスで動かす

- **状態**: 確定 (ユーザー回答、2026-11-09)。推奨どおり (G1)。
- **決定**: 初期は TUI とコアを 1 つのプロセスで動かし、TUI を閉じるとコアも止まる。コアと画面の間はコアの API (命令・イベント・照会) で切り、後で常駐やほかの画面に分けるときは、この API をプロセスの外へ出す。
- **根拠**: P8 (常駐の仕組みを先に作り込まない)、P1 (プロセスが 1 つならデータ根の書き手も 1 つ)。
- **影響**: 02 §1・§3。常駐の採否は OQ-25。

### ADR-0004: 記録の正本は redb の汎用の表

- **状態**: 確定 (ユーザー回答)。汎用の構成 (少数の汎用の表に種類を付けた記録を入れ、機能を足すときは種類を増やす) は 2026-11-08、DB の実装に redb を使うことは 2026-11-09 (G1。耐久性は S-01 で合格)。
- **決定**: 埋め込み型の DB の redb を 1 ファイルで使い、`meta`・`records`・`links`・`lookup`・`blobs` の 5 表を持つ。DB の操作は `evorag-store` の trait に閉じ込める。SQLite は外部の道具で中を見られる利点があるが、C を含む依存になるので採らない。
- **根拠**: P6、P7、P1 (ACID)。
- **影響**: 03。redb のメジャー版の上げ方は OQ-16。

### ADR-0005: 記録の本体は項目名つきの CBOR

- **状態**: 確定 (ユーザー回答、2026-11-09)。推奨どおり (G1)。
- **決定**: 封筒の本体は項目名つきの CBOR (ciborium) にする。並び順で意味が決まる符号は使わない。書き出しとジャーナルは JSON Lines にする。
- **根拠**: P6 (項目を足しても古いデータが読める)、P5 (JSON より小さく速い)。
- **影響**: 03 §3.2・§6・§11。

### ADR-0006: 会話のジャーナルを先に書く

- **状態**: 確定 (ユーザー回答、2026-11-09)。推奨どおり (G1)。
- **決定**: 会話のターンと明示の操作を、DB とは別の追記専用のジャーナルにも書く。書き手スレッドは、ジャーナルに書いて書き切ってから DB をコミットする。行には単調に増える連番を付け、起動時に DB と突き合わせる。削除と忘れるは、ジャーナルからも即時に取り除く。
- **根拠**: P1 (DB が全部壊れても会話を読める)、P3。
- **影響**: 03 §6。会話が 2 か所に残ることは、削除の即時の反映で扱う (OQ-09)。

### ADR-0007: 自動の退避

- **状態**: 確定 (ユーザー回答、2026-11-09)。推奨どおり (G1)。
- **決定**: 1 日 1 回まで、DB の一貫した写し (論理的な写し) を作る。日次 7 世代と週次 4 世代を残す。移行・作り直し・復元の前には必ず退避する (新しいものから 3 世代)。
- **根拠**: P1。
- **影響**: 03 §7。写し方は OQ-15。

### ADR-0008: 索引は作り直せる派生物

- **状態**: 確定 (ユーザー回答、2026-11-09)。推奨どおり (G1)。
- **決定**: 検索の索引は `evorag.redb` とカートリッジから作り直せるファイルとして別に置く。セグメントは一度書いたら変えず、`CURRENT` の入れ替えで切り替える。壊れたら捨てて作り直す。
- **根拠**: P1 (記録の正本を 1 つにする)、P5 (読み手を待たせない)。
- **影響**: 05 §2。

### ADR-0009: ベクトルの検索は int8 の全件走査から始める

- **状態**: 確定 (ユーザー回答、2026-11-09)。推奨どおり (G1)。
- **決定**: ベクトルは int8 に量子化して全件を走査する。件数が増えたら HNSW + RaBitQ に替える。入れ物の trait は同じにする。
- **根拠**: P8、P7。
- **影響**: 05 §2.2。速度と精度は S-05 で確かめる。

### ADR-0010: 外部の llama-server だけを使う

- **状態**: 確定 (ユーザー回答、2026-11-09)。推奨どおり (G1)。
- **決定**: 推論は外部の llama-server に任せ、chat・embed・rerank の役割ごとに接続先を設定で持つ。足りない能力に応じて縮退する。evorag は llama-server を起動・更新・管理しない。
- **根拠**: P7 (推論エンジンを内蔵しない)、P5。
- **影響**: 06。

### ADR-0011: 外へ通信するのは llama-server と手動の更新だけ

- **状態**: 確定 (ユーザー回答、2026-11-08: 更新の確認は手動だけ)
- **決定**: evorag が通信するのは、設定した llama-server と、利用者が `evorag update check` / `apply` を打ったときの更新の確認・取得だけ。起動時や定期の自動の確認、テレメトリはしない。確認の通信には版と OS の種類以外を含めない。
- **根拠**: P2。
- **影響**: 12 §7.5、NFR-501、09 §3.7。

### ADR-0012: 重みを学習しない

- **状態**: 確定 (ユーザー回答)。2026-11-11 に、学んでよいものの範囲の文言を改めた (ユーザー回答)。
- **決定**: LoRA・アダプタを含む、モデルの重みの学習はしない。学んでよいのは次の 3 つだけにする。どれも、ゲートで確かめ、版を持ち、巻き戻せる。
  1. プロンプトに足す文字列 (precept など)。
  2. 同梱した選択肢からの選択 (システムプロンプトの選べる既定、ADR-0017)。
  3. LLM を使わずに決定論で求める数値 (リランクのしきい値、OQ-38)。
- **根拠**: P4 (確かめられないものを採らない)、P7。
- **影響**: 13。

### ADR-0013: 自己学習の第 1 段で学ぶ対象

- **状態**: 提案中。2026-11-11 に、学ぶ対象の文言を改めた (ユーザー回答)。
- **決定**: v0.4 で学ぶ対象は次の 3 つにし、学習のループ (信号 → 事例 → 提案 → リプレイ → ゲート → 採用・巻き戻し) を一通り作る。第 2 段以降は対象と提案の作り方を足す。
  1. precept。
  2. 選べる既定の切り替え (precept と同じゲートと承認を通す、OQ-34)。
  3. リランクのしきい値の較正 (LLM を使わない決定論のゲート、OQ-38)。
- **根拠**: P4、P8。本体と食い違う precept は効かない (S-13 §7) ので、既定に関わる学習は切り替えとして出す。
- **影響**: 13。採用の条件は OQ-11、承認は OQ-10。

### ADR-0014: カートリッジは開発の初期に含めない

- **状態**: 確定 (ユーザー回答、2026-11-08)
- **決定**: カートリッジは開発の初期 (v0.1〜v0.4) に含めない。設計は 14 に残し、v0.5 で作る。それまでは、記録の種類・索引の種類・文脈の枠・`/sources` の名前だけを予約する。
- **根拠**: P8。
- **影響**: 14、08 §2.6。

### ADR-0015: C を含む依存は 0 にする

- **状態**: 確定 (ユーザー回答、2026-11-09)。TLS の暗号の実装の部分は条件付き確定 (S-06、OQ-05)。
- **決定**: C を含む依存は 0 にし、例外を作らない。`deps-policy.toml` で検査する。v0.1〜v0.2 は通信が llama-server (ループバックの HTTP) だけなので TLS を持たない。v0.3 の更新機能の TLS は、rustls と純 Rust の暗号の実装 (rustls-graviola) で組み、`evorag-update` に限る。
- **根拠**: P7。
- **影響**: 02 §4.3 の R5、09 §7、12 §7.5。

### ADR-0016: v1.0 までコーディングモードを入れない

- **状態**: 提案中。2026-11-11 に、モデルの切り替えの文言を改めた (ユーザー回答)。
- **決定**: コーディングモード・ProjectMap・道具の実行は v1.0 までに入れない。v1.0 までに入れるのは、保存の形式の名前の予約 (OQ-33) だけにする。起動中のモデルの切り替え (`/model`) は、その仕組みにしない (ADR-0018)。コーディングモードの応答のモデルは、チャットとは別の役割として setup で記録する (OQ-44)。
- **根拠**: P8 (チャットとメモリを先に固める)。
- **影響**: 00 §3 の N6、08 §2.8。構想と、v0.5 の凍結までに予約する名前は 15 (OQ-30〜33)。

### ADR-0017: 要求の先頭を変えない (システムプロンプトの 3 層)

- **状態**: 確定 (ユーザー回答、2026-11-11)
- **決定**: llama-server へ送る要求は、前のターンの要求と先頭が一致するように組み立てる (llama-server のプロンプトのキャッシュを毎ターン使うため)。
  - システムプロンプトは 3 層にする。**凍結の核** (安全の指示、引用の扱い方、道具の使い方。誰も変えない)、**選べる既定** (答える言語・長さ・書式。同梱した文から選ぶ)、**precept** (学習した短い指示。全部入れる)。
  - システムプロンプトに、今の日時と想起の引用を入れない。日時は発話の側に付ける。想起は今の発話の直前に添え、次のターンでは外す。
  - 細目は OQ-34 (3 層と選べる既定) と OQ-35 (並べ方)。
- **根拠**: P5。v0.1 の組み立ては毎ターン全体を処理し直し、応答が始まるまでに 14 秒かかる。先頭を変えなければ 1〜2 秒になる (S-13 §3)。P4 (本体と食い違う指示は効かないので、既定は切り替えとして持つ、S-13 §7)。
- **影響**: 05 §4、07 §6、13 §3。FR-402・FR-406・FR-407 の AC。

### ADR-0018: モデルは setup で記録し、切り替えは setup でだけ行う

- **状態**: 確定 (ユーザー回答、2026-11-11)
- **決定**: `evorag setup` (または最初の起動) のときに、役割ごとのモデル (「役割 → model_key」の表) をデータ根に記録する。起動と再接続のたびに照合し、記録と違うモデルでは動かさない。モデルの切り替えは `evorag setup` でだけ行い、起動中の切り替えと、記録を変えずに別のモデルを一時的に使う機能は持たない。切り替えたときは、そのモデルで学んだものを確かめ直す。細目は OQ-37。
- **根拠**: P4 (学習の成果はモデルごとに効き方が違うので、どのモデルの評価かを混ぜない、S-13 §7)。P2 (llama-server のふりをする別のプロセスを、起動時に止める、02 §8.2)。
- **影響**: 06 §2・§3・§5、07 §3・§4・§5、13 §8、03 §9。FR-108・FR-410・FR-608。

### ADR-0019: 想起はリランカーの値で決め、LLM の判断を応答の経路に入れない

- **状態**: 確定 (ユーザー回答、2026-11-11)
- **決定**:
  - 小さな埋め込みのモデルとリランカーの両方を使う構成を、勧める構成にする (どちらも任意のままで、無ければ縮退する)。
  - 想起は毎ターン行い、添えるかどうかはリランカーの生の値で決める。細目は OQ-36。
  - LLM の補助の呼び出し (言い換え、検索の計画、検索の道具をモデルに呼ばせる形) は、応答の経路に入れない。補助の呼び出しは、利用者が操作していない間に裏で動かす。
- **根拠**: P4 (関係の無い問いに誤って添える件数が、語彙とベクトルの規則で 31 件、リランカーで 1 件、S-13 §5)。P5 (補助の呼び出しは 1 回に 2.3〜6.5 秒、S-13 §4)。
- **影響**: 05 §3、06 §2・§3、04 §4。FR-404・FR-405・FR-502。

### ADR-0020: 学習の成果は役割とモデルごとに持ち、チャットとコーディングで分ける

- **状態**: 確定 (ユーザー回答、2026-11-11)
- **決定**:
  - 学習した結果 (precept・playbook、選べる既定の切り替え、リランクのしきい値、回帰台帳の事例) は、「役割 + model_key」ごとに持つ。チャットとコーディングでは共有しない。
  - 共有するのは、学習の仕組み (13 のループ)、評価と訂正の記録の置き場所と形、埋め込みとリランカーのモデル、利用者についての事実の置き場所だけにする。
  - 一方で学んだ指示を他方で使いたいときは、他方の候補として出し、そちらのゲートと承認を通ったものだけを有効にする (自動では渡さない)。
  - 細目は OQ-39。
- **根拠**: P4 (同じ指示でもモデルで効き方が違う。共有すると、片方のための変更がもう片方を悪くする、S-13 §7)。02 §8 (コーディングの指示は、コードと道具の結果という信頼しない出力から作る)。
- **影響**: 13 §3・§8、15 §4.5・§8、03 §3 (成果の鍵)。

### OQ-05: TLS と C を含む依存

- **背景**: rustls の既定の暗号の実装 (aws-lc-rs) は C のライブラリを含み、代わりの ring も C とアセンブリを含む。更新の確認と取得 (v0.3) には HTTPS が要る。
- **回答**: 条件付き確定 (S-06) (ユーザー回答、2026-11-09)。代替 (a) **純 Rust の暗号の実装** を採る。C を含む依存の例外は作らない。
- **採る実装**: rustls + **rustls-graviola** (暗号の実装は graviola)。`evorag-update` に限って使い、`evorag-llm` は TLS を持たない。
- **検討の結果** (2026-11-09 時点の各 crate の README による):
  - **graviola** は「C コンパイラ・アセンブラなどの道具が要らず、Rust のコンパイラだけで作れる」。楕円曲線などの一部の計算は、形式的に検証済みの s2n-bignum のコードを取り込んでいる。TLS のクライアントに要るもの (X25519・P-256・P-384 の鍵交換、RSA-PSS / PKCS#1・ECDSA・Ed25519 の署名の検証、AES-GCM・ChaCha20-Poly1305) がそろう。ライセンスは Apache-2.0 OR ISC OR MIT-0 で、許可リスト (`deny.toml`) の Apache-2.0 で通る。
  - **rustls-rustcrypto** (RustCrypto の実装) は、README に「本番で使わないこと」とあり、採らない。
- **問題になりうる点と対策**:

  | 点 | 内容 | 対策 |
  |---|---|---|
  | 成熟度 | graviola の README に「とても新しいので注意して使うこと」とあり、第三者の監査の記載が無い | 信頼の拠り所を TLS に置かない。配布物が本物かどうかは、minisign の署名つきのマニフェストで確かめる (12 §5.2・§7.5)。TLS が破られても、偽の配布物は署名の検証で拒否される。graviola の版を固定し、`cargo audit` と更新の通知を追う |
  | CPU の機能 | x86_64 は AES-NI・SSSE3・AVX・AVX2・ADX・BMI2・PCLMULQDQ (おおむね 2014 年以降の CPU)、aarch64 は aes・sha2・pmull・neon を必須とし、無い CPU での代替の実装を持たない | 通信の前に CPU の機能を実行時に確かめ、足りなければ通信せずに手作業の更新 (12 §7.1) を案内する。ローカル LLM を動かす PC では、ほぼ満たす見込み |
  | 対応する CPU の種類 | x86_64 と aarch64 だけ | 配布の対象 (12 §5.1) は Windows x86_64・Linux x86_64・macOS aarch64 なので足りる |
  | 対応する OS | README は OS を明記していない | S-06 で、Windows (MSVC)・Linux (musl)・macOS で作れて GitHub に繋がることを確かめる |
  | 証明書のルート | rustls はルートの一覧を持たない。同梱の一覧 (webpki-roots) はライセンスが許可リストの外の可能性がある | OS の証明書ストアを使う方法 (rustls-platform-verifier など) と同梱の一覧を S-06 で比べ、C を含まずライセンスが通る方を選ぶ |
  | HTTP のクライアント | reqwest は既定で aws-lc-rs を引く | 暗号の実装を自分で入れる構成 (reqwest の提供者なしの機能、または ureq) を S-06 で選ぶ |

- **条件 (S-06)**: 上の 3 つの対象で GitHub の Releases から取得でき、`cargo xtask check-deps` (C を含む依存 0) が通ること。
- **条件を満たさないとき**: ring を `evorag-update` に限った例外として認める案 (元の推奨) に戻し、PO に確認する。暗号の実装は rustls の提供者として差し替えられるので、戻すときの影響は `evorag-update` の中に閉じる。
- **採らなかった案**: (b) 取得を OS の道具 (Windows の `curl.exe` など) に任せる (外部のプロセスの実行が増える)。

### OQ-08: UI の言語とプロンプトの言語

- **回答**: 確定 (ユーザー回答、2026-11-09)。
  - **UI の言語**: 英語の UI (`en`) は **v0.3** で入れる (v0.6 から前倒し、ユーザー回答、2026-11-09)。v0.1〜v0.2 は `ja` だけで、コアは v0.1 から文言キーで返す。
  - **プロンプトの言語**: システムプロンプトと補助の呼び出しのプロンプトは 1 つの言語に固定する。言語は、初回の起動時 (`evorag setup` または最初の TUI の起動) に決めるか、設定 `prompt.language` があればその値にする。決めた言語はデータ根に記録し、**途中では変えられない** (07 §6.1)。応答は利用者の発話の言語に合わせるよう指示する。
- **根拠**: プロンプトを変えると、作りの指紋が変わって学習の取り直しが起き (13 §8)、ノートや事実の抽出の結果の言語もそろわなくなる。そのため、データ根ごとに 1 つの言語に固める。

### OQ-09: 忘れるの約束の範囲

- **回答**: 確定 (ユーザー回答、2026-11-09)。推奨のとおり。
- **推奨 (採用)**: 削除と忘れるは、DB・ジャーナル・索引・退避・quarantine から即時に取り除く (04 §7.2)。restore と repair はジャーナルの操作の行から当て直す。忘れるでは、出典の発話の該当の範囲を既定で伏せ字にする。約束しない範囲 (書き出したファイル・OS のバックアップ・SSD の物理的な消去・llama-server のログ) は確認の文言で伝える。
- **代替**: (a) 退避は保持の期限で消えるのに任せる (約束が数週間守られず、restore で蘇る)。(b) 出典の発話には触れず、事実だけを消す (次の抽出で蘇らないよう印を付ける)。
- **弱点**: 削除のたびに退避を写し直すので、DB が大きいと時間がかかる。

### OQ-10: precept の採用に利用者の承認を要するか

- **回答**: 確定 (ユーザー回答、2026-11-09)。推奨のとおり。
- **推奨 (採用)**: 要する (既定)。ゲートを通った提案を「採用待ち」にし、利用者が差分を見て承認したときだけ有効にする。設定 `learning.require_approval = false` で省ける。
- **背景**: 30 件ほどの LLM の採点ではゲートの統計の力が弱く、事例の本文を経由した指示の混入の経路もある。それなのに結果がシステムプロンプトに入る。

### OQ-31: 道具の実行の隔離と通信

- **区分**: PO (P2 と安全に関わる)。
- **期限**: C3 (15 §9) の着手前 (S-11 の結果を見て決める)。

### OQ-34: システムプロンプトの 3 層と選べる既定

- **回答**: 確定 (ユーザー回答、2026-11-11)。
- **推奨 (採用)**: 3 層の中身は ADR-0017。細目は次のとおり。
  1. 選べる既定は、言語・長さ・書式のそれぞれについて、同梱した文から 1 つを選ぶ。「指定なし」も選べる。文は、プロンプトの言語 (`ja`・`en`) ごとに同梱する。
  2. 「発話の言語に合わせる」の指示は、凍結の核には置かず、言語の既定の「指定なし」の文にする (核に置くと、「常に日本語で」を選んでも効かない、S-13 §7)。
  3. 利用者が自分で選んだ既定は、すぐ効かせる。学習は、利用者が選んだ既定を上書きしない。
  4. 既定に関わる学習の提案は、precept を足す形ではなく、既定の切り替えとして出す (ADR-0013)。本体を打ち消す言い方の precept は、決定論の検査で断る。
  5. 選んだ既定は、設定ファイルではなくデータ根に記録する (OQ-40)。作りの指紋には入れない (OQ-39)。
  6. 引用の区切りの印 (要求ごとに変わる) は、凍結の核には置かない。核には扱い方の指示だけを置き、印は引用の側に付ける。
- **代替**: システムプロンプトの本体を学習で書き換える (どの文が効いているかを確かめられず、P4 を満たせない)。本体を変えずに precept だけを足す (本体と食い違う指示が効かない)。
- **本文の改訂**: 07 §3・§6、05 §4.1・§4.3 (v0.2 の M2.0 で改めた)。学習に関わる部分は 13 §3 (v0.4 の M4.0)。

### OQ-35: 文脈の並べ方 (日時・想起・古い発言・先の処理)

- **回答**: 確定 (ユーザー回答、2026-11-11)。
- **推奨 (採用)**:
  1. 今の日時は、発話の側に付ける。ターンに記録した時刻から作るので、後のターンでも同じ文字列になる。
  2. 想起した往復は、信頼しない引用の枠に入れて今の発話の直前に添え、次のターンでは外す。
  3. 出典の番号は、セッションの中の通し番号にする (履歴の応答に残る番号と、新しい引用の番号がぶつからないように)。
  4. 古い発言は、予算を超えたら、予算の 6 割になるまでまとめて省く (1 往復ずつ省かない)。
  5. 応答の直後に、次のターンの分を先に処理しておく (生成を 1 トークンに限った要求)。
  6. 利用者についての事実の表 (v0.3) は先頭に固定し、事実が変わったとき (訂正・忘れる・private) だけ、次のターンで作り直す。
  7. カートリッジ (v0.5) の扱い方の指示は凍結の核に置く。有効なカートリッジの一覧と「見当たらない」の通知は末尾に置く。
- **試験**: 応答が始まるまでの時間は CI で測れないので、「連続する 2 つの要求で、先頭のバイト列が一致すること」を試験する。
- **根拠**: S-13 §3。
- **本文の改訂**: 05 §4 (v0.2 の M2.0)。

### OQ-36: 想起の規則 (候補・リランク・添え方・縮退)

- **回答**: 確定 (ユーザー回答、2026-11-11)。OQ-18 の添える規則を置き換える。
- **推奨 (採用)**:
  1. 想起は毎ターン行う。LLM の判断は入れない (ADR-0019)。
  2. 候補は、語彙とベクトルの順位を RRF で 1 つにし、上位 6 ターンを取って、往復 (利用者の発話と応答の組) にまとめる。
  3. 往復の本文をリランクし、生の値がしきい値以上なら、最上位の 1 件だけを添える。
  4. しきい値の少し下の帯は、文脈には入れず、画面に「関係しそうな記録」として出す。利用者は、そこから添えることも、「無関係」の印を付けることもできる。それより下は何もしない。
  5. 縮退は次のとおりにし、縮退したことを判定点に記録する (2026-11-12 の注: 判定点の列挙には値を足さず、応答のターンの観測値 `obs` に理由を置く。03 §4.2 の規則 11、05 §3.5)。
     - 埋め込みが無い: 語彙の上位 6 ターンを往復にまとめてリランクする。
     - リランカーが無い・締切に間に合わない: 語彙だけの v0.1 の規則 (05 §3.5) に戻す。
     - リランカーの較正の値が無い: 添えずに、画面の候補にだけ出す (OQ-38)。
  6. リランクの件数と締切は、モデルの性質の点検 (OQ-37 の 7) で測った速さから決める。
  7. 事実とノートは裏で作り、検索の鍵として索引に足す。添えるのは原文 (往復) にする。private の事実から鍵を作らない。鍵の数と長さに上限を置く。
  8. 言い換え (FR-405) は応答の経路に入れない。追い質問のときに直前の発話を足す補い (LLM を使わない) は残す。
- **代替**: 上位 30 ターンをリランクする (遅く、質も下がる)。検索の道具をモデルに呼ばせる (暗黙の問いで呼ばない)。

### OQ-37: モデルの記録・照合・切り替えの手順

- **回答**: 確定 (ユーザー回答、2026-11-11)。ADR-0018 の細目。
- **推奨 (採用)**:
  1. **記録**: 「役割 → model_key」の表をデータ根に記録する。役割は、応答 (chat)・埋め込み (embed)・リランカー (rerank) で、足すだけで広げられる形にする (提案と採点のモデル、コーディングの応答のモデル)。違いの中身を見せられるように、model_key の元の値 (ファイル名と、サーバが返す値) も残す。v0.1 のデータ根には記録が無いので、v0.2 の最初の起動のときに、繋がっているモデルを記録する (プロンプトの言語と同じ規則、07 §6.1)。
  2. **照合**: 起動と再接続のたびに照合する。
     - 応答のモデルが記録と違う: 画面を開かずに、案内を出して終わる (記録したモデルで起動し直すか、`evorag setup` で切り替える)。
     - 埋め込み・リランカーが記録と違う: 無いものとして動かし (OQ-36 の縮退)、状態の行で知らせる。
     - 起動中に入れ替わった: 再接続のときに気づき、送信を止める。
  3. **切り替え**: `evorag setup` は、違いの中身、やり直しになるもの、時間の目安を見せ、明示の確認があったときだけ記録を書き換える。確認が無ければ設定だけを書く。記録を書き換える setup は、画面を閉じてから実行する (03 §9)。
  4. **同じモデルとして扱う**: model_key は、ファイル名の変更や llama-server の更新でも変わる (06 §5)。setup で「同じモデルとして扱う」を選ぶと、記録だけを直し、学んだものを確かめ直さない。量子化の違いは、別のモデルとして扱う。
  5. **切り替えたときの動き**: 元のデータ (評価・訂正・回帰台帳の事例) は残す。記録の更新と、やり直しの手順の一覧 (job) は、同じコミットで書く。途中で落ちたら、起動時に続きを行う。
     - 応答: precept と学習による既定の切り替えを候補に戻し、新しいモデルでゲートを通ったものだけを有効にする。確かめ直しはまとめて 1 回で行い、落ちたら半分に分けて確かめる。確かめ終わるまでは有効にしない。
     - 埋め込み: ベクトルの索引と事例の群を作り直す。その間は語彙の検索とリランクで答える。前のモデルの索引は 1 世代だけ残す。
     - リランカー: しきい値を既定に戻し、較正し直す (OQ-38)。
     - 前のモデルに戻した: 成果は model_key ごとに持つので、確かめ済みのモデルに戻したら、その成果をそのまま使う。
  6. **`/model`**: 切り替えをやめ、今のモデルの表示だけにする (FR-108 を改める)。設定 `llm.chat.models` は、読んで無視し、通知を出す (キーを消すと、このキーを書いた設定で起動を拒むため)。
  7. **モデルの性質の点検**: 速さ、思考を切れるか、型縛りの出力が空にならないかを、小さな課題で確かめて保存する。行うのは、setup のときと、model_key か llama-server の版が変わったときだけ (起動のたびには行わない、NFR-101)。通らない機能は止めて、画面に理由を示す。
  8. **新しいモデルを試す**: 別のデータ根 (`--data-root`) を使う、と案内する。
  9. **書き出しと取り込み**: 役割の表としきい値を、書き出しに含める。
- **代替**: 起動時に「切り替える / 今回だけ使う」を選ばせる (不採用。偽のサーバを記録する経路になり、どのモデルの評価かが混ざる)。
- **本文の改訂**: 06 §2・§3・§5、07 §3〜§5、03 §9、02 §3・§8.2 (v0.2 の M2.0)。学習の確かめ直しは 13 §8 (v0.4 の M4.0 と v0.6 の M6.0)。

### OQ-39: 学習の時機・作りの指紋・成果の鍵

- **回答**: 確定 (ユーザー回答、2026-11-11)。ADR-0020 の細目。
- **推奨 (採用)**:
  1. **時機**: 評価と訂正はすぐ記録する。提案・リプレイ・ゲートは、利用者が操作していない間 (60 秒) に少しずつ進める。
  2. 学習が動くのは、記録したモデル (ADR-0018) で動いている間だけ。裏の学習は、今読み込まれているモデルの分だけ進め、学習のためにモデルを入れ替えない。
  3. 埋め込みとリランカーは、学習の裏側だけで使う (似た事例を群にまとめる、ゲートに流す事例を選ぶ、提案の重複を見つける)。採点には使わない。無ければ使わずに進める。
  4. **作りの指紋** を「生成」と「検索」に分ける。生成の指紋には、凍結の核のハッシュ、生成の設定 (温度、思考の有無、要求に足す JSON)、チャットテンプレートのハッシュを入れる。選んだ既定は指紋に入れず、事例の入力として記録する (既定を変えるたびに取り直しが走らないように)。

  6. **成果の鍵** は「役割 + model_key」。提案のきっかけ (失敗の事例 3 件) は、役割ごとに数える。
  7. 学習が止まっているときは、理由を状態の行・`evorag doctor`・`/precepts` に出す (型縛りの出力が空、リランクがいつも締切切れ、モデルが記録と違う)。確かめ直しの進み具合も `/precepts` に出す。

### OQ-40: 古い版が新しい記録と設定を読めること

## 人間 (PO) が決める事項

着手のゲート (08 §5) の順に並べる。推奨は各 OQ の節にある。

PO 区分で残っている判断は、外部寄稿の受付の時期 ([OQ-28](#oq-28-公開の時期と外部寄稿の受付)、PO が別途指示する。指示があるまで受け付けない) と、v1.0 の前に決める暗号化消去 ([OQ-27](#oq-27-暗号化消去)) だけである。

**回答済み (2026-11-09)**:
- 推奨どおり: OQ-03 (版の割り当て)、OQ-04 (更新機能の時期)、OQ-06 (v0.1 の語彙の想起)、OQ-07 (OS の順序)、OQ-09 (忘れるの約束の範囲)、OQ-10 (precept の採用の承認)。
- 回答に合わせて本文を直したもの: OQ-08 (英語の UI は v0.3、プロンプトの言語は初回に固定)、OQ-24 (データの互換は v0.5 から)、OQ-28 (最初から public)、OQ-05 (純 Rust の暗号の実装。S-06 を条件とする)。

## 0. 運用ルール

### 0.1 状態

| 状態 | 意味 |
|---|---|
| **提案中** | 推奨案として記載。変わりうる。実装着手の根拠にしない |
| **確定** | PO が決めた (指示または確認)。変えるには新しい ADR を起こす |
| **確定 (ユーザー回答)** | PO が推奨案 (または示した選択肢) に回答して確定したもの。扱いは「確定」と同じ |
| **一部提案中** | 一部が確定し、細目や残りが提案中のもの。確定した部分と提案中の部分を書き分ける |
| **条件付き確定 (S-nn)** | PO が確定し、スパイク S-nn の結果が合否の基準を満たすことを条件とするもの。実装着手の根拠にしてよい。満たさなかったときは、その節の「条件を満たさないとき」の代替を採り、本書に記録する |

### 0.2 書式

- 各 ADR は「状態 / 決定 / 根拠 (どの設計原則に基づくか) / 影響」を持つ。最終的な決定 (提案中のものは推奨案) だけを書き、検討の経緯は書かない。
- 各 OQ は「件名 / 推奨 / 代替 / 区分 / 期限」を持つ。

### 0.3 確定手続き

1. PO が本書をレビューし、ADR ごとに「確定 / 修正 / 不採用」、OQ ごとに回答する (まず上の「PO が決める事項」)。
2. 回答に基づき本書と関連の文書を直す。
3. 着手のゲートに要る ADR・OQ は、PO の 1 回の承認でまとめて推奨どおり確定してよい (状態は「確定 (ユーザー回答)」)。

### 0.4 OQ の区分

| 区分 | 意味 | 扱い |
|---|---|---|
| **PO** | 製品の方針・安全・互換・範囲に関わる | PO の回答で確定する。回答が無ければ着手のゲートで止まる |
| **裁量** | 推奨案が明確で、変えても局所的 | 推奨案で本文を書いた。期限までに PO の異議が無ければ推奨で確定する |
| **スパイク** | 技術的な事実で決まる | 08 §3 のスパイクの結果で確定し、本書に記録する |

### ADR-0001: 仕様書駆動での開発

- **状態**: 確定 (ユーザー回答)
- **決定**: 仕様書 (docs/) の **その版の範囲** を確定してから、その範囲の実装 (Cargo.toml を含む) を作る。docs/ を正本にし、実装中に仕様と食い違う判断が要るときは、仕様書を先に直す。対象外: 技術検証のスパイク (`spikes/`、使い捨て)、開発運用の文書・設定 (`CLAUDE.md`・`.claude/`・11)、開発用の道具 (`xtask`)。
- **根拠**: P6、P8。
- **影響**: 着手の条件は 08 §5。運用は 11。

### ADR-0002: リリース最優先の段階リリース

- **状態**: 確定 (ユーザー回答)。版の割り当ての中身は OQ-03 で提案中。
- **決定**: v0.1 で「ある程度は使える」最小核を出し、その後の版で少しずつ機能を足す。版は日付ではなくゲートで区切る。後の版で足すものは、v0.1 で決めた形式と公開面を壊さない (足すだけの) 形で入れる。機能リリースは `0.y.0`、bugfix はパッチ版。
- **根拠**: P6、P8。
- **影響**: 08。ブランチと版の運用は 11 §9.1。

### ADR-0003: TUI とコアを 1 つのプロセスで動かす

- **状態**: 提案中
- **決定**: 初期は TUI とコアを 1 つのプロセスで動かし、TUI を閉じるとコアも止まる。コアと画面の間はコアの API (命令・イベント・照会) で切り、後で常駐やほかの画面に分けるときは、この API をプロセスの外へ出す。
- **根拠**: P8 (常駐の仕組みを先に作り込まない)、P1 (プロセスが 1 つならデータ根の書き手も 1 つ)。
- **影響**: 02 §1・§3。常駐の採否は OQ-25。

### ADR-0004: 記録の正本は redb の汎用の表

- **状態**: 一部提案中。**確定 (ユーザー回答、2026-11-08)**: DB は後方互換を重視した汎用の構成にする (少数の汎用の表に種類を付けた記録を入れ、機能を足すときは種類を増やす)。**提案中**: DB の実装に redb を使う。
- **決定**: 埋め込み型の DB の redb を 1 ファイルで使い、`meta`・`records`・`links`・`lookup`・`blobs` の 5 表を持つ。DB の操作は `evorag-store` の trait に閉じ込める。SQLite は外部の道具で中を見られる利点があるが、C を含む依存になるので採らない。
- **根拠**: P6、P7、P1 (ACID)。
- **影響**: 03。redb のメジャー版の上げ方は OQ-16。

### ADR-0005: 記録の本体は項目名つきの CBOR

- **状態**: 提案中
- **決定**: 封筒の本体は項目名つきの CBOR (ciborium) にする。並び順で意味が決まる符号は使わない。書き出しとジャーナルは JSON Lines にする。
- **根拠**: P6 (項目を足しても古いデータが読める)、P5 (JSON より小さく速い)。
- **影響**: 03 §3.2・§6・§11。

### ADR-0006: 会話のジャーナルを先に書く

- **状態**: 提案中
- **決定**: 会話のターンと明示の操作を、DB とは別の追記専用のジャーナルにも書く。書き手スレッドは、ジャーナルに書いて書き切ってから DB をコミットする。行には単調に増える連番を付け、起動時に DB と突き合わせる。削除と忘れるは、ジャーナルからも即時に取り除く。
- **根拠**: P1 (DB が全部壊れても会話を読める)、P3。
- **影響**: 03 §6。会話が 2 か所に残ることは、削除の即時の反映で扱う (OQ-09)。

### ADR-0007: 自動の退避

- **状態**: 提案中
- **決定**: 1 日 1 回まで、DB の一貫した写し (論理的な写し) を作る。日次 7 世代と週次 4 世代を残す。移行・作り直し・復元の前には必ず退避する (新しいものから 3 世代)。
- **根拠**: P1。
- **影響**: 03 §7。写し方は OQ-15。

### ADR-0008: 索引は作り直せる派生物

- **状態**: 提案中
- **決定**: 検索の索引は `evorag.redb` とカートリッジから作り直せるファイルとして別に置く。セグメントは一度書いたら変えず、`CURRENT` の入れ替えで切り替える。壊れたら捨てて作り直す。
- **根拠**: P1 (記録の正本を 1 つにする)、P5 (読み手を待たせない)。
- **影響**: 05 §2。

### ADR-0009: ベクトルの検索は int8 の全件走査から始める

- **状態**: 提案中
- **決定**: ベクトルは int8 に量子化して全件を走査する。件数が増えたら HNSW + RaBitQ に替える。入れ物の trait は同じにする。
- **根拠**: P8、P7。
- **影響**: 05 §2.2。速度と精度は S-05 で確かめる。

### ADR-0010: 外部の llama-server だけを使う

- **状態**: 提案中
- **決定**: 推論は外部の llama-server に任せ、chat・embed・rerank の役割ごとに接続先を設定で持つ。足りない能力に応じて縮退する。evorag は llama-server を起動・更新・管理しない。
- **根拠**: P7 (推論エンジンを内蔵しない)、P5。
- **影響**: 06。

### ADR-0011: 外へ通信するのは llama-server と手動の更新だけ

- **状態**: 確定 (ユーザー回答、2026-11-08: 更新の確認は手動だけ)
- **決定**: evorag が通信するのは、設定した llama-server と、利用者が `evorag update check` / `apply` を打ったときの更新の確認・取得だけ。起動時や定期の自動の確認、テレメトリはしない。確認の通信には版と OS の種類以外を含めない。
- **根拠**: P2。
- **影響**: 12 §7.5、NFR-501、09 §3.7。

### ADR-0012: 重みを学習しない

- **状態**: 確定 (ユーザー回答)
- **決定**: LoRA・アダプタを含む、モデルの重みの学習はしない。学ぶのはプロンプトに足す文字列 (precept など) だけにする。
- **根拠**: P4 (確かめられないものを採らない)、P7。
- **影響**: 13。

### ADR-0013: 自己学習の第 1 段は precept のみ

- **状態**: 提案中
- **決定**: v0.4 で学ぶ対象は precept だけにし、学習のループ (信号 → 事例 → 提案 → リプレイ → ゲート → 採用・巻き戻し) を一通り作る。第 2 段以降は対象と提案の作り方を足す。
- **根拠**: P4、P8。
- **影響**: 13。採用の条件は OQ-11、承認は OQ-10。

### ADR-0014: カートリッジは開発の初期に含めない

- **状態**: 確定 (ユーザー回答、2026-11-08)
- **決定**: カートリッジは開発の初期 (v0.1〜v0.4) に含めない。設計は 14 に残し、v0.5 で作る。それまでは、記録の種類・索引の種類・文脈の枠・`/sources` の名前だけを予約する。
- **根拠**: P8。
- **影響**: 14、08 §2.6。

### ADR-0015: C を含む依存は 0 にする

- **状態**: 確定 (ユーザー回答、2026-11-09)。TLS の暗号の実装の部分は条件付き確定 (S-06、OQ-05)。
- **決定**: C を含む依存は 0 にし、例外を作らない。`deps-policy.toml` で検査する。v0.1〜v0.2 は通信が llama-server (ループバックの HTTP) だけなので TLS を持たない。v0.3 の更新機能の TLS は、rustls と純 Rust の暗号の実装 (rustls-graviola) で組み、`evorag-update` に限る。
- **根拠**: P7。
- **影響**: 02 §4.3 の R5、09 §7、12 §7.5。

### ADR-0016: v1.0 までコーディングモードを入れない

- **状態**: 提案中
- **決定**: コーディングモード・ProjectMap・道具の実行は v1.0 までに入れない。モデルの切り替えの仕組み (`/model`) だけを入れる。
- **根拠**: P8 (チャットとメモリを先に固める)。
- **影響**: 00 §3 の N6、08 §2.8。

### OQ-01: ブランチと公開の運用

- **回答**: 確定 (ユーザー回答)。evoeditor と同じ運用にする。長命ブランチは `main` (リリース専用) と `develop` (開発の本線) の 2 本。作業ブランチは `develop` から作り、PR (squash) で入れる。リポジトリは最初から public で開発し、docs/ も公開する (OQ-28)。
- **影響**: 11 §9.1、12 §4。

### OQ-02: 寄稿ポリシー

- **回答**: 確定 (ユーザー回答)。DCO。ライセンスは Apache-2.0。
- **影響**: 11 §9.4、12 §3。

### OQ-03: 版の割り当て

- **回答**: 確定 (ユーザー回答、2026-11-09)。推奨のとおり。英語の UI だけは OQ-08 の回答で v0.6 から前倒しする。
- **推奨 (採用)**: 08 §1 の割り当て。v0.1 会話・保存・保護・語彙の想起 → v0.2 sleep-time・ベクトル検索・ノート・Linux → v0.3 事実・訂正・忘れる・更新機能 → v0.4 自己学習の第 1 段 → v0.5 カートリッジ → v0.6 仕上げ (macOS、学習の引き継ぎ、import)。英語の UI は当初 v0.6 の案だったが、OQ-08 の回答で v0.3 に前倒しした。
- **代替**: (a) メモリ (事実まで) を v0.2 にまとめる (v0.2 が大きくなりすぎる)。(b) カートリッジを自己学習より先にする (v0.4 と v0.5 は独立なので入れ替えられる)。
- **弱点**: 一番の売り (事実を覚える) が届くのが 3 版目になる。v0.1 の語彙の想起でその間をつなぐ。

### OQ-04: 更新機能の時期

- **回答**: 確定 (ユーザー回答、2026-11-09)。推奨のとおり。
- **推奨 (採用)**: v0.1 には、データの移行の枠組み・移行の前の退避・新しい版のデータを読むだけで開く規則・署名つきの配布物を入れ、本体の更新は手作業にする (12 §7.1)。`evorag update check|apply|rollback` は v0.3 で入れ、以後の更新はすべて `update` を通す。

### OQ-05: TLS と C を含む依存

- **背景**: rustls の既定の暗号の実装 (aws-lc-rs) は C のライブラリを含み、代わりの ring も C とアセンブリを含む。更新の確認と取得 (v0.3) には HTTPS が要る。
- **回答**: 条件付き確定 (S-06) (ユーザー回答、2026-11-09)。代替 (a) **純 Rust の暗号の実装** を採る。C を含む依存の例外は作らない。
- **採る実装**: rustls + **rustls-graviola** (暗号の実装は graviola)。`evorag-update` に限って使い、`evorag-llm` は TLS を持たない。
- **検討の結果** (2026-11-09 時点の各 crate の README による):
  - **graviola** は「C コンパイラ・アセンブラなどの道具が要らず、Rust のコンパイラだけで作れる」。楕円曲線などの一部の計算は、形式的に検証済みの s2n-bignum のコードを取り込んでいる。TLS のクライアントに要るもの (X25519・P-256・P-384 の鍵交換、RSA-PSS / PKCS#1・ECDSA・Ed25519 の署名の検証、AES-GCM・ChaCha20-Poly1305) がそろう。ライセンスは Apache-2.0 OR ISC OR MIT-0 で、許可リスト (`deny.toml`) の Apache-2.0 で通る。
  - **rustls-rustcrypto** (RustCrypto の実装) は、README に「本番で使わないこと」とあり、採らない。
- **問題になりうる点と対策**:

  | 点 | 内容 | 対策 |
  |---|---|---|
  | 成熟度 | graviola の README に「とても新しいので注意して使うこと」とあり、第三者の監査の記載が無い | 信頼の拠り所を TLS に置かない。配布物が本物かどうかは、minisign の署名つきのマニフェストで確かめる (12 §5.2・§7.5)。TLS が破られても、偽の配布物は署名の検証で拒否される。graviola の版を固定し、`cargo audit` と更新の通知を追う |
  | CPU の機能 | x86_64 は AES-NI・SSSE3・AVX・AVX2・ADX・BMI2・PCLMULQDQ (おおむね 2014 年以降の CPU)、aarch64 は aes・sha2・pmull・neon を必須とし、無い CPU での代替の実装を持たない | 通信の前に CPU の機能を実行時に確かめ、足りなければ通信せずに手作業の更新 (12 §7.1) を案内する。ローカル LLM を動かす PC では、ほぼ満たす見込み |
  | 対応する CPU の種類 | x86_64 と aarch64 だけ | 配布の対象 (12 §5.1) は Windows x86_64・Linux x86_64・macOS aarch64 なので足りる |
  | 対応する OS | README は OS を明記していない | S-06 で、Windows (MSVC)・Linux (musl)・macOS で作れて GitHub に繋がることを確かめる |
  | 証明書のルート | rustls はルートの一覧を持たない。同梱の一覧 (webpki-roots) はライセンスが許可リストの外の可能性がある | OS の証明書ストアを使う方法 (rustls-platform-verifier など) と同梱の一覧を S-06 で比べ、C を含まずライセンスが通る方を選ぶ |
  | HTTP のクライアント | reqwest は既定で aws-lc-rs を引く | 暗号の実装を自分で入れる構成 (reqwest の提供者なしの機能、または ureq) を S-06 で選ぶ |

- **条件 (S-06)**: 上の 3 つの対象で GitHub の Releases から取得でき、`cargo xtask check-deps` (C を含む依存 0) が通ること。
- **条件を満たさないとき**: ring を `evorag-update` に限った例外として認める案 (元の推奨) に戻し、PO に確認する。暗号の実装は rustls の提供者として差し替えられるので、戻すときの影響は `evorag-update` の中に閉じる。
- **採らなかった案**: (b) 取得を OS の道具 (Windows の `curl.exe` など) に任せる (外部のプロセスの実行が増える)。

### OQ-08: UI の言語とプロンプトの言語

- **回答**: 確定 (ユーザー回答、2026-11-09)。
  - **UI の言語**: 英語の UI (`en`) は **v0.3** で入れる (v0.6 から前倒し、ユーザー回答、2026-11-09)。v0.1〜v0.2 は `ja` だけで、コアは v0.1 から文言キーで返す。

- **根拠**: プロンプトを変えると、作りの指紋が変わって学習の取り直しが起き (13 §8)、ノートや事実の抽出の結果の言語もそろわなくなる。そのため、データ根ごとに 1 つの言語に固める。

### OQ-09: 忘れるの約束の範囲

- **回答**: 確定 (ユーザー回答、2026-11-09)。推奨のとおり。
- **推奨 (採用)**: 削除と忘れるは、DB・ジャーナル・索引・退避・quarantine から即時に取り除く (04 §7.2)。restore と repair はジャーナルの操作の行から当て直す。忘れるでは、出典の発話の該当の範囲を既定で伏せ字にする。約束しない範囲 (書き出したファイル・OS のバックアップ・SSD の物理的な消去・llama-server のログ) は確認の文言で伝える。
- **代替**: (a) 退避は保持の期限で消えるのに任せる (約束が数週間守られず、restore で蘇る)。(b) 出典の発話には触れず、事実だけを消す (次の抽出で蘇らないよう印を付ける)。
- **弱点**: 削除のたびに退避を写し直すので、DB が大きいと時間がかかる。

## 1. 方針

- **重みは学習しない** (LoRA を含む、[ADR-0012](10-decisions.md#adr-0012-重みを学習しない))。学ぶのは、システムプロンプトに足す短い指示 (precept) だけ。
- 学習のループ (信号 → 事例 → 提案 → リプレイ → ゲート → 採用・巻き戻し) は第 1 段で一通り作る。第 2 段以降は「学ぶ対象」と「提案の作り方」を足す (§9)。
- どの段も同じゲートと巻き戻しを通す。対象を足すときは `Proposal<A: Artifact>` の `A` を増やすだけにする。
- ラベルに使うのは **強い信号だけ**。モデルの自己判定は信号にしない。
- 安全に関わる指示は precept に入れず、システムプロンプトに固定する (自動の編集の対象外)。

## 2. 信号

| 区分 | 信号 | 使い方 | 記録の開始 |
|---|---|---|---|
| 強い | 検証済みの訂正 (04 §6) | 失敗の事例の根拠 | v0.3 |
| 強い | 利用者の評価 `/good`、`/bad [理由]` | 守るべき事例 / 失敗の事例の根拠 | v0.1 |
| 弱い | 再生成 `/retry`、同じ質問の繰り返し | 候補を拾うだけで、正解の根拠にはしない | v0.1 |

## 3. precept

### 3.1 形 (確かめられる約束)

| 項目 | 内容 |
|---|---|
| `id` | 項目の ID |
| `condition` | いつ効くか (例: 「利用者が手順を尋ねたとき」) |
| `instruction` | 指示 (例: 「番号つきの手順で答える」) |
| `check` | 守れているかの確かめ方。決定論で確かめられるもの (正規表現・長さ・含む語) を優先し、無ければ LLM の採点の観点を書く |
| `origin` | 提案の ID と、根拠の事例の ID |

- 上限: 最大 20 項目、合計 500 トークンまで。
- **決定論の検査** (採用の前に必ず通す): URL を含まない、他の指示 (システムプロンプト・安全の指示) の打ち消しや言及を含まない、`condition` と `instruction` が空でない、1 項目 100 トークンまで。

### 3.2 置き方

- 有効な precept は、文脈の順 2 (05 §4.1) に入る。
- precept と採点の結果は model_key ごとに持つ。

## 4. 回帰台帳

- 事例は **入力と望ましい性質だけ** を持ち、特定のモデルの出力を正解として持たない。モデルを替えても台帳をそのまま使える。
  - **入力**: 発話、直前の会話 (ターンの ID)、そのとき添えたメモリの ID。
  - **望ましい性質**: 訂正の後の値、守るべき条件、利用者が書いた理由。
- 悪かった応答は参考として残すが、採点の基準には使わない。
- 良い評価の応答は「守るべき事例」として積む。元のターンの ID でたどれるようにする。
- **安全の回帰事例**: 拒むべき依頼・指示の混入・個人の情報の扱いなどの固定の事例を、本体に同梱する (`evorag-learn/safety-cases/`)。利用者のデータとは別に持ち、すべてのゲートで必ず流す。
- セッションの削除と忘れるの操作は、台帳の事例にも波及する (04 §7)。

## 5. 提案

- 失敗の事例が 3 件以上たまったら、sleep-time に、型縛りの LLM の呼び出しで、precept の追加・修正・削除を **1 件だけ** 提案させる。
- 自由に振り返らせず、決まった書式と確認項目 (何の失敗か、どういう条件で起きるか、何が観察できれば直ったと言えるか、既存の項目と重ならないか) を与える。
- 失敗の事例と守るべき事例を並べて渡し、差から考えさせる。
- **編集の上限**: 1 件の提案で変えてよいのは 1 項目、100 トークンまで。超えた提案は捨てる。
- 提案を作るモデルは設定 `learning.proposer_model` で選べる。既定は chat と同じモデル (確定、[OQ-22](10-decisions.md#oq-22-提案と採点に使うモデルの既定))。
- 事例の本文 (利用者の発話・`/bad` の理由) に埋め込まれた指示が precept に昇格しないよう、§3.1 の決定論の検査と、§7 の承認を通す。

## 6. ゲート

### 6.1 事例の分け方

- 提案の材料に使った事例 (**材料の組**) と、使っていない事例 (**保留の組**) を分ける。採用の判定は保留の組で行う (材料の組への過剰な適合を避けるため)。

### 6.2 1 段目 (安い検査)

- 提案のきっかけの失敗の事例と、関係しそうな守るべき事例を、合わせて 2〜4 件だけ流す。失敗が直らないか、守るべき事例が悪化したら、ここで却下する。

### 6.3 2 段目 (リプレイ)

- 1 段目を通った提案だけ、保留の組から最大 30 件 (失敗の事例と守るべき事例を半分ずつ) と、同梱の安全の回帰事例のすべてを、今の precept と提案の後の precept の両方で流し直す。
- **生成の設定を固定する**: temperature 0、固定の seed、プロンプトのキャッシュを使わない、同じスロット。
- 各事例は「メモリを添えない」場合も 1 回流し、メモリを添えた方が悪い事例を記録する (検索のしきい値を見直す材料。第 4 段で使う)。この試行は採用の判定に使わない。
- 途中で止めても再開できる (事例ごとの結果を `job` に記録する)。

### 6.4 採点と採用の条件

- **決定論の採点**: precept の `check` や値の一致など、機械的に確かめられるものは決定論で採点する。
- **LLM の採点**: それ以外は、新旧の応答を並べて型縛りの LLM の呼び出しに比べさせ、並べる順を入れ替えて 2 回採点する。2 回の結果が食い違えば「引き分け」にする。
- **採用の条件** (確定、[OQ-11](10-decisions.md#oq-11-ゲートの採用の条件)):
  1. 安全の回帰事例と、決定論で採点した事例で、悪化が 0 件。
  2. LLM で採点した事例で、悪化が 0 件、かつ (改善 − 悪化) が 2 以上。
  3. 引き分けばかりの提案は却下する。
- **揺れの計測**: 同じ precept どうしのリプレイ (A/A) を定期的に流し、上の条件を偶然に満たす率 (誤採用の率) を測る。5% を超えたら、条件を厳しくする (件数を増やす・改善の差を広げる) まで採用を止める (v0.4 の合格条件 (6)、技術検証 S-08)。

## 7. 採用・版・巻き戻し

- **承認**: ゲートを通った提案は「採用待ち」になり、利用者が `/precepts` で差分 (足す・直す・消す項目と、根拠の事例の要約) を見て承認したときだけ有効にする (確定 (ユーザー回答)、[OQ-10](10-decisions.md#oq-10-precept-の採用に利用者の承認を要するか))。設定 `learning.require_approval = false` で承認を省ける (台帳が 100 件を超え、誤採用の率を測ってから使うことを勧める)。
- **型**: 提案は `Proposal<Precept>` として扱い、台帳に合格の記録が無いものは有効な版にできない。
- **版**: precept の一覧は版を積んで保存し (`precept_set`)、「有効な版」を指すだけにする。巻き戻しは指す版を戻すだけ。
- 採用した内容はイベントで通知し、`/precepts` で確かめて戻せる。
- **書き直さない**: precept の統合や整理も、通常の提案と同じゲートを通す。定期的に全体をまとめ直す処理は作らない (まとめ直すたびに細部が失われ、誤った一般化が起きやすい)。
- **止められる**: 設定 `learning.enabled = false` で学習を止められる。メモリの sleep-time は動き続ける。

## 8. 学習の引き継ぎ

引き継ぐべき一番の資産は回帰台帳である。precept は台帳があれば作り直せる。

| 変わるもの | 検出の方法 | 引き継ぎの動き | 版 |
|---|---|---|---|
| evorag 本体の作り | **作りの指紋**: evorag の版、システムプロンプトのハッシュ、検索の設定のハッシュ | 今の precept は有効のまま、新しい作りでリプレイし直す。悪化した項目は無効にする提案を自動で出す。終わるまで新しい提案は採用しない | v0.4 |
| llama-server | `/props` の `build_info` | 本体の作りが変わったときと同じように取り直す | v0.4 |
| モデル | model_key | 回帰台帳はそのまま使う。前のモデルの precept を 1 件の提案としてゲートにかけ、合格すれば新しいモデルの最初の版にする。前のモデルに戻したときは、そのモデルの版をそのまま使う | v0.6 |
| 自己学習の段 | 新しい段の追加 | 新しい種類の記録を足すだけで、既存の precept と台帳はそのまま使う | — |
| 保存の形式 | 封筒の `v` | 古い版の事例や precept も読める (golden fixture) | v0.4 |

- `evorag export` には、回帰台帳の事例、precept のすべての版、提案と判定の記録も含める (03 §11)。別の PC や別のデータ根へ移しても、学習の経過ごと引き継げる。

## 9. 自己学習の段階

| 段 | 学ぶ対象 | 提案の作り方 | 時期 |
|---|---|---|---|
| 第 1 段 | precept | 失敗の事例から追加・修正・削除を 1 件ずつ提案 | v0.4 |
| 第 2 段 | モード別の手順書、部品のプロンプト (言い換え、要約、事実の抽出、訂正の検証) | 手順書は差分だけを足す。部品のプロンプトは、正解つきの事例で採点しながら反復して改善する (常駐を設定した利用者の夜間) | v1.0 より後 |
| 第 3 段 | 成功と失敗から取り出した戦略、どの戦略を文脈に出すか、利用者の好みの重み | 戦略の抽出と、役立ち度の重みの学習 (CPU の小さなモデル)。モデルの重みは変えない | v1.0 より後 |
| 第 4 段 | 検索の設定 (候補数、しきい値、予算の配分)、判定点のしきい値 | LLM を使わず数値の探索で決める。待ち時間の目標 (NFR-102) を超える設定は採らない | v1.0 より後 (検索の評価の事例がたまってから) |
| 第 5 段 | コーディングの経験、成功した道具の手順 | 正解を試験で判定できる課題で複数の回答を比べる。道具の手順はサンドボックスで再実行して確かめる | コーディングモードを作ってから |

- **第 2 段に進む条件**: 回帰台帳の事例が 100 件以上たまり、採用した提案のうち巻き戻したものが少なく、誤採用の率 (§6.4) が 5% 以下であること。
- 各段の手法の出典 (論文) は、その段の着手の前に本書に書く。

## 10. 計算の量

- 2 段目のリプレイ (30 件 × 新旧 2 回と採点、安全の回帰事例を加える) は、中規模のモデルで 1 時間前後の見込み (暫定。v0.4 で計測する)。1 段目は数分で済むので、外れの提案を早く落とせる。
- リプレイは sleep-time に少しずつ進め、途中から再開できるようにする。利用者が操作したら止まる (NFR-105)。

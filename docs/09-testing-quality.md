## 1. 方針

- 試験は決定的にする (NFR-701)。時刻・ID・llama-server・ファイルシステムの障害は注入する (02 §6)。
- LLM の出力に依存する判定 (応答が指示に従わないか、など) は、通常の試験から分け、明示したときだけ流す (§3.4)。
- データの保全 (P1) に関わる試験は、障害の注入で網羅する (§4)。

## 2. 検証の区分

| 区分 | 意味 | 実行者・頻度 | 記録 |
|---|---|---|---|
| T | 自動の試験 | CI (PR ごと) | CI のログ |
| B | ベンチマーク・計測 | 基準機で、リリースの前と性能に関わる PR | `docs/perf/<X.Y.Z>/` |
| M | 手動の確認 | 人間が、リリースの前 | `docs/compat/<X.Y.Z>/` のチェックリスト |
| R | レビュー | PR のレビューとリリースの前 | PR の記録 |

## 3. 試験の階層

### 3.1 単体の試験

- 各 crate の `#[cfg(test)]` と doctest。正規化・キーの符号化・封筒・RRF・予算の計算など、純粋な関数を網羅する。

### 3.2 プロパティの試験 (proptest)

- キーの符号化の順序 (符号化した辞書順 = 意味の順)、封筒の CBOR の往復、知らない項目の保持 (03 §4.2 の規則 7)、正規化の冪等性、事実の置き換えの規則 (単値・多値の不変条件)。

### 3.3 llama-server の記録と再生

- `LlmClient` の trait の再生の実装で、記録した応答 (SSE の断片の並び・エラー・切断・遅延) を流す。記録は `tests/llm-cassettes/` に置き、作った会話だけを使う。
- 切断・5xx・逐次表示の途中の切断・`/slots` が無い・`/tokenize` が無いなどの縮退を、記録で再現する。v0.2 からは、embed・rerank が無い・記録と違うモデル・リランクの締切切れ・型縛りの出力が空、も再現する。
- **要求の先頭の一致** (v0.2、AC-FR-414-1): 応答が始まるまでの時間は CI で測れないので、再生のサーバが受け取った要求を並べ、連続する 2 つの要求で、システムプロンプトと前のターンまでの履歴のバイト列が一致することを確かめる (OQ-35)。

### 3.4 実際の llama-server を使う試験

- `cargo xtask live-llm` で、明示したときだけ流す。小さなモデル (設定で指定) を使う。
- 対象: 06 の API の前提 (S-02 の項目)、型縛りの出力、指示の混入への対策 (AC-NFR-504-1)、対応する llama-server の版の下限と最新。
- 結果は判定の揺れを含むので、同じ事例を 5 回流して 4 回以上の合格を合格とする (暫定)。

### 3.5 メモリの回帰ケース

- 事実の抽出・置き換え (単値・多値)・訂正の検証・忘れる・削除の波及について、入力 (作った会話) と期待する記録の状態の組を `tests/memory-cases/` に置く。
- v0.3 の着手前に、置き換えの誤りが起きやすい型 (多値の属性の一部の訂正、引用の中の否定、時間の軸の取り違えなど) を事例に書き出す (確定、[OQ-29](10-decisions.md#oq-29-メモリの回帰ケースの出どころ))。

### 3.6 版をまたぐ互換

- **golden fixture**: 種類ごと・版ごとの見本 (`tests/fixtures/<kind>/v<n>.cbor`) を読み、期待する値になること。v0.1〜v0.4 は今の形式の見本だけを持ち、形式を変えたら作り直す。v0.5 で固定した形式の版 `1` 以降の見本は、一度入れたら変えない (03 §4.1)。
- **移行**: v0.1〜v0.4 は、直前の版の DB の見本 (リリースのときに `tests/fixtures/db/<版>/` に残す) から今の版へ移行して、記録の件数とチェックサムが合うこと。v0.5 からは、形式の版 `1` 以降の各版の見本から今の版まで移行する。
- **新しい版のデータ**: 未来の版を模した見本 (知らない種類・知らない項目・新しい `v`・新しい DB の形式の版) を、読むだけで開き、壊さないこと (FR-215)。
- **版をまたぐ更新** (v0.2 から): 直前の版の配布物で作ったデータ根を、今の版で開いて使い、直前の版に戻して開けること (v0.2 は v0.1.2 に戻して、セッションを開いて書けること。v0.1.2 で消したものが、v0.2 で開き直したときに派生の記録と索引からも消えること、03 §4.2 の規則 12)。v0.6 では v0.5 から通し、v0.5 の書き出しを import で取り込む。

### 3.7 通信の検査

- 試験の実行中に、設定した llama-server (試験用の再生のサーバ) 以外への接続が 0 件であることを確かめる (AC-NFR-501-1)。外への接続を拒否する環境で試験を流し、拒否が起きたら失敗にする。

### 3.8 手動の受入

- `docs/compat/<X.Y.Z>/acceptance.md` のチェックリストで、端末と IME の組み合わせ (07 §2.3)、setup の案内 (NFR-603)、エラーの表示 (NFR-604)、配布物の検証の手順を確かめる。

## 4. 障害の注入

`evorag-store` の下の層 (ファイルの書き込みと書き切り) に、注入の点を置く。

| 注入 | 確かめること |
|---|---|
| 書き込みの任意の時点での強制終了 (子プロセスを kill) | 起動し直すと、確定したターンと明示の操作が残り、書きかけは無い (NFR-301)。1,000 回 (v0.1 のリリースゲート) |
| ジャーナルだけの書き込みの失敗 | DB に書かれず、画面に知らされる (AC-FR-202-1) |
| DB だけのコミットの失敗 | ジャーナルから起動時に取り込まれる |
| DB のファイルの一部の書き換え・切り詰め | `broken/` に移り、退避とジャーナルから戻る (AC-FR-205-1) |
| 記録 1 件の本体の書き換え | quarantine に移り、他の記録は読める (AC-FR-206-1) |
| 索引のファイルの削除・書き換え | 作り直し、その間は残りで答える (AC-NFR-306-1) |
| 空きの不足 | 裏の処理が止まり、会話の追記は続く (AC-FR-217-1) |
| ジャーナルの末尾の書きかけの行 | 起動時に切り詰められ、他の行は取り込まれる |
| 退避の作成中の強制終了 | 一時名のまま残り、次の退避で消され、古い退避は無事 |
| setup でのモデルの記録の書き換えの途中の強制終了 (v0.2) | 記録とやり直しの job が、両方あるか両方無いか。job を失っても、起動時に状態から作り直しが求まる (06 §3.2、04 §4) |
| 突き合わせ (03 §4.2 の規則 12) と sleep-time の job の途中の強制終了 (v0.2) | 次の起動で続き、結果が止めずに通したときと同じ (AC-FR-301-1) |
| 削除の行をジャーナルに書いた後、DB のコミットの前の強制終了 (v0.2) | 取り込みの後に、派生の記録も消える (AC-NFR-506-2) |

- **電源断の模擬** (S-01 で実現できることを確かめた): redb の `StorageBackend` を差し替え、書き切りを呼ぶ前の書き込みを「すべて捨てる」「4 KiB の単位で一部だけ残す」「すべて残す」の 3 通りで模擬する。対照として、会話の追記を `Durability::None` で書く設定で、模擬が失いを検出できること (S-01 では 50 回中 50 回失った) を毎回の版で確かめる。ジャーナルの書き込みにも同じ形の注入の層を置く。
- 強制終了の時点は、コミットの最中だけでなく、起動・修復・退避・compact・移行の最中にも散らす。

### 5.2 想起と検索の評価

- **想起の事例** (v0.1): 作った会話のセッションの組と、別のセッションでの問い、正しい以前の発言の組 (`tests/retrieval/recall-v0.1.toml`)。AC-FR-402-1 で使う。
  - 30 件以上にし、易しいもの・表記揺れ・言い換えをそれぞれ 3 割以上含める (10 件では、組み方で合否が変わる、S-04)。
  - 関係の無い問い (以前の会話に答えが無い問い) を 10 件以上置き、Abstain の率を記録する。
  - 初版には S-04 の会話と事例 (`spikes/S-04/data/`) を使う。共通の文字が無い言い換えの事例は、v0.2 のベクトルの検索の評価にも使う。
- **想起の事例** (v0.2): v0.1 の事例に、リランカーのある構成での判定 (AC-FR-402-3。関係の無い問いで何も添えない割合と、正しく添える割合) を足す。実際の埋め込みとリランカーを使うので、§3.4 の試験として流す。英語の事例 (`en`) も置く (S-14)。
- **検索の評価** (v0.2 から): recall@3、recall@10、nDCG@10、待ち時間の平均と p95 (05 §6)。
- **事実の想起** (v0.3): 別のセッションで話した事実を答える事例 20 件以上。
- **LongMemEval の一部** (v0.3): 公開の長期記憶の評価の一部を流し、基準値を記録する (合否には使わず、版の間の比較に使う)。

## 6. CI (GitHub Actions)

### 6.1 ワークフロー

| ワークフロー | きっかけ | 内容 |
|---|---|---|
| `ci.yml` | PR (宛先が `develop`・`main`) と、`develop`・`main` への push | §6.2 のジョブ |
| `nightly.yml` | 毎日 (既定ブランチの定義で動き、`develop` を対象にする) | 障害の注入の長い版 (10,000 回)、proptest の件数を増やした版、`cargo audit` |
| `release.yml` | 人間が付けたタグ `v*` と、署名の後の手動の実行 | タグの検証、配布物の作成、`SHA256SUMS`・`release.json`、署名の検証 (署名そのものは人間が手元で行う、12 §5)。手順は §9.2 |

## 7. 依存の検査

- `deny.toml`: ライセンスの許可リスト、取得元 (crates.io だけ)、ワイルドカードの版の禁止。
- `deps-policy.toml`: crate ごとの禁止依存 (02 §4.3)、C を含む依存の数 (0。例外なし)、禁止する crate (ring・aws-lc-rs・aws-lc-sys・openssl-sys・cc を使う build script)、推移的な依存の数の上限 (M1.1 で計測して決める)。
- 依存を足す PR の書き方は 11 §9.5。

## 8. 品質ゲート

### 8.1 PR のマージのゲート

1. 必須のチェック (§6.2) がすべて通る。
2. 変更に関わる AC の試験が足されているか、既存の試験で判定されている (`verifies:`)。
3. 仕様と食い違う判断があれば、仕様の変更の PR か OQ がある (`needs-oq`)。
4. セルフレビューのチェックリスト (データの保全・通信・ログに本文を出さない・後方互換・文言キー・依存) を PR の本文に貼る。
5. CHANGELOG の Unreleased に 1 行 (利用者に見えない変更は `changelog: none`)。

### 8.2 リリースのゲート

ゲートは、版上げの後の `develop` の先頭 (**判定コミット**) で判定し、リリースのチェックリスト `docs/compat/<X.Y.Z>/release-checklist.md` (雛形は `docs/compat/_template/release-checklist.md`) に、判定・根拠・確認者・日付を書く。**タグの前に済む行だけ** を載せ、タグの後の結果 (配布物・タグの検証・署名の検証・公開後の検証) は GitHub Release のノートの「検証」の節に書き、リポジトリには戻さない。

| 項目 | 判定 |
|---|---|
| 要件充足 | その版の Must の AC (01 §5) がすべて合格。`tests/ac-checklist.toml` に `missing` が無い |
| データ保全 | §4 の注入を v0.1 は 1,000 回、v0.2 以降は 10,000 回続けて失敗 0 (判定コミットに対する `nightly.yml` の手動の実行)。試験を 2 回流して結果が同じ (`determinism`) |
| 互換 | §3.6 の試験がすべて通る (v0.2 からは直前の版からの移行、v0.3 からは `update` での更新と巻き戻し、v0.5 からは形式の版 `1` 以降のすべてからの移行を含む) |
| 性能 | §5.1 の目標を基準機で満たす。記録は `docs/perf/<X.Y.Z>/` |
| 受入 | §3.8 の手動の受入のチェックリスト (`docs/compat/<X.Y.Z>/acceptance.md`) が完了 |
| 実際の LLM | §3.4 の試験 (`cargo xtask live-llm`) が合格 (v0.1 は AC-NFR-504-1) |
| セキュリティ | `cargo deny check advisories` がきれい。配布物・docs・試験データに秘密と個人情報が無い (12 §6 の PC-1・PC-2・PC-6) |
| 依存 | C を含む依存 0、推移的な依存が上限以内 (`cargo xtask check-deps`) |
| ドキュメント | 利用者向けの README (`dist/README.md`)・CHANGELOG・リリースノートに、既知の制約・更新と巻き戻しの手順・データの移行の有無がある。リポジトリの README (`README.md` と `README.ja.md`) の「最新の版」と「状況」がその版と合っていて、2 つの内容が食い違っていない (11 §9.3) |

- 判定コミットを書いた後に入れてよい変更は、`docs/compat/<X.Y.Z>/`・`docs/perf/<X.Y.Z>/`・`tests/ac-checklist.toml` だけ (記録の許可リスト)。ほかを入れたらゲートをやり直す。
- 基準機の型番など固有の情報は記録に書かない (11 §9.7)。

## 9. リリース手順

手順の名前と番号は evoeditor の 09 §9.2 に揃える (同じ番号は同じ手順。その版で行わない手順は「行わない」と書いて番号を残す)。

### 9.1 版と頻度

- 機能リリースは `0.y.0`、bugfix リリースはパッチ版 (11 §9.1)。日付ではなくゲートで出す。
- **リリース候補 (`-rc.N` などのプレリリース) は出さない** (確定 (ユーザー回答、2026-11-10))。ゲートは版上げの後の判定コミットで行い、合格したらそのまま昇格する。
- 記録の置き場所は、版を `X.Y.Z` (先頭の `v` なし) で書いたフォルダ: `docs/compat/<X.Y.Z>/` (リリースのチェックリスト・手動の受入) と `docs/perf/<X.Y.Z>/` (計測)。

### 9.2 手順

1. **凍結**: `develop` への merge (Dependabot の PR を含む) を保留する。例外は `main` → `develop` の取り込み (パッチ版のリリースの後) だけで、版上げ (手順 2) の前に限る (11 §9.1)。
2. **版上げ**: `develop` に対するリリース PR (`chore(release): vX.Y.Z`) で、workspace の版を `X.Y.Z` にし、CHANGELOG の Unreleased を `X.Y.Z` にし、リポジトリの README (`README.md` と `README.ja.md`) の「最新の版」と「状況」をその版に直す (パッチ版を含む、11 §9.3)。**ゲートの前に行う** (出荷する版番号のソースで判定するため)。リリース PR を作る前に、`develop` の先頭の push の CI (`dco` を含む) が通っていることを確かめる (落ちたまま進めると、`develop` → `main` の PR で止まり、判定コミットを改めることになる。08 §6 の v0.1.2)。入れた後の `develop` の先頭の SHA を判定コミットとし、`git merge-base --is-ancestor develop <判定コミット>` と `git merge-base --is-ancestor main <判定コミット>` が真であることを確かめる (偽なら `main` を `develop` に取り込むなどして整え、手順 2 からやり直す)。
3. **ゲート**: 判定コミットで §8.2 を行い、`docs/compat/<X.Y.Z>/release-checklist.md` (先頭に判定コミットの 40 桁の SHA) と、性能・受入の記録を埋めて `develop` に入れる (タグの前)。
4. **昇格とタグ**: `develop` → `main` の PR を人間が作り、merge commit で入れる。`main` のマージコミットに、人間が署名付きのタグ `vX.Y.Z` を付ける。`release.yml` は最初にタグを検証する (`git verify-tag` と `.github/allowed_signers`、`main` のマージコミットを指すこと、`Cargo.toml` の版との一致、判定コミットとの差分が記録の許可リストだけであること)。昇格が終わったら凍結を解く。
   - タグの署名鍵 (Git の SSH 署名鍵) は、minisign の鍵とは別の鍵にする (11 §9.7)。
   - `release.yml` の失敗: publish の前 (draft のまま) なら、直して同じタグで再実行してよい。成果物の内容に関わる直しが要るときは、メンテナが draft の Release とタグを消し、直しを `develop` に入れて手順 3・4 をやり直してから、同じ版でタグを付け直す。publish した後は同じ版のタグを付け直さない (次のパッチ版で出す)。
5. **ビルド** (`release.yml`): `cargo xtask dist` で、配布物 (v0.1 は Windows x86_64 の zip、C ランタイムは静的にリンク。v0.2 から Linux x86_64 の tar.gz (musl、静的) も)・`SHA256SUMS`・`release.json` を作り、`THIRD-PARTY-NOTICES.md` を同梱する (12 §5)。v0.2 からは、タグの検証と下書きの作成 (draft)、ターゲットごとの配布物 (build)、すべての配布物の目録 (manifest、`cargo xtask dist --manifest-only`) の 3 段で行う。
6. **検証** (`release.yml`): 配布物の中身とハッシュ、`release.json` と `SHA256SUMS` の一致、`evorag --version` の版がタグと一致することを確かめ、draft の Release に置く。minisign の検証は署名 (手順 7) の後なので、ここでは行わず手順 9・10 で行う。
7. **署名**: メンテナが手元 (オフラインの鍵) で `SHA256SUMS` と `release.json` に minisign で署名し (trusted comment に版と `release.json` の SHA-256、12 §5.2)、`.minisig` を draft に添付する。公開鍵はリポジトリ直下の `minisign.pub` と README に置き、リポジトリの外の経路でも公開する。
8. **SBOM**: v0.1 では行わない (時期は未定)。
9. **draft から publish**: 人が、署名の後の `release.yml` の検証 (`workflow_dispatch`、`cargo xtask verify-release --require-signatures`) が通ること、CHANGELOG の本文とリリースノートの「更新の方法」・データの移行の有無・README の「更新と巻き戻し」が版と合っていること、リリースのチェックリストがすべて埋まり、ノートの「検証」の節に publish の前の結果があることを確かめて、publish する。
10. **公開後の検証**: publish した Release から (手元の成果物ではなく) 配布物・`SHA256SUMS`・`.minisig` を取得し、`dist/README.md` の手順 (`minisign -V` とハッシュ) で確かめ、結果をノートの「検証」の節に追記する (リポジトリには戻さない)。不一致なら直ちにノートの先頭に「検証に失敗したので使わない」と書き、告知を止めて原因を調べる (同じ版の成果物は差し替えず、次のパッチ版で出す)。
11. **crates.io**: 行わない (公開の時期は v1.0 の前に決める、12 §5.1)。
12. **パッケージ** (winget など): 行わない (時期は未定)。
13. **告知と取り込み**: `main` → `develop` の取り込みの PR (merge commit) を人間が作る。08 の繰り越しの記録を更新する。

### 9.3 リリースの取り下げ

- 重大な不具合が見つかったら、Releases の説明に警告を書き、パッチ版を出す。配布物は消さない (巻き戻しの手順で使うため)。
- データの形式に関わる不具合は、リリースノートに退避からの戻し方を書く。

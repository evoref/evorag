## 1. DB の使い方

- **DB サーバは使わない**。埋め込み型の DB の redb (純 Rust、ACID、1 つの書き手と MVCC の読み手) を 1 ファイルで使う。SQL は使わない (確定、[ADR-0004](10-decisions.md#adr-0004-記録の正本は-redb-の汎用の表))。
- **記録の正本は `evorag.redb` だけ**。会話、ノート、事実、埋め込み、信号、学習の台帳、カートリッジの台帳を入れる。
- **索引は派生物**。`evorag.redb` とカートリッジから作り直せるファイルとして別に置き、壊れたら消して作り直す (05 §2)。
- **カートリッジの中身はファイル**。導入した版ごとのフォルダに読み取り専用で置く (14)。

## 2. 置き場所

### 2.1 フォルダ

置き場所は OS ごとに環境変数から解決し (Windows は `LOCALAPPDATA`、Linux は `XDG_CONFIG_HOME`・`XDG_DATA_HOME` (無ければ `HOME` の下の既定)、macOS は `HOME`)、`--data-root` (と設定 `storage.data_root`) で変えられる (確定、[OQ-17](10-decisions.md#oq-17-置き場所))。`directories` crate は、依存に MPL-2.0 の crate を含むので使わない (12 §2)。

| 区分 | 中身 | Windows | Linux | macOS |
|---|---|---|---|---|
| 設定 | `config.toml` | `%LOCALAPPDATA%\evorag\config\` | `~/.config/evorag/` | `~/Library/Application Support/evorag/config/` |
| データ根 | `evorag.redb`、`journal/`、`index/`、`cartridges/`、`backups/`、`broken/`、`lock` | `%LOCALAPPDATA%\evorag\data\` | `~/.local/share/evorag/` | `~/Library/Application Support/evorag/data/` |
| 状態 | `logs/`、`update/` (取得した更新の一時置き場) | `%LOCALAPPDATA%\evorag\state\` | `~/.local/state/evorag/` | `~/Library/Logs/evorag/` (logs)、`~/Library/Caches/evorag/` (update) |

- Windows で Roaming (`%APPDATA%`) を使わない。移動プロファイルで同期され、§2.2 の「危ない置き場所」に自分から当たるため。
- macOS では設定とデータ根を別の下位フォルダにする。`evorag reset` (データ根を消し、設定は残す) が設定まで消さないようにするため。
- 状態のフォルダは、Linux は `XDG_STATE_HOME` (無ければ `~/.local/state`)、Windows と macOS は上の表の場所を使う。
- 作るフォルダとファイルは、ほかの一般の利用者が読み書きできない権限にする (Windows は所有者・SYSTEM・Administrators だけの ACL、Unix は 0700 / 0600、NFR-503)。
  - Windows は、今の利用者・SYSTEM (`S-1-5-18`)・Administrators (`S-1-5-32-544`) の 3 つだけを許す ACE を持つ、継承を切った DACL を付ける。Windows の慣例 (`%LOCALAPPDATA%` の既定、OpenSSH が秘密鍵に求める権限) と同じ。フォルダは evorag が新しく作ったときだけ付け (中へ継承させる)、既にあったフォルダ (`--data-root` で指した既存のフォルダなど) は変えない (継承を切ると、その下のすべての権限が変わるため)。ファイルは書くたびに付ける。
  - ネットワークの置き場所 (相手の側では SID が別のアカウントになり、作った本人が開けなくなるおそれ) と、ACL を持たないファイルシステム (FAT・exFAT) には付けない。FAT・exFAT の警告 (§2.2) には、所有者だけの権限が付かないことも含める。
  - SYSTEM と Administrators を残す理由: 管理者は所有権を取れば読めるので、外しても守れない。外すと、SYSTEM の権限で動く退避のソフトが読めなくなり、利用者のアカウントの SID が変わったとき (PC の移行・アカウントの付け替え) に管理者の画面操作で戻せなくなる。守る相手は、同じ PC の別の一般の利用者である (02 §8)。

### 2.2 危ない置き場所

データ根と退避先の両方について、起動時に次を調べ、当たれば既定で起動を拒否する (設定 `storage.allow_unsafe_location = true` で警告だけにできる)。同期による書き換え・ロックの無効化で壊れやすいため。

| OS | 調べること |
|---|---|
| Windows | ドライブの種類 (ネットワーク)、UNC パス、クラウドファイルの属性・リパースポイント (OneDrive、既知フォルダの移動を含む)。ファイルシステムが FAT / exFAT のときは警告だけを出す (拒否はしない。S-01 の試験は exFAT でも合格したが、ジャーナリングを持たず、電源断に弱いため) |
| Linux | `statfs` のファイルシステムの種類 (NFS、CIFS/SMB、FUSE の同期) |
| macOS | ボリュームの種類 (ネットワーク)、iCloud Drive の下か |

- 判定は経験則で、漏れはありうる。README に「同期フォルダに置かない」と書く。

## 3. `evorag.redb` の構成

### 3.1 表

用途ごとの専用の表は作らず、少数の汎用の表に「種類」を付けた記録を入れる。機能を足すときは、表を増やさずに種類を増やす (確定 (ユーザー回答、2026-11-08))。

| 表 | キー → 値 | 中身 |
|---|---|---|
| `meta` | 文字列 → 文字列 | §3.1.1 のキー。DB の形式の版、データ根の ID、書いた evorag の版、ジャーナルの最後に取り込んだ連番、プロンプトの言語など |
| `records` | (kind, id) → 封筒 | すべての記録 |
| `links` | (from, rel, to) → 属性 | 記録どうしの関係。逆引き用に (to, rel⁻¹, from) も同じトランザクションで書く |
| `lookup` | (kind, field, 値, id) → () | 探すための副索引 |
| `blobs` | (id, part) → バイト列 | 大きなデータ (埋め込みのベクトル、長い本文) |

#### 3.1.1 `meta` のキー

キーと値の意味は v0.1 から変えない (08 §2.2)。キーは足すだけにする。値はすべて UTF-8 の文字列。

| キー | 値 |
|---|---|
| `format.version` | この DB の形式の版 (`0.<n>`、v0.5 から `1`、`2` …)。版は `.` で区切った整数の並びとして比べる (文字列として比べない) |
| `format.min_read` | この DB を読むだけで開くのに要る、evorag が知る形式の版の下限 |
| `format.min_write` | この DB に書くのに要る、evorag が知る形式の版の下限。足すだけの変更なら `format.version` だけを上げ、`min_write` を据え置いて古い版の書き込みを許せる |
| `key_encoding.version` | キーの符号化 (§3.3) の版 (`1`) |
| `data_root.id` | データ根の ID (UUID v7)。作ったときに 1 度だけ書く |
| `created_by` | DB を作った evorag の版 (semver) |
| `last_writer` | 最後に書き込みで開いた evorag の版 |
| `max_writer` | これまで書き込みで開いた evorag の版の最大。単調に増やす。自分の版より大きければ、巻き戻しとして扱う (§4.2 の規則 6、12 §7) |
| `writer.<semver>` | その版が最初に書き込みで開いた時刻 (UTC、ミリ秒)。書いた版の履歴 |
| `migration.state` | `none`、または `in_progress:<元の版>:<先の版>:<段>`。移行先のファイルに書き、移行を終えてから `none` にして入れ替える (§12.1) |
| `journal.last_seq` | ジャーナルから取り込んだ最後の連番 (§6) |
| `prompt.language` | プロンプトの言語 (07 §6.1)。一度書いたら変えない |

### 3.2 封筒

すべての記録の共通の形。`records` の値は、次のバイト列にする。

| 位置 | 内容 |
|---|---|
| 先頭の 1 バイト | 値の配置の版 (`1`)。知らない値なら、新しい版の記録として読むだけにして数える (quarantine に移さない) |
| 続く 8 バイト | チェックサム。xxh3-64 (リトルエンディアン) で、**表のキーと、続く封筒の CBOR のバイト列そのもの** を覆う。符号化し直したものではなく、保存したバイト列を覆うので、知らない項目と `writer` も含めて、どのバイトの破損も見つかる。読むたびに、復号の前に確かめる |
| 残り | 封筒の CBOR (項目名つきの map) |

封筒の項目は次のとおり。

| 項目 | 内容 |
|---|---|
| `id` | 記録の ID (キーと同じ値。読むときにキーと突き合わせる) |
| `kind` | 種類の名前 (§3.3) |
| `v` | その種類の形式の版 (整数) |
| `created_at` / `updated_at` | 作成と更新の時刻 (UTC、ミリ秒) |
| `writer` | 書いた evorag の版 |
| `body` | 本体。項目名つきの CBOR (確定、[ADR-0005](10-decisions.md#adr-0005-記録の本体は項目名つきの-cbor)) |
| (知らない項目) | 読み手が知らない封筒の項目。保存上の項目名は持たず、読み手はまとめて保持し、書き戻すときに同じ名前のまま残す (§4.2 の規則 7)。本体の読み方を変える封筒の項目 (圧縮・暗号化など) は、`format.min_write` を上げて足す |

- 書き出し (§11) とジャーナル (§6) の行には、封筒の項目だけを JSON で写す。チェックサムは写さず、行の `sum` で代える。

### 3.3 種類

| 種類 | 中身 | 主な関係 (links) と副索引 (lookup) | 版 |
|---|---|---|---|
| `session` | 題名、モード、状態 | 更新時刻の順 | v0.1 |
| `turn` | 本文、役割 (利用者 / 応答 / システム)、状態 (確定 / 応答待ち / 完了 / 中断 / 失敗)、model_key、生成の設定、添えたものの ID、判定点。v0.2 から任意の項目 `obs` (観測値、05 §3.6) | セッションへ、添えたメモリへ | v0.1 |
| `signal` | 評価・再生成・訂正の候補などの生の記録 | 対象のターンへ | v0.1 |
| `setting` | 利用者が画面から変えた、データ根の全体に効く設定。v0.2 は答え方の既定 (07 §3 の `/style`) だけ。セッションごとの出典の範囲 (`/sources`) は、v0.1 から `session` の本体 (`memory`) に置く | 項目の名前 | v0.2 |
| `job` | 裏の処理の手順の進み具合 | 状態 | v0.1 |
| `tombstone` | 消した記録の ID と時刻 | — | v0.1 |
| `quarantine` | チェックサムが合わないか読めない記録の原文と理由 | 元の種類と ID | v0.1 |
| `chunk` | ターンの中の範囲 (文字の位置)。本文は持たない (05 §2.4) | 出典のターンへ | v0.2 |
| `note` | 1 つの話題の検索の鍵 (語句の並び、8 個まで) と、出典の往復の一覧 (各往復の利用者の発話のターンの ID) (04 §2) | 出典のターンへ | v0.2 |
| `embedding` | どの記録の、どの単位 (チャンク 1 つ、またはノートの鍵 1 つ。鍵は単位 `key` と鍵の位置で表す、04 §2) の、どのモデル (model_key) の埋め込みか。ベクトル自体は `blobs` | 対象の記録へ | v0.2 |
| `model_binding` | 役割 (`chat`・`embed`・`rerank`。足すだけで広げる文字列) ごとに記録したモデル: model_key、元の値 (ファイル名、名前、`meta` の値、`build_info`)、記録した時刻、前の model_key の履歴 (06 §3.1) | 役割 | v0.2 |
| `model_probe` | モデルの性質の点検の結果 (06 §3.3)。作り直せる派生の記録 | model_key と `build_info` | v0.2 |
| `threshold` | リランクのしきい値と帯の下限: リランカーの model_key、対象の種類 (`conversation` など。足すだけで広げる文字列)、版、求めた方法 (`bundled`、v0.4 から `signals`)、使った同梱の事例、合否と数えた値、採用した時刻 (封筒の作成時刻、05 §3.7) | リランカーの model_key と対象の種類 | v0.2 |
| `recall_feedback` | 想起への利用者の操作 (05 §5.2): 操作 (`attach`・`irrelevant`)、問いの応答のターン、対象の往復、その時のリランクの生の値とリランカーの model_key | 応答のターンへ、対象の往復のターンへ | v0.2 |
| `fact` | 04 §5 の「事実の形」 | 出典のターンへ、置き換えた事実へ。subject と attribute | v0.3 |
| `correction` | 訂正の候補と検証の結果 | 対象のターンへ | v0.3 |
| `case` / `precept_set` / `proposal` | 回帰台帳の事例、precept の版、提案と判定 | 元のターンへ。model_key | v0.4 |
| `cartridge` | 導入した版、有効・無効、署名者、埋め込みの状態 | カートリッジの ID と版 | v0.5 |

- **v0.2 で足す種類の、知らない値の読み方** (§4.2 の規則 11): `model_binding` の知らない役割、`threshold` の知らない対象の種類は、読んで残し、使わない。`recall_feedback` の知らない操作は、読んで残し、較正 (v0.4) に使わない。`setting` の答え方の既定の知らない値は `auto` として扱う (07 §3)。どれも、読めない記録として数えない。v0.1.2 から見ると、v0.2 の種類はどれも知らない種類なので、読み飛ばして残す (規則 6)。
- **v0.1 の種類の `v` を上げない**: v0.2 は `turn`・`session`・`signal`・`job` の `v` を 1 のままにする。v0.1.2 は、`v` の新しい記録がある種類の記録を新しく作らない (規則 6) ので、上げると v0.1.2 に戻したときにセッションの削除 (`job` を書く) などが断られるため。
  - `turn` の `obs` は、既存の項目とつながらない任意の項目なので、規則 1 の「`v` を上げる」に当たらない。
  - `job` は `task` (文字列) と `ids` の形を保ち、新しい手順は `task` の新しい値で表す。足す項目 (手順の版、model_key) は任意にする。
- **`turn` の `obs`**: 観測値はすべて任意の項目にし、本体の最上位の 1 つの map (`obs`) にまとめる。判定点 (`recall`) の中には足さない (古い版が判定点を書き戻すときに、知らない項目を落とさないため。§4.2 の規則 7 は本体の最上位の項目を残す)。縮退の理由のように値が増えうるものは、列挙ではなく文字列で持つ。
- **1 件だけのはずの記録**: `model_binding` (役割ごとに 1 件) と `setting` (項目ごとに 1 件) が、ジャーナルからの取り込みなどで 2 件以上になったときは、`updated_at` の新しいものを採り、ほかを消す (消すときはジャーナルにも削除の行を書く)。
- **派生の記録の出典**: `chunk`・`note`・`embedding`・`recall_feedback` は、出典の記録の ID を本体に持つ (関係だけに頼らない)。古い版は、ターンを消すときにそのターンへの関係も消すので、関係ではたどれなくなるため (§4.2 の規則 12)。
- **`threshold` とジャーナル**: v0.2 のしきい値は同梱の事例から求め直せるので、ジャーナルに書かない。v0.4 で利用者の信号で動かす (05 §3.7) ときは、利用者の操作から作る値になるので、ジャーナルに書くかを M4.0 で決める。
- ID は時刻順に並ぶ UUID v7 (RFC 9562)。同じミリ秒の中でも単調に増えるように生成する (`IdGen`、02 §6)。
- キーの符号化: キーを要素の並び (tuple) として、各要素の先頭に型の印 (1 バイト) を付け、順序を保つ符号で並べる。文字列とバイト列は `0x00` を `0x00 0xFF` に置き換え、終端に `0x00` を置く。整数と時刻は符号ビットを反転した 8 バイトのビッグエンディアン、ID は 16 バイト。これで、バイト列の辞書順の比較が意味の順と一致し、前方一致で走査できる。文字列の順は Unicode の code point の順で、正規化 (NFC など) は副索引の項目を定める側が決める。符号化は `evorag-store` の 1 か所に置き、版 (`key_encoding.version`) を持つ。

### 3.4 書き込みと耐久性

- 書き込みはすべて書き手スレッドの redb のトランザクションで行う (02 §5)。記録とその関係・副索引は同じトランザクションで書く。
- redb は 4.x に固定する (S-01 で確かめた版は 4.5.0。5.0 は開発中)。書き込みの並行の形は既定の 1 つの書き手 (`ExclusiveWriter`) にする (ほかの形では `Durability::None` を使えない)。
- **会話の追記と明示の操作**: コミットのたびにディスクへ書き切る `Durability::Immediate` で書く。S-01 で、1,000 回の強制終了と 1,000 回の電源断の模擬で、コミット済みの記録を 1 件も失わないことを確かめた (コミット 1 件は約 1〜2 ms)。
- **裏の処理の結果**: `Durability::None` でまとめて書き、区切りで `Immediate` のコミットを 1 回入れる。`None` のコミットは、電源断だけでなく **プロセスの強制終了でも失われる** (S-01)。失っても job から作り直せるものだけを `None` で書く。
- 強制終了の後の開き直しには修復が走る (S-01 で 60〜85 MB の DB で中央 46 ms、最大 287 ms。DB の大きさに比例する)。修復を速くする設定 (`quick_repair`。コミットは少し遅くなる) を使うかは、起動の時間 (BM-101) を測って決める。
- **発話は先に保存する**: 発話は LLM に送る前に `turn` (状態「応答待ち」) として確定する。応答は、完了・中断・失敗のいずれかを別のコミットで書く (04 §3)。
- redb は I/O のエラーの後、開き直すまで書き込みを受け付けない (`PreviousIo`)。書き込みのエラーを受けたら、それ以上書き込まずに DB を開き直す。開き直せなければ §8 の「DB の破損」として扱う。会話の追記はジャーナルに残っているので失わない。
- 型を知らずに表を写せるように (退避と移行、§7.1・§12)、すべての表のキーと値の型をバイト列 (`&[u8]` → `&[u8]`) にし、符号化は `evorag-store` の中で行う。

## 4. 後方互換の規則

後方互換を最優先にする (P6、確定 (ユーザー回答、2026-11-08))。

### 4.1 互換の起点 (v0.5)

データの互換は **v0.5 から** 約束する (確定 (ユーザー回答、2026-11-09)、[OQ-24](10-decisions.md#oq-24-データの互換をいつから約束するか))。

| 期間 | 形式の扱い | 必ず守ること |
|---|---|---|
| v0.1〜v0.4 (形式を固める期間) | 表・キーの符号化・封筒・種類の本体・ジャーナル・書き出しの形を、より良い構成に変えてよい。形式の版は `0.<n>` と書く | 形式を変える版は、**直前の版のデータからの移行** を持ち、移行の前に退避する (§7.2、§12)。下の規則 6 (新しい版のデータを壊さない) と規則 7 (知らない項目を消さない) は v0.1 から守る。版を飛ばして更新したときは、間の版を順に当てるか、理由を示して読むだけで開く |
| v0.5 のリリースの前 | 保存の形式を見直して凍結する (08 §2.6 の M5.0)。v0.1〜v0.4 の間に分かった問題をここで直す | 凍結した形式を形式の版 `1` とし、golden fixture をこの版から固定する |
| v0.5 以降 | 下の規則のすべてを守る | 形式の版 `1` 以降のすべての版を読める |

- v0.1〜v0.4 の利用者向けのリリースノートと README に、「形式は v0.5 まで変わることがあり、移行は直前の版から行う。版を飛ばさずに更新する」と書く。

### 4.2 規則

1. **足すだけ**: 項目は追加だけにする。名前の変更・削除・意味の変更はしない。足す項目には既定値を決め、その項目が無い古い記録は既定値で読む。**既存の項目とつながる項目 (派生の値など) を足すときは、その種類の `v` を上げる** (古い版がつながりを知らずに既存の項目だけを書き換えるのを、規則 6 で止めるため)。
2. **意味を変えるときは新しく作る**: 新しい項目か新しい種類を作り、古いものも読み続ける。
3. **項目名つきの符号**: 本体は項目名つきの CBOR にする。並び順で意味が決まる符号は使わない。
4. **古い版はすべて読める**: 種類ごとに、過去のすべての版 (形式の版 `1` 以降) の読み方をコードに残し、版ごとの固定の見本 (golden fixture、`tests/fixtures/<kind>/v<n>.cbor`) で試験する。書くときは今の版で書く。読んだ記録を書き直すときに新しい版になる。v0.1〜v0.4 の間は、今の版の見本だけを持ち、形式を変えたら見本も作り直してよい (§4.1)。
5. **一括の移行は最後の手段**: 表の構成を変える移行は避ける。必要なときだけ、退避してから `meta` の DB の形式の版を上げて行う (§12)。
6. **新しい版のデータ**:
   - 知らない種類は読み飛ばして数え、消さない。
   - 知っている種類でも `v` が新しい記録は、その記録の更新を止めて読むだけにし、更新を案内する。その種類の新しい記録を今の `v` で作ってよいかは、種類ごとに決める (既定は作らない)。忘れる・削除 (tombstone) は本体を解釈せずにできるので、新しい `v` の記録にも行う。
   - `max_writer` (§3.1.1) が自分の版より新しいときは、巻き戻しとして知らせる (書き込みは上の規則に従う)。
   - DB の形式の版が新しければ、全体を読むだけで開く。
7. **知らない項目を消さない**: 封筒の知らない項目は、同じ名前のまま書き戻す。本体の知らない項目は本体の map の中にそのまま残す。書き戻すときは、今の版の本体を省略なしに書き (値の無い項目は null で書く)、元の本体のうち書いた項目に無い名前だけを足す。こうすると、消した既知の項目は戻らず、知らない項目だけが残る。
8. **保存の仕組みからの独立**: DB の操作は `evorag-store` の trait に閉じ込め、他の crate は redb を直接使わない (02 §4.3 の R2)。
9. **書き出しの形式を互換の拠り所にする**: `evorag export` は封筒をそのまま JSON Lines に書く。どの版の evorag も、自分より古い書き出しを読める。
10. **索引とカートリッジも同じ考え方**: どちらも形式名と版を持ち、古い版を読めるようにする。索引は作り直せるので、読めない版は捨てて作り直す。
11. **列挙の値と、本体を読めない記録** ([OQ-40](10-decisions.md#oq-40-古い版が新しい記録と設定を読めること)):
    - 既存の列挙 (ターンの役割と状態、判定点、信号の種類、セッションの状態など) に値を足さない。新しい区別は、任意の項目を足して表す (規則 1)。値を足せる列挙にするときは、知らない値の読み方 (既定の値で読むか、その記録を読めない記録として扱うか) を種類ごとに決めてから足す。
    - 封筒は読めるが、本体をこの版の型として読めない記録 (知らない列挙の値、型の違う項目) は、**読めない記録** として読み飛ばして数える。消さず、書き換えない。同じセッションのほかのターンは読み続け、読めなかった件数を画面に示す。
    - 本体から作り直す関係と副索引 (ジャーナルからの取り込みと復元で作るもの、§6) は、本体のうち、その関係に要る項目 (ターンの `session` と `reply_to`、信号の `target`、v0.2 から想起への操作の対象) だけを読んで作る。ほかの項目が読めなくても、関係を失わない (読めないターンも、セッションの削除と忘れる操作の対象に残る)。
12. **出典の無い派生の記録の突き合わせ** (v0.2 から): 削除・忘れるの操作が、派生の記録 (チャンク・ノート・埋め込みとその blob・想起への操作など) に届かないことがある。古い版はそれらの種類を知らない。ジャーナルからの取り込み (§6) と restore は、消した記録そのものしか消さない。そこで、次の突き合わせを行う。
    - **見つけ方**: 本体が持つ出典の ID (§3.3 の「派生の記録の出典」) の記録が DB に無い派生の記録を、出典の無い記録とする。関係ではたどらない。
    - **消し方**: 出典の無い記録を消す。ジャーナルに書く種類 (`recall_feedback`) は、ジャーナルに削除の行を書き、`put` の行を除く (§6。書かないと、restore で蘇る)。消した ID は、保持している退避からも除く (§7.3)。次の起動で compact する。
    - **いつ行うか**: (1) 前回書いた版 (`meta` の `last_writer`) が、自分の知る派生の種類のどれかを持たない版のとき (v0.2 では、`last_writer` が 0.2.0 より古いとき)。(2) `restore` の後。(3) ジャーナルの取り込みで削除・忘れるの行を当てたとき。(4) 書き込みの失敗の後に DB を開き直したとき (§6 の「失敗」)。
    - (1) のときは、さらに次を行う。索引を作り直す (前の世代の索引も)。新しい版のジャーナルに書く種類 (古い版が関係を作らずに取り込んだもの) の関係と副索引を、本体から作り直す。古い版が使う派生物 (v0.1 の索引 `index/memory/lex/` など) は、使わなければ消す (古い版は、戻したときに作り直す)。
    - **登録**: `job` として、`last_writer` を自分の版に書き換える (または restore を終える、開き直す) のと同じコミットで登録する。途中で止まっても、次の起動で続ける。
    - **終わるまで**: 想起 (05 §3.2・§3.4)・`/memory`・書き出し (§11) は、出典が DB に無い派生の記録を除いて扱う。`evorag export` は、突き合わせの job が残っていれば、先に済ませてから書き出す。

- **redb のファイル形式の版**: redb はメジャー版でファイル形式を変え、古い形式を読まなくなることがある。上の規則は封筒の層の約束で、redb の層では守れない。redb のメジャー版を上げるときは §12.2 の手順で移す (確定、[OQ-16](10-decisions.md#oq-16-redb-のメジャー版の上げ方))。

## 5. 索引とカートリッジのファイル

- 索引のファイルの形式は [05 §2](05-retrieval.md#2-索引)、カートリッジの形式は [14 §2](14-cartridge.md#2-形式-evocart) が正本。
- どちらもデータ根の下 (`index/`・`cartridges/`) に置き、記録の正本ではない。

## 6. 会話のジャーナル

会話のターンと明示の操作を、DB とは別の追記専用のファイルにも書く (確定、[ADR-0006](10-decisions.md#adr-0006-会話のジャーナルを先に書く))。

| 項目 | 内容 |
|---|---|
| 置き場所 | `journal/<年>-<月>.jsonl` (年と月は UTC) |
| 1 行 | `{"seq": <連番>, "op": <操作>, "env": <中身>, "sum": "<16 進の xxh3-64>"}` の 1 行の JSON。`sum` は最後の項目で、行の `,"sum":"…"}` を `}` に置き換えたバイト列 (書いたとおりのバイト列。読み直して書き直さない) を覆う |
| 操作 | `put` (`env` は封筒。形式は書き出し (§11) と同じ)、`delete` (`env` は `{"kind", "id"}`)、`meta` (`env` は `{"key", "value"}`。一度だけ書く `meta` の値、07 §6.1 のプロンプトの言語)、`forget` と `private` (v0.3)。知らない操作の行は、新しい版の行として読み飛ばして数え (壊れた行とは分ける)、連番だけは数に入れる |
| 書く物 | `turn`、`session`、`signal`、`setting` (v0.2 から答え方の既定を含む)、v0.2 から `model_binding` と `recall_feedback` と、明示の操作 (削除・忘れる・private)。忘れる・削除の操作の行は対象の ID だけを持ち、本文を含めない。`threshold` は書かない (同梱の事例から求め直せる。DB を失って戻したときに無ければ、`evorag setup` で求め直す、05 §3.5 の `no_threshold`) |
| 順序 | 書き手スレッドは、DB のトランザクションで操作を当てて規則 (§4.2 の規則 6 など) を確かめてから、**ジャーナルに書いて書き切り**、`journal.last_seq` を同じトランザクションで進めてコミットする (先書き)。規則で断られた操作はジャーナルにも書かない。連番は単調に増える |
| 突き合わせ | DB の `meta` に、取り込んだ最後の連番を持つ。起動時に、ジャーナルの末尾と比べ、DB に無い分を冪等に取り込む。忘れる・削除で行を抜くので連番の欠けは許し、`journal.last_seq` より大きい行を取り込む。取り込みは通常の書き込みと同じ規則で当てる (新しい `v` の記録と読めない記録は上書きしない)。関係と副索引は封筒から作り直し、上書きする記録から作ったものは消す。DB を読むだけで開いているときは、取り込まず、ジャーナルにも書かない |
| 失敗 | ジャーナルへの書き込みに失敗したら DB にも書かず、画面に知らせる (発話は入力欄に戻す)。追記が途中で失敗したら、ファイルを追記の前の長さに戻す。ジャーナルにだけある状態は許し、DB にだけある状態を作らない。ジャーナルに書いた後で DB のコミットに失敗したら、それ以後の書き込みを止め、DB を開き直して取り込み直す (§3.4) |
| 削除と忘れる | 削除と忘れるの操作の行を先に書き (順序の行のとおり)、DB をコミットした後に、**書き手スレッドがすぐに**、ファイルから対象の ID の `put` の行を除いた新しいファイルを書き、書き切ってから入れ替える (一時名 → rename、Unix ではフォルダも書き切る)。除く前に止まったときは、起動時に、削除の行がある ID の `put` の行を除く |
| 壊れた行 | チェックサムが合わない行は読み飛ばして数え、`doctor` が報告する。ファイルの最後の行が改行で終わらないとき (書きかけ) だけ、起動時にその行を切り詰める (すべてのファイルについて)。読めない行を切り詰めの理由にしない (新しい形式の行を消さないため) |

- 書き切る手順: Windows は `FlushFileBuffers` (書き込みの権限のあるハンドルが要る。読み取り専用のハンドルでは拒否される)、Linux は `fdatasync`、macOS は `F_FULLFSYNC` (失敗したら `fsync`)。
- 入れ替えの rename: Windows では `MoveFileExW` に `MOVEFILE_WRITE_THROUGH` を付ける (std の `fs::rename` は付けない)。Windows にはフォルダの書き切りが無いので、この旗で代える。Unix では rename の後にフォルダを書き切る。

## 7. 退避

### 7.1 自動の退避

- 1 日 1 回まで、DB の一貫した写しを `backups/daily/` に作る (確定、[ADR-0007](10-decisions.md#adr-0007-自動の退避))。v0.1 は起動時と終了時の空き時間に作る。v0.2 はそれに加えて、日をまたいで動き続けているときは sleep-time の手順として作る (短い利用でも 1 日 1 回の退避を欠かさないため、起動時と終了時の分は残す)。
- **写し方は論理的な写し**: 読み取りのトランザクションを 1 つ開き、すべての表を新しい redb のファイルに写す。一時名に書いて書き切り、rename する。ファイルのバイト列をそのまま写さない (書き手のコミットと競合して一貫しない恐れがあるため、[OQ-15](10-decisions.md#oq-15-退避の方式))。
- 退避の `meta` に、含む最後のジャーナルの連番を書く。`restore` はこの連番より後の行だけを足す。
- 10 万件 (各 1 KB) の論理的な写しは、書き手が止まっていれば 1.2〜1.4 秒、書き手がコミットを続けている間でも 7.0〜11.8 秒で、写しは写し始めの時点と一致した (S-01)。退避の前に、元の DB の大きさ以上の空きがあることを確かめる。
- 保持: 日次 7 世代と週次 4 世代 (週の最初の日次を週次に残す)。
- 退避の置き場所は設定 `storage.backup_dir` で変えられる (別のディスクを勧める)。§2.2 の検査を同じく当てる。

### 7.2 移行と作り直しの前の退避

- DB の形式の移行 (§12)、`rebuild`、`repair`、`restore` の前には必ず退避を作る (`backups/pre-op/<日時>-<操作>-v<版>/`)。中身は DB の写しと `config.toml`。新しいものから 3 世代を残す。
- 本体の更新で移行が要るときも、この形の退避を作る (12 §7)。

### 7.3 忘れる・削除と退避

- 削除と忘れるの操作をしたら、保持している退避のうち対象の記録を含むものを、対象を除いて写し直す (確定 (ユーザー回答)、[OQ-09](10-decisions.md#oq-09-忘れるの約束の範囲))。v0.1 で対象になるのはセッションの削除だけ。
- 除く対象には、消した記録の ID だけでなく、そこから派生した記録 (チャンク・ノート・埋め込みとその blob・想起への操作) の ID も入れる (v0.2 から)。退避の表のキーは派生の記録の自分の ID なので、出典の ID だけでは除けないため。§4.2 の規則 12 の突き合わせで消した ID も同じく除く。
- 写し直しは書き手スレッドの依頼として行い、終わるまで状態の行に「退避を整理中」と出す。終わる前に強制終了しても、起動時に続きを行う (job)。
- `evorag backups purge` で、退避をすべて消せる (v0.3)。

## 8. 破損への対策

| 起きうること | 対策 |
|---|---|
| 強制終了・電源断 | redb のトランザクションで書きかけを残さない。会話の追記は先にジャーナルに書き切り、DB も書き切る (§3.4、§6) |
| DB のファイルの破損 | 起動時に開けなければ、そのファイルを `broken/<日時>/` へ移し (消さない)、最新の退避とジャーナルから戻すかを尋ねる |
| 記録 1 件の破損 | 派生の種類 (チャンク・ノート・埋め込み・`model_probe`) の壊れた記録は、`quarantine` へ移さずに消して作り直す (本体を読めないと出典が分からず、削除が届かないため。作り直せるので失うものは無い)。それ以外の種類で封筒のチェックサムが合わない記録は、1 度読み直して確かめてから、消さずに `quarantine` へ移して数え、他の記録はそのまま使う。ジャーナルにある種類は、ジャーナルから戻す (§6)。チェックサムが合っていて読めない記録 (知らない配置・新しい形) は、新しい版の記録として読み飛ばして数える (隔離しない)。読むだけで開いているときは移さず、数えるだけにする |
| 索引のファイルの破損 | ヘッダのハッシュが合わなければ、そのセグメントを捨てて作り直す。その間は残りの索引で答える (05 §2.3) |
| 派生データの誤り | `evorag rebuild` で、会話の本文と明示の操作から作り直す (v0.2) |
| ディスクの空き不足 | 起動時と、移行・作り直し・退避の前に空きを確かめる。足りなければ裏の処理を止めて知らせ、会話の追記だけ続ける。会話の追記のために、データ根に予備のファイル (既定 16 MiB) を確保しておく。空きが尽きたら (redb の `StorageFull`、ジャーナルの書き込みの失敗)、予備のファイルを消し、DB を開き直してから書く |
| 危ない置き場所 | §2.2 |
| 2 つの evorag が同じデータ根を開く | §9 |
| 古い版への巻き戻し | §4 の規則 6 と、12 §7 の巻き戻し |
| 利用者の誤操作 | 消す前に確認する。確認の文言で、消える範囲と、退避からも消えることを示す |

- `broken/` と `quarantine` は、evorag が自動で消すことはない。忘れる・削除の操作は `quarantine` の対象の記録にも当て、`broken/` にファイルがあるときは、消すかを尋ねる (04 §7)。
- redb の空きページに消した記録が残るので、削除と忘れるの後の次の起動時に compact する。

## 9. ロックと同時に動くコマンド

- データ根の `lock` ファイルに、プロセスが生きている間ずっと OS のロックを持つ。std の `File::try_lock` (Rust 1.89 で安定。Windows は `LockFileEx`、Unix は `flock`) を使い、取れないときは `TryLockError::WouldBlock` で見分ける。強制終了するとロックはすぐに外れる (S-01)。ファイルがあるかどうかでは判定しないので、異常終了の後に残ったファイルで誤判定しない。
- Windows のロックは強制ロックで、ロックを持たれたファイルは他のプロセスから読めない。そのため、動いている evorag の PID はロックのファイルとは別のファイル (`lock.pid`) に書く。
- redb も DB のファイルをロックし、2 つ目の open (読み取り専用を含む) は `DatabaseAlreadyOpen` で失敗する。
- どちらのロックが取れなくても、理由 (分かれば PID) を示して終了コード 2 で終わる。
- ネットワークのファイルシステムではロックが効かないことがある。§2.2 の拒否の理由の 1 つでもある。

| コマンド | TUI が動いているとき |
|---|---|
| `evorag --version`、`evorag setup` (設定だけを書く) | 動く |
| `evorag setup` (モデルの記録を書き換える・点検の結果やしきい値を書く、06 §3.2) | 設定だけを書き、DB に書く部分は TUI を閉じてから実行するよう案内する |
| `evorag doctor`、`export`、`restore`、`repair`、`rebuild`、`backups`、`reset`、`import`、`update apply` | 理由を示して断る (TUI を閉じてから実行する) |

## 10. 点検と復元のコマンド

| コマンド | 内容 | 版 |
|---|---|---|
| `evorag doctor` | 設定・接続・データ根・索引の状態を、読むだけで点検する。v0.2 から、モデルの記録と繋がっているモデル、点検の結果 (06 §3.3)、しきい値の版、想起の縮退の状態、残っている job (作り直し・突き合わせ) も示す。`--deep` で全記録のチェックサム、関係の参照先、副索引と記録の食い違い、DB とジャーナルの食い違い、出典の無い派生の記録 (§4.2 の規則 12) を調べる | v0.1 (`--deep` は Should。v0.2 に繰り越し) |
| `evorag restore <退避>` | 退避から戻し、その後の会話をジャーナルから足す。実行前に今の DB を退避する。退避の後にした忘れる・削除の操作は、ジャーナルの操作の行から必ず当て直す | v0.1 |
| `evorag rebuild [--index]` | 派生データ (チャンク・ノート・事実・埋め込み・索引・点検の結果) を、会話の本文と明示の操作から作り直す。`--index` は索引だけ。実行前に退避する。チャンクと語彙の索引はその場で作り、埋め込みとノートは job として登録して、次に TUI を開いたときの裏の処理で進める (LLM のサーバを使うため)。正本 (モデルの記録・しきい値・想起への操作) は作り直さない | v0.2 |
| `evorag repair` | 副索引と関係を記録から作り直し、ジャーナルにあって DB に無いターンを戻す。実行前に退避する | v0.3 |
| `evorag backups list` / `purge` | 退避の一覧と削除 | v0.1 (list は Should) / v0.3 (purge) |
| `evorag reset` | データ根を消す (確認あり。設定は残す) | v0.1 (Should。v0.2 に繰り越し) |

## 11. 書き出しの形式

- `evorag export <出力先>` は、記録を種類ごとに 1 ファイルの JSON Lines で書き出す (`<kind>.jsonl`)。各行は封筒 (`body` は JSON に写す) で、ファイルの先頭の行に形式名 `evorag-export` と形式の版を書く。
- 封筒の知らない項目は、同じ名前の項目として写す (§4.2 の規則 7)。読むときは、既知の項目以外を知らない項目として保つ。
- JSON にそのまま写せない CBOR の値 (バイト列、タグ、±2^53 を超える整数、NaN と無限大、文字列でない map のキー) は、その値の CBOR を base64 にした `{"$cbor": "<base64>"}` で写し、読むときに元の CBOR に戻す (知らない項目を元の形のまま運ぶため)。ジャーナルの行の `env` も同じ規則で写す。
- 書き出しに含めるもの: v0.1 は会話 (`session`・`turn`)・信号・設定。v0.2 からモデルの記録 (`model_binding`)・しきい値 (`threshold`)・想起への操作 (`recall_feedback`)・ノートも含める (OQ-37 の 9)。v0.3 以降は事実、v0.4 以降は precept・回帰台帳の事例・提案と判定も含める。カートリッジは `.evocart` のまま同梱する (v0.5)。
- 書き出しに含めないもの: 索引、チャンク、埋め込みのベクトル、点検の結果 (`model_probe`)、`quarantine`、API キー (どれも作り直せるか、外に出さないもの)。出典が DB に無い派生の記録 (§4.2 の規則 12) も含めない。
- 書き出しのファイルは所有者だけの権限で作る。
- `evorag import <書き出し>` は、空のデータ根へだけ取り込む (v0.6)。

## 12. 移行

### 12.1 DB の形式の版

- `meta` の DB の形式の版が、今の evorag が書く形式の版より古ければ、起動時に §7.2 の退避を作ってから移行する。移行に失敗したら、元の DB のまま (読むだけで) 起動し、理由を示す。
- 移行は新しいファイルに書き、`migration.state` を `in_progress:…` にしておく。終えてから `none` にし、件数とチェックサムを突き合わせて入れ替える。起動時に `in_progress` のファイルが残っていれば、それを捨てて元から移行し直す。
- 移行の関数は版ごとに 1 つずつ持ち、順に当てる。移行の試験は、各版の DB の見本から今の版まで当てて行う。
- v0.1〜v0.4 の間 (§4.1) は、移行の関数を直前の版の分だけ持てばよい。v0.5 では、v0.4 の形式から形式の版 `1` への移行を持つ。
- **v0.1 から v0.2** (形式の版 `0.1` → `0.2`): 種類と任意の項目を足すだけなので、記録は書き換えない。`format.version` を `0.2` にし、`format.min_read` と `format.min_write` は `0.1` のままにする (v0.1.2 に戻しても、読み書きできる。新しい種類は v0.1.2 が読み飛ばして残す)。移行の前に §7.2 の退避を作る。移行の後は、`last_writer` が 0.1.x なので、§4.2 の規則 12 の (1) と同じ扱いになる。次を、`last_writer` を書き換えるのと同じコミットで job として登録する。
  1. v0.1 の索引 (`index/memory/lex/`) を消し、チャンクを作って `chunk-lex/` を作る (05 §2.3)。
  2. 埋め込みとノートを作る (裏の処理、04 §4)。進み具合を状態の行に出す。
  - モデルの記録は、job ではなく、起動時の照合 (06 §3.1) で行う (記録が無いので、繋がっているモデルを記録する)。
- 移行は、表の構成ごと作り直すときも、記録を 1 件ずつ論理的に写して件数とチェックサムを突き合わせてから入れ替える (§12.2 と同じ手順)。ジャーナルの形式を変えるときは、古いジャーナルを新しい形式で書き直してから入れ替える。

### 12.2 redb のメジャー版を上げるとき

1. 新しい evorag は、古い redb の形式を読む手段 (古い版の redb を別名で依存に持つ、または書き出しを経由する) を 1 つの版の間だけ持つ。
2. 起動時に §7.2 の退避を作り、古い形式から新しい形式のファイルへ、すべての記録を論理的に写す。
3. 写した後に、記録の件数とチェックサムを突き合わせてから入れ替える。

手段の選択は OQ-16。

### 12.3 設定の版

- `config.toml` は `version` のキーを持ち、版ごとの移行の関数で書き換える。書き換える前に元のファイルを `config.toml.bak-v<旧版>` に写す (07 §4)。

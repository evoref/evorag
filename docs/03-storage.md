## 1. DB の使い方

- **DB サーバは使わない**。埋め込み型の DB の redb (純 Rust、ACID、1 つの書き手と MVCC の読み手) を 1 ファイルで使う。SQL は使わない (確定、[ADR-0004](10-decisions.md#adr-0004-記録の正本は-redb-の汎用の表))。
- **記録の正本は `evorag.redb` だけ**。会話、信号、利用者の指示、設定、モデルの記録、区切りと台帳と単位 (v0.5)、埋め込み、学習の記録 (v0.7)、カートリッジの台帳 (v0.9) を入れる (v0.4 まではノート・事実・訂正も)。
- **索引は派生物**。`evorag.redb` とカートリッジから作り直せるファイルとして別に置き、壊れたら消して作り直す (05 §2)。
- **カートリッジの中身はファイル**。導入した版ごとのフォルダに読み取り専用で置く (14)。

## 2. 置き場所

### 2.1 フォルダ

置き場所は OS ごとに環境変数から解決し (Windows は `LOCALAPPDATA`、Linux は `XDG_CONFIG_HOME`・`XDG_DATA_HOME` (無ければ `HOME` の下の既定)、macOS は `HOME`)、`--data-root` (と設定 `storage.data_root`) で変えられる (確定、[OQ-17](10-decisions.md#oq-17-置き場所))。`directories` crate は、依存に MPL-2.0 の crate を含むので使わない (12 §2)。

| 区分 | 中身 | Windows | Linux | macOS |
|---|---|---|---|---|
| 設定 | `config.toml` | `%LOCALAPPDATA%\evorag\config\` | `~/.config/evorag/` | `~/Library/Application Support/evorag/config/` |
| データ根 | `evorag.redb`、`journal/`、`index/`、`cartridges/`、`backups/`、`broken/`、`lock` | `%LOCALAPPDATA%\evorag\data\` | `~/.local/share/evorag/` | `~/Library/Application Support/evorag/data/` |
| 状態 | `logs/`、`update/` (更新のロックと状態のファイル、12 §7.2・§7.3。取得したものは主記憶で扱い、ここには置かない) | `%LOCALAPPDATA%\evorag\state\` | `~/.local/state/evorag/` | `~/Library/Logs/evorag/` (logs)、`~/Library/Application Support/evorag/state/update/` (update。`Caches` は OS に消されることがあり、状態のファイルを失うと巻き戻しの記録が無くなるため) |

- Windows で Roaming (`%APPDATA%`) を使わない。移動プロファイルで同期され、§2.2 の「危ない置き場所」に自分から当たるため。
- macOS では設定とデータ根を別の下位フォルダにする。`evorag reset` (データ根を消し、設定は残す) が設定まで消さないようにするため。
- 状態のフォルダは、Linux は `XDG_STATE_HOME` (無ければ `~/.local/state`)、Windows と macOS は上の表の場所を使う。
- 作るフォルダとファイルは、ほかの一般の利用者が読み書きできない権限にする (Windows は所有者・SYSTEM・Administrators だけの ACL、Unix は 0700 / 0600、NFR-503)。
  - Windows は、今の利用者・SYSTEM (`S-1-5-18`)・Administrators (`S-1-5-32-544`) の 3 つだけを許す ACE を持つ、継承を切った DACL を付ける。Windows の慣例 (`%LOCALAPPDATA%` の既定、OpenSSH が秘密鍵に求める権限) と同じ。フォルダは evorag が新しく作ったときだけ付け (中へ継承させる)、既にあったフォルダ (`--data-root` で指した既存のフォルダなど) は変えない (継承を切ると、その下のすべての権限が変わるため)。ファイルは書くたびに付ける。
  - ネットワークの置き場所 (相手の側では SID が別のアカウントになり、作った本人が開けなくなるおそれ) と、ACL を持たないファイルシステム (FAT・exFAT) には付けない。FAT・exFAT の警告 (§2.2) には、所有者だけの権限が付かないことも含める。
  - SYSTEM と Administrators を残す理由: 管理者は所有権を取れば読めるので、外しても守れない。外すと、SYSTEM の権限で動く退避のソフトが読めなくなり、利用者のアカウントの SID が変わったとき (PC の移行・アカウントの付け替え) に管理者の画面操作で戻せなくなる。守る相手は、同じ PC の別の一般の利用者である (02 §8)。

### 2.2 危ない置き場所

データ根と退避先の両方について、起動時に次を調べ、当たれば既定で起動を拒否する (設定 `storage.allow_unsafe_location = true` で警告だけにできる)。同期による書き換え・ロックの無効化で壊れやすいため。

| OS | 調べること |
|---|---|
| Windows | ドライブの種類 (ネットワーク)、UNC パス、クラウドファイルの属性・リパースポイント (OneDrive、既知フォルダの移動を含む)。ファイルシステムが FAT / exFAT のときは警告だけを出す (拒否はしない。S-01 の試験は exFAT でも合格したが、ジャーナリングを持たず、電源断に弱いため) |
| Linux | `statfs` のファイルシステムの種類 (NFS、CIFS/SMB、FUSE の同期) |
| macOS | ボリュームの種類 (ネットワーク)、iCloud Drive の下か |

- 判定は経験則で、漏れはありうる。README に「同期フォルダに置かない」と書く。

## 3. `evorag.redb` の構成

### 3.1 表

用途ごとの専用の表は作らず、少数の汎用の表に「種類」を付けた記録を入れる。機能を足すときは、表を増やさずに種類を増やす (確定 (ユーザー回答、2026-11-08))。

| 表 | キー → 値 | 中身 |
|---|---|---|
| `meta` | 文字列 → 文字列 | §3.1.1 のキー。DB の形式の版、データ根の ID、書いた evorag の版、ジャーナルの最後に取り込んだ連番、プロンプトの言語など |
| `records` | (kind, id) → 封筒 | すべての記録 |
| `links` | (from, rel, to) → 属性 | 記録どうしの関係。逆引き用に (to, rel⁻¹, from) も同じトランザクションで書く |
| `lookup` | (kind, field, 値, id) → () | 探すための副索引 |
| `blobs` | (id, part) → バイト列 | 大きなデータ (埋め込みのベクトル、長い本文) |

#### 3.1.1 `meta` のキー

キーと値の意味は v0.1 から変えない (08 §2.2)。キーは足すだけにする。値はすべて UTF-8 の文字列。

| キー | 値 |
|---|---|
| `format.version` | この DB の形式の版 (`0.<n>`、v0.8 の凍結から `1`、`2` …。§4.1)。版は `.` で区切った整数の並びとして比べる (文字列として比べない)。v0.1〜v0.4 の書く版は `0.1`〜`0.3` (v0.4 は v0.3 の形式のまま)、v0.5 の新しい根は `0.5` (§12.4) |
| `format.min_read` | この DB を読むだけで開くのに要る、evorag が知る形式の版の下限 |
| `format.min_write` | この DB に書くのに要る、evorag が知る形式の版の下限。足すだけの変更なら `format.version` だけを上げ、`min_write` を据え置いて古い版の書き込みを許せる |
| `key_encoding.version` | キーの符号化 (§3.3) の版 (`1`) |
| `data_root.id` | データ根の ID (UUID v7)。作ったときに 1 度だけ書く |
| `created_by` | DB を作った evorag の版 (semver) |
| `last_writer` | 最後に書き込みで開いた evorag の版 |
| `max_writer` | これまで書き込みで開いた evorag の版の最大。単調に増やす。自分の版より大きければ、巻き戻しとして扱う (§4.2 の規則 6、12 §7) |
| `writer.<semver>` | その版が最初に書き込みで開いた時刻 (UTC、ミリ秒)。書いた版の履歴 |
| `migration.state` | `none`、または `in_progress:<元の版>:<先の版>:<段>`。移行先のファイルに書き、移行を終えてから `none` にして入れ替える (§12.1) |
| `journal.last_seq` | ジャーナルから取り込んだ最後の連番 (§6) |
| `cleanup.pending_deletes` | 開くときにジャーナルの削除の行で消した ID のうち、まだ整理の job (§7.3、04 §7.7 の 2) にしていないもの (空白区切り)。消すのと同じトランザクションで足し、コアが job を書くのと同じ依頼で消す (v0.3) |
| `forget.recheck` | すべての忘れるの指示について、退避の写し直しの job (`forget_backups`) を作り直し、指示の副索引を作り直す (§4.2 の規則 12 の (1)) ことが要る印 (値は `1`)。restore が戻した DB に書くとき、`repair` が忘れるの指示のあるデータ根を直したとき (ストアの層と同じコミット。失った DB にあった job を取り戻すため)、`last_writer` が 0.3.0 より古いデータ根を書き込みで開いたとき (`last_writer` を書くのと同じコミット) に書く。コアが job を書き、忘れるの当て直し (04 §7.2) を `memory.forget_key` で済ませた後に消す (鍵が使えない・当て直しの書き込みに失敗したときは消さない。立っている間は書き出しを断るため、§11)。上書きしてよいキーで、ジャーナルには書かない (v0.3) |
| `compact.pending` | 次の起動で compact が要ること (値は `1`)。削除・忘れる (04 §7.2)、忘れるの当て直し、開くときのジャーナルの削除の行 (§6)、規則 12 の突き合わせで記録を消した・書き換えたときに、そのコミットで書く。`last_writer` が 0.3.0 より古いデータ根を v0.3 が開いたときも書く。compact を終えた後に消す (§8)。`cleanup.pending_deletes` と同じく、書き換えてよいキー (一度だけ書くキーではない) で、ジャーナルには書かない。無い・知らない値は「要らない」として読む (v0.3) |
| `prompt.language` | プロンプトの言語 (07 §6.1)。一度書いたら変えない。`import-v04` は古い根の値を写す (§12.4) |
| `import.source` | (v0.5) `import-v04` で作った根だけが持つ。取り込み元のデータ根の ID (`data_root.id`)・取り込んだときの古い根のパス (入れ替えの後のパス)・取り込んだ時刻と evorag の版・取り込んだときの古い根の `journal.last_seq` とファイルの要約 (§12.4 の照合の (4) で取ったファイルの一覧の大きさ・更新時刻・SHA-256 をまとめたハッシュ) を、1 つの JSON の文字列で書く。一度だけ書く (ジャーナルにも `meta` の行として書く)。古い根の処分の前に、今の古い根と比べる (§10.2) |
| `import.report` | (v0.5) 取り込みの照合の結果 (§12.4 の「照合」: 種類ごとの件数とハッシュ、除いたものの件数と理由)。JSON の文字列。一度だけ書く (ジャーナルには書かない。`doctor` が示す) |
| `import.v04_ended` | (v0.5) `import-v04` で作った根だけが持つ。v0.4 で今の値でなかった値の表 (主語・属性・値の鍵と照合の鍵の 16 進・出典の最も新しいターンの ID。値の文字列は持たない) と、取り込んだターンの区切りの台帳がそろって照らし終えたかの印を、1 つの JSON の文字列で書く。導出のたびにこの表で `end` を足す (§12.4、04 §7.4)。照らし終えた印だけは書き換えてよい。ジャーナルにも `meta` の行として書く (連番の最も大きい行の値を採る) |
| `import.old_root` | (v0.5) 古い根の処分の状態: `kept` (取り込みの後、まだ残っている) か `disposed:<UTC の時刻>`。`import-v04` が入れ替えと同じ手順で `kept` を書き、`evorag reset --old` (§10) が古い根を消し終えたコミットで `disposed:…` にする。忘れるとセッションの削除の確認 (07 §3 の `/forget`・`/delete`) がこのキーを見る。上書きしてよいキーで、ジャーナルにも `meta` の行として書く (DB を失って戻したときに、処分を求め直さずに済むため)。ジャーナルの `meta` の行は一度だけ書く値の扱いが原則 (§6) だが、このキーだけは、取り込みと `repair` で、連番の最も大きい行の値を採る (`disposed` を `kept` に戻さない。値が `disposed` の行が 1 つでもあれば `disposed` とする) |
| `memory.derive_fingerprint` | (v0.5) 今の単位を作った導出の指紋と、起動時の軽い検査に使う成分 (形と成分の正本は 04 §5.3)。単位と同じトランザクションで書く。起動時に今の入力から求めた指紋と合わなければ、全件を導き直す。上書きしてよいキーで、ジャーナルには書かない (派生) |
| `memory.forget_key` | 値の鍵と再び覚えない印 (04 §5.6・§7.6) を作る HMAC の鍵 (OS の乱数で作った 32 バイトを、ちょうど 64 桁の小文字の 16 進で書く。HMAC には 16 進を復号した 32 バイトを使う)。変えない。ジャーナルにも一度だけ書く `meta` の行として書く (§6)。<br>**作る時機**: v0.3 が書き込みでデータ根を開いたとき (ジャーナルの取り込みの後、裏の処理の前)。会話と同じ優先度と `Immediate` で書く (裏の処理の書き込みと `/forget` が別々に作って食い違うのを防ぐため)。<br>**探し方**: DB に無ければ、作る前に、ジャーナルのすべての `meta` の行を `journal.last_seq` に関わらず探し、あればそれを入れる (v0.2.x は、この `meta` の行を取り込まずに連番だけを進めるので、v0.2.x で開いた後は、連番での取り込みでは二度と入らないため)。<br>**フェイルクローズ**: DB とジャーナルのどちらにも無いのに `fact_directive` の記録 (v0.5 の根では `directive` の記録) があるとき、またはジャーナルの値と DB の値が違うときは、鍵を作らず、書き換えない。事実の抽出・統合・事実の表 (v0.5 では、区切りの呼び出し・導出・プロファイル) を止め、`doctor` と状態の行で知らせる (別の鍵で作ると、private と再び覚えない印が黙って効かなくなるため)。<br>**v0.5 の取り込み**: `import-v04` は古い根の鍵をそのまま写す (新しく作らない。写した `directive` の値の鍵が同じ鍵で作られているため、§12.4)。新しい根を作るときは、DB とジャーナルの両方に、ほかの記録より先に書く |

### 3.2 封筒

すべての記録の共通の形。`records` の値は、次のバイト列にする。

| 位置 | 内容 |
|---|---|
| 先頭の 1 バイト | 値の配置の版 (`1`)。知らない値なら、新しい版の記録として読むだけにして数える (quarantine に移さない) |
| 続く 8 バイト | チェックサム。xxh3-64 (リトルエンディアン) で、**表のキーと、続く封筒の CBOR のバイト列そのもの** を覆う。符号化し直したものではなく、保存したバイト列を覆うので、知らない項目と `writer` も含めて、どのバイトの破損も見つかる。読むたびに、復号の前に確かめる |
| 残り | 封筒の CBOR (項目名つきの map) |

封筒の項目は次のとおり。

| 項目 | 内容 |
|---|---|
| `id` | 記録の ID (キーと同じ値。読むときにキーと突き合わせる) |
| `kind` | 種類の名前 (§3.3) |
| `v` | その種類の形式の版 (整数) |
| `created_at` / `updated_at` | 作成と更新の時刻 (UTC、ミリ秒) |
| `writer` | 書いた evorag の版 |
| `body` | 本体。項目名つきの CBOR (確定、[ADR-0005](10-decisions.md#adr-0005-記録の本体は項目名つきの-cbor)) |
| (知らない項目) | 読み手が知らない封筒の項目。保存上の項目名は持たず、読み手はまとめて保持し、書き戻すときに同じ名前のまま残す (§4.2 の規則 7)。本体の読み方を変える封筒の項目 (圧縮・暗号化など) は、`format.min_write` を上げて足す |

- 書き出し (§11) とジャーナル (§6) の行には、封筒の項目だけを JSON で写す。チェックサムは写さず、行の `sum` で代える。

### 3.3 種類

| 種類 | 中身 | 主な関係 (links) と副索引 (lookup) | 版 |
|---|---|---|---|
| `session` | 題名、モード、状態 | 更新時刻の順 | v0.1 |
| `turn` | 本文、役割 (利用者 / 応答 / システム)、状態 (確定 / 応答待ち / 完了 / 中断 / 失敗)、model_key、生成の設定、添えたものの ID、判定点。v0.2 から任意の項目 `obs` (観測値、05 §3.6)。v0.3 から任意の項目として、改訂の番号 (伏せ字のたびに上げる、04 §7.3) と、`obs` に貼り付けで入った範囲と見分けが効いていたか (04 §5.2)・事実の表の版 (v0.3〜v0.4。v0.5 の根ではプロファイルの版 `profile`、04 §5.4・05 §3.6)。v0.5 から `obs` に、1 回の読み取りで届いた長い入力の範囲 (04 §5.2)。v0.4 から `obs` に、応答のターンの候補・詰めた窓・問いの分析・先読みの当たり・言い直しの対・版と、発話のターンの UTC からのずれ・前の発話からの時間・起動したときに残っていた裏の処理の手順 (05 §3.6)。`v` は上げず、形式の版も変えない (任意の項目を足すだけ) | セッションへ、添えたメモリへ | v0.1 |

- **v0.2 で足す種類の、知らない値の読み方** (§4.2 の規則 11): `model_binding` の知らない役割、`threshold` の知らない対象の種類は、読んで残し、使わない。`recall_feedback` の知らない操作は、読んで残し、較正 (v0.4) に使わない。`setting` の答え方の既定の知らない値は `auto` として扱う (07 §3)。どれも、読めない記録として数えない。v0.1.2 から見ると、v0.2 の種類はどれも知らない種類なので、読み飛ばして残す (規則 6)。
- **v0.1 の種類の `v` を上げない**: v0.2 は `turn`・`session`・`signal`・`job` の `v` を 1 のままにする。v0.1.2 は、`v` の新しい記録がある種類の記録を新しく作らない (規則 6) ので、上げると v0.1.2 に戻したときにセッションの削除 (`job` を書く) などが断られるため。
  - `turn` の `obs` は、既存の項目とつながらない任意の項目なので、規則 1 の「`v` を上げる」に当たらない。
  - `job` は `task` (文字列) と `ids` の形を保ち、新しい手順は `task` の新しい値で表す (v0.3 の忘れるの退避の写し直しは `forget_backups`。忘れるの指示の ID を任意の項目 `directive` に持ち、`ids` は除く ID だけにする、§7.3)。足す項目 (手順の版、model_key) は任意にする。
- **`turn` の `obs`**: 観測値はすべて任意の項目にし、本体の最上位の 1 つの map (`obs`) にまとめる。判定点 (`recall`) の中には足さない (古い版が判定点を書き戻すときに、知らない項目を落とさないため。§4.2 の規則 7 は本体の最上位の項目を残す)。縮退の理由のように値が増えうるものは、列挙ではなく文字列で持つ。
- **1 件だけのはずの記録**: `model_binding` (役割ごとに 1 件) と `setting` (項目ごとに 1 件) が、ジャーナルからの取り込みなどで 2 件以上になったときは、`updated_at` の新しいものを採り、ほかを消す (消すときはジャーナルにも削除の行を書く)。
- **派生の記録の出典**: `chunk`・`note`・`embedding`・`recall_feedback` と、v0.3 から `fact`・`correction` は、出典の記録の ID を本体に持つ。v0.3 から、ターンから作る派生の記録 (`chunk`・`note`・`embedding`・`fact`・`correction`) は、作ったときの出典のターンの改訂の番号を任意の項目 `src_rev` に持つ (`fact` と `correction` は、出典ごとの `rev` で持ち、`src_rev` を置かない、04 §5.1・§6。複数のターンを出典とする `note` は、v0.3 から出典ごとの改訂の番号 `src_revs` (`[{turn, rev}]`。往復の発話と応答の両方) を持つ、04 §7.7 の 4。`src_revs` の無いノートは、どの出典も 0 とみなす。ノートは v0.3 から、入力を読んだときに見えていた最新の忘れるの指示の ID `forgets_seen` (無ければ null) も持つ (04 §7.5)。合わなければ古いノートとして作り直すだけで、古い版が `src_revs` を書かずに作ったノートも安全の側に倒れるので、`note` の `v` は上げない (§4.2 の規則 1 の「つながる項目」に当たらない)。無ければ 0。伏せ字の後に古い本文から作ったものを見分けるため、04 §7.3) (関係だけに頼らない)。古い版は、ターンを消すときにそのターンへの関係も消すので、関係ではたどれなくなるため (§4.2 の規則 12)。
- **`threshold` とジャーナル**: v0.2 のしきい値は同梱の事例から求め直せるので、ジャーナルに書かない。利用者の信号で動かす学習は v0.7 (ADR-0021) なので、ジャーナルに書くかは v0.7 の M7.0 で決める。
- **v0.5 の種類の耐久性とジャーナル** (§3.4・§6。本節を耐久性の正本にする): `directive` は正本で、DB とジャーナルの 2 か所に持つ。`proposal` (台帳) は派生だが、区切りごとに `Immediate` で書き、退避と書き出しに含める (ジャーナルには書かない)。`segment` は、閉じた区切りと、台帳と同じトランザクションで書く分を `Immediate` で書き (閉じた区切りの境界を決め直すと、前のふるいの規則の版で動きうるため、04 §2)、開いている末尾の区切りは裏の処理の結果として `None` で書く (失っても往復から決め直せる)。`unit` と `memory.derive_fingerprint` は裏の処理の結果として `None` で書く (失っても指紋が合わなくなり、起動時に導き直す)。
- **台帳の本体の互換** (OQ-53、確定、2026-11-26): 台帳は失うと戻らないので、本体と `output` の型は v0.5.0 から「項目を足すだけ」にする (形式の凍結の v0.8 より前から)。列挙の値を足すのも「足すだけ」の変更に含める。読み手は寛容にし (書くときの型と読むときの型を分ける、04 §5.2)、知らない項目は残し (規則 7)、知らない列挙の値を持つ要素は、その要素だけを「型が合わない」として数えて導出に使わない (台帳の全体は読めない記録にしない)。`call` が `segment` 以外の台帳は、v0.5 では読み飛ばして残す。
- **v0.5 の派生の記録の出典**: `segment`・`proposal`・`unit` は、出典のターン (と改訂の番号) を本体に持つ (`segment` は往復のターン、`proposal` は `sentences`、`unit` は `anchors`)。台帳は、出典のターンの改訂の番号が合わなくなっても、それだけでは消さずに「有効でない台帳」として残す (使うかどうかは 04 §5.2.1 の有効性と選び方)。台帳を変える・消すのは、セッションの削除 (その区切りの台帳を消す)、忘れるの掃除 (04 §7.2。private では掃除しない)、末尾の区切りと `partial` の台帳の置き換え、04 §5.2.1 の「台帳を消すとき」の規則だけにする。
- ID は時刻順に並ぶ UUID v7 (RFC 9562)。同じミリ秒の中でも単調に増えるように生成する (`IdGen`、02 §6)。
- **中身から ID を作る種類** (v0.5): `segment` (04 §2) と `unit` (04 §5.1) の ID は中身のハッシュで、時刻の順に並ばない。下の `IdGen` の下限には入れない (入れると、下限が先の時刻に飛ぶため)。
- **プロセスをまたいでも単調にする** (v0.3): 書き込みでデータ根を開いたら、記録した ID の最大 (種類ごとの最後の記録の ID の最大。中身から ID を作る種類は除く) を `IdGen` の下限にし、それ以下の ID を出さない (時計が戻ったまま起動したとき、新しいターンの ID が前の ID より小さくなると、ID の順で進み具合を持つ手順 (04 §5.2.1 の抽出) が新しいターンを飛ばし続けるため)。下限を使うときは、時刻の部分を下限の時刻にし、乱数の部分で増やす。
- キーの符号化: キーを要素の並び (tuple) として、各要素の先頭に型の印 (1 バイト) を付け、順序を保つ符号で並べる。文字列とバイト列は `0x00` を `0x00 0xFF` に置き換え、終端に `0x00` を置く。整数と時刻は符号ビットを反転した 8 バイトのビッグエンディアン、ID は 16 バイト。これで、バイト列の辞書順の比較が意味の順と一致し、前方一致で走査できる。文字列の順は Unicode の code point の順で、正規化 (NFC など) は副索引の項目を定める側が決める。符号化は `evorag-store` の 1 か所に置き、版 (`key_encoding.version`) を持つ。

### 3.4 書き込みと耐久性

- 書き込みはすべて書き手スレッドの redb のトランザクションで行う (02 §5)。記録とその関係・副索引は同じトランザクションで書く。
- redb は 4.x に固定する (S-01 で確かめた版は 4.5.0。5.0 は開発中)。書き込みの並行の形は既定の 1 つの書き手 (`ExclusiveWriter`) にする (ほかの形では `Durability::None` を使えない)。
- **会話の追記と明示の操作**: コミットのたびにディスクへ書き切る `Durability::Immediate` で書く。S-01 で、1,000 回の強制終了と 1,000 回の電源断の模擬で、コミット済みの記録を 1 件も失わないことを確かめた (コミット 1 件は約 1〜2 ms)。
- **裏の処理の結果**: `Durability::None` でまとめて書き、区切りで `Immediate` のコミットを 1 回入れる。`None` のコミットは、電源断だけでなく **プロセスの強制終了でも失われる** (S-01)。失っても job から作り直せるものだけを `None` で書く。
- **台帳** (v0.5): 台帳 (`proposal`) は LLM を呼ばないと作り直せず、同じものが戻らないので、区切りの呼び出しが終わるごとに、その台帳 (と同じ区切りの `segment` の更新) を 1 つの `Immediate` のコミットで書く。台帳を置き換えるとき (末尾の区切り・`partial`) は、前の台帳を消すことも同じコミットに入れる (04 §5.2.1)。閉じた区切りの `segment` も、閉じたときに `Immediate` で書く。会話の追記より後に回す (書き手スレッドの裏の処理の待ち行列、02 §5) が、`None` のコミットにまとめない。導出の結果 (`unit`・`memory.derive_fingerprint`) は `None` でよい (失っても指紋で気付いて導き直す)。
- 強制終了の後の開き直しには修復が走る (S-01 で 60〜85 MB の DB で中央 46 ms、最大 287 ms。DB の大きさに比例する)。修復を速くする設定 (`quick_repair`。コミットは少し遅くなる) を使うかは、起動の時間 (BM-101) を測って決める。
- **発話は先に保存する**: 発話は LLM に送る前に `turn` (状態「応答待ち」) として確定する。応答は、完了・中断・失敗のいずれかを別のコミットで書く (04 §3)。
- redb は I/O のエラーの後、開き直すまで書き込みを受け付けない (`PreviousIo`)。書き込みのエラーを受けたら、それ以上書き込まずに DB を開き直す。開き直せなければ §8 の「DB の破損」として扱う。会話の追記はジャーナルに残っているので失わない。
- 型を知らずに表を写せるように (退避と移行、§7.1・§12)、すべての表のキーと値の型をバイト列 (`&[u8]` → `&[u8]`) にし、符号化は `evorag-store` の中で行う。

## 4. 後方互換の規則

後方互換を最優先にする (P6、確定 (ユーザー回答、2026-11-08))。

### 4.1 互換の起点 (v0.8)

データの互換は **v0.8 から** 約束する (確定 (ユーザー回答、2026-11-09)。2026-11-20 に起点を v0.5 から v0.8 に改めた、[ADR-0021](10-decisions.md#adr-0021-メモリの新エンジンを段階に分けて入れる) の決定 4、[OQ-24](10-decisions.md#oq-24-データの互換をいつから約束するか))。v0.5〜v0.7 でメモリの記録の種類を組み直すため。

| 期間 | 形式の扱い | 必ず守ること |
|---|---|---|
| v0.1〜v0.7 (形式を固める期間) | 表・キーの符号化・封筒・種類の本体・ジャーナル・書き出しの形を、より良い構成に変えてよい。形式の版は `0.<n>` と書く | 形式を変える版は、**直前の版のデータを必ず持ち込める** ようにする。原則は、直前の版のデータからの在り場所での移行で、移行の前に退避する (§7.2、§12)。**v0.5 だけは例外** で、在り場所で移行せず、v0.4 のデータ根から **新しいデータ根への取り込み** (`import-v04`、§12.4) で持ち込む (古い根に触らない)。下の規則 6 (新しい版のデータを壊さない) と規則 7 (知らない項目を消さない) は v0.1 から守る。版を飛ばして更新したときは、間の版を順に当てるか、理由を示して読むだけで開く (v0.5 は、v0.4 で一度開いた根だけを取り込む) |
| v0.5〜v0.7 の台帳 | 台帳 (`proposal`) の `output` の型は、v0.5.0 から「項目を足すだけ」にする (§3.3 の「台帳の本体の互換」、OQ-53) | 台帳は失うと LLM を呼ばないと戻らず、同じものが戻らないため、凍結の前から足すだけにする |
| v0.8 のリリースの前 | 保存の形式を見直して凍結する (08 §2.9 の M8.0。カートリッジとコーディングモードの種類・索引の置き場所・名前の予約を含め、PO が確認する)。v0.1〜v0.7 の間に分かった問題をここで直す | 凍結した形式を形式の版 `1` とし、golden fixture をこの版から固定する。v0.7 のデータ根から形式の版 `1` へ移行する |
| v0.8 以降 | 下の規則のすべてを守る | 形式の版 `1` 以降のすべての版を読める |

- v0.1〜v0.4 の利用者向けのリリースノートと README には、「形式は v0.5 まで変わることがあり、移行は直前の版から行う。版を飛ばさずに更新する」と書いた。v0.5〜v0.7 では「形式は v0.8 まで変わることがあり、直前の版から持ち込む。版を飛ばさずに更新する。v0.5 は v0.4 のデータ根から新しい根へ取り込む」と書く。

### 4.2 規則

0. **消した ID は使い直さない**: ジャーナルに削除の行のある ID は、どの種類でも、取り消しや作り直しで同じ ID のまま生き返らせない (新しい ID で作る)。古い版は、削除の行のある ID の記録を開くときに消すため (§6)。ID の下限は、消した ID の最大も含めて上げる。ただし単位 (`unit`) は、中身から ID を決める派生の種類なので、この規則の外にする (同じ中身を導き直せば同じ ID で作る。単位はジャーナルに書かないので、削除の行も持たない。04 §7.7 の 3、確定、2026-11-26)。
1. **足すだけ**: 項目は追加だけにする。名前の変更・削除・意味の変更はしない。足す項目には既定値を決め、その項目が無い古い記録は既定値で読む。**既存の項目とつながる項目 (派生の値など) を足すときは、その種類の `v` を上げる** (古い版がつながりを知らずに既存の項目だけを書き換えるのを、規則 6 で止めるため)。
2. **意味を変えるときは新しく作る**: 新しい項目か新しい種類を作り、古いものも読み続ける。
3. **項目名つきの符号**: 本体は項目名つきの CBOR にする。並び順で意味が決まる符号は使わない。
4. **古い版はすべて読める**: 種類ごとに、過去のすべての版 (形式の版 `1` 以降) の読み方をコードに残し、版ごとの固定の見本 (golden fixture、`tests/fixtures/<kind>/v<n>.cbor`) で試験する。書くときは今の版で書く。読んだ記録を書き直すときに新しい版になる。v0.1〜v0.7 の間は、今の版の見本だけを持ち、形式を変えたら見本も作り直してよい (§4.1)。ただし台帳 (`proposal`) の `output` は v0.5.0 から足すだけなので、v0.5.0 の見本を残し、後の版でも読めることを試験する。
5. **一括の移行は最後の手段**: 表の構成を変える移行は避ける。必要なときだけ、退避してから `meta` の DB の形式の版を上げて行う (§12)。
6. **新しい版のデータ**:
   - 知らない種類は読み飛ばして数え、消さない。
   - 知っている種類でも `v` が新しい記録は、その記録の更新を止めて読むだけにし、更新を案内する。その種類の新しい記録を今の `v` で作ってよいかは、種類ごとに決める (既定は作らない)。削除と、伏せ字にしないで忘れるは、本体を解釈せずにできるので、新しい `v` の記録にも行う。伏せ字は本文を解釈して書き換えるので、新しい `v` のターンを伏せ字にする忘れるは中止する (04 §7.1 の「中止」。伏せ字にしないで忘れることを勧める)。
   - `max_writer` (§3.1.1) が自分の版より新しいときは、巻き戻しとして知らせる (書き込みは上の規則に従う)。
   - DB の形式の版が新しければ、全体を読むだけで開く。
7. **知らない項目を消さない**: 封筒の知らない項目は、同じ名前のまま書き戻す。本体の知らない項目は本体の map の中にそのまま残す。書き戻すときは、今の版の本体を省略なしに書き (値の無い項目は null で書く)、元の本体のうち書いた項目に無い名前だけを足す。こうすると、消した既知の項目は戻らず、知らない項目だけが残る。
8. **保存の仕組みからの独立**: DB の操作は `evorag-store` の trait に閉じ込め、他の crate は redb を直接使わない (02 §4.3 の R2)。
9. **書き出しの形式を互換の拠り所にする**: `evorag export` は封筒をそのまま JSON Lines に書く。どの版の evorag も、自分より古い書き出しを読める。
10. **索引とカートリッジも同じ考え方**: どちらも形式名と版を持ち、古い版を読めるようにする。索引は作り直せるので、読めない版は捨てて作り直す。
11. **列挙の値と、本体を読めない記録** ([OQ-40](10-decisions.md#oq-40-古い版が新しい記録と設定を読めること)):
    - 既存の列挙 (ターンの役割と状態、判定点、信号の種類、セッションの状態など) に値を足さない。新しい区別は、任意の項目を足して表す (規則 1)。値を足せる列挙にするときは、知らない値の読み方 (既定の値で読むか、その記録を読めない記録として扱うか) を種類ごとに決めてから足す。
    - 封筒は読めるが、本体をこの版の型として読めない記録 (知らない列挙の値、型の違う項目) は、**読めない記録** として読み飛ばして数える。消さず、書き換えない。同じセッションのほかのターンは読み続け、読めなかった件数を画面に示す。
    - 本体から作り直す関係と副索引 (ジャーナルからの取り込みと復元で作るもの、§6) は、本体のうち、その関係に要る項目 (ターンの `session` と `reply_to`、信号の `target`、v0.2 から想起への操作の対象) だけを読んで作る。ほかの項目が読めなくても、関係を失わない (読めないターンも、セッションの削除と、伏せ字にしないで忘れる操作の対象に残る。伏せ字にする対象なら中止する、04 §7.1)。
12. **出典の無い派生の記録の突き合わせ** (v0.2 から): 削除・忘れるの操作が、派生の記録 (チャンク・ノート・埋め込みとその blob・想起への操作、v0.3 から事実・訂正・事実から作った検索の鍵など) に届かないことがある。古い版はそれらの種類を知らない。ジャーナルからの取り込み (§6) と restore は、消した記録そのものしか消さない。そこで、次の突き合わせを行う。
    - **見つけ方**: 本体が持つ出典の ID (§3.3 の「派生の記録の出典」) の記録が DB に無い派生の記録を、出典の無い記録とする。関係ではたどらない。
    - **消し方**: 出典の無い記録を消す。ジャーナルに書く種類 (`recall_feedback`) は、ジャーナルに削除の行を書き、`put` の行を除く (§6。書かないと、restore で蘇る)。消した ID は、保持している退避からも除く (§7.3)。次の起動で compact する。
    - **いつ行うか**: (1) 前回書いた版 (`meta` の `last_writer`) が、自分の知る派生の種類のどれかを持たない版のとき (v0.2 では、`last_writer` が 0.2.0 より古いとき。v0.3 では 0.3.0 より古いとき)。(2) `restore` の後。(3) ジャーナルの取り込みで、削除の行か忘れるの `fact_directive` を当てたとき。(4) 書き込みの失敗の後に DB を開き直したとき (§6 の「失敗」)。
    - v0.3 では (1) と restore の後に、さらに、すべての忘れるの指示について `forget_backups` の job を作り直し、`compact.pending` を書く (古い版が開いた間に作った退避と、古い版に戻す前の退避に、伏せ字の前の本文が残りうるため。04 §7.2 の当て直しも当てる)。
    - v0.5 の根では、v0.4 以前の版は書き込みで開かない (`format.min_write` が `0.5`、§12.4) ので、(1) は起きない。(2)〜(4) では、`unit` は突き合わせで 1 件ずつ消さず、導出の指紋 (`memory.derive_fingerprint`) を消して全件を導き直す (単位は台帳と正本だけの関数なので、導き直せば出典の無い単位は残らない)。台帳は、出典のセッションが無ければその区切りの台帳を消す (セッションの削除と同じ)。
    - (1) のときは、さらに次を行う。索引を作り直す (前の世代の索引も)。新しい版のジャーナルに書く種類 (古い版が関係を作らずに取り込んだもの) の関係と副索引を、本体から作り直す。古い版が使う派生物 (v0.1 の索引 `index/memory/lex/` など) は、使わなければ消す (古い版は、戻したときに作り直す)。
    - **登録**: `job` として、`last_writer` を自分の版に書き換える (または restore を終える、開き直す) のと同じコミットで登録する。途中で止まっても、次の起動で続ける。
    - **終わるまで**: 想起 (05 §3.2・§3.4)・`/memory`・書き出し (§11) は、出典が DB に無い派生の記録を除いて扱う。`evorag export` は、突き合わせの job が残っていれば、先に済ませてから書き出す。

- **redb のファイル形式の版**: redb はメジャー版でファイル形式を変え、古い形式を読まなくなることがある。上の規則は封筒の層の約束で、redb の層では守れない。redb のメジャー版を上げるときは §12.2 の手順で移す (確定、[OQ-16](10-decisions.md#oq-16-redb-のメジャー版の上げ方))。

## 5. 索引とカートリッジのファイル

- 索引のファイルの形式は [05 §2](05-retrieval.md#2-索引)、カートリッジの形式は [14 §2](14-cartridge.md#2-形式-evocart) が正本。
- どちらもデータ根の下 (`index/`・`cartridges/`) に置き、記録の正本ではない。

## 6. 会話のジャーナル

会話のターンと明示の操作を、DB とは別の追記専用のファイルにも書く (確定、[ADR-0006](10-decisions.md#adr-0006-会話のジャーナルを先に書く))。

| 項目 | 内容 |
|---|---|
| 置き場所 | `journal/<年>-<月>.jsonl` (年と月は UTC) |
| 1 行 | `{"seq": <連番>, "op": <操作>, "env": <中身>, "sum": "<16 進の xxh3-64>"}` の 1 行の JSON。v0.5 の根では、複数の行で 1 つの操作になる行に、任意の項目 `grp` (`{"id": <組の ID>, "n": <組の行数>}`) を `sum` の前に足す (下の「組の行」)。`sum` は最後の項目で、行の `,"sum":"…"}` を `}` に置き換えたバイト列 (書いたとおりのバイト列。読み直して書き直さない) を覆う |
| 操作 | `put` (`env` は封筒。形式は書き出し (§11) と同じ)、`delete` (`env` は `{"kind", "id"}`)、`meta` (`env` は `{"key", "value"}`。一度だけ書く `meta` の値。07 §6.1 のプロンプトの言語と、v0.3 から `memory.forget_key`)。v0.3 は操作の種類を足さない。忘れる・private などの事実への操作は `fact_directive` の `put` で表す (古い版は、知らない操作の行を読み飛ばしたうえで、後ろの既知の行まで取り込みの連番を進めるので、古い版で開いた後に新しい操作の行が二度と取り込まれなくなるため。知らない種類の `put` は古い版でもそのまま残る)。知らない操作の行は、新しい版の行として読み飛ばして数え (壊れた行とは分ける)、連番だけは数に入れる |
| 書く物 | `turn`、`session`、`signal`、`setting` (v0.2 から答え方の既定を含む)、v0.2 から `model_binding` と `recall_feedback`、v0.3 から `fact_directive` と、削除の操作。削除の行は対象の ID だけを持つ。忘れるの `fact_directive` は、それだけで当て直せるように、伏せ字の範囲・伏せ字の後の改訂の番号と本文のハッシュ・再び覚えない印を持つ (04 §7.5)。どちらも本文と値を含めない。忘れるでは、1 回の追記で、指示の行を先に、伏せ字にしたターンの封筒の `put` の行 (伏せ字の後の本文と改訂の番号) をその後に続けて書く (下の「削除と忘れる」)。`threshold` は書かない (同梱の事例から求め直せる。DB を失って戻したときに無ければ、`evorag setup` で求め直す、05 §3.5 の `no_threshold`)。<br>**v0.5 の根**: `fact_directive` に代えて `directive` を書く (忘れる・private・削除で足す `end`・`private` を含む。忘れるの `directive` は `fact_directive` と同じく、それだけで当て直せるように伏せ字の範囲・伏せ字の後の改訂の番号と本文のハッシュ・`[非表示]` の範囲を持つ。v0.5 の忘れるは再び覚えない印 (`marks`) を作らない。`marks` は `import-v04` で写した指示だけが持ち、写すだけで当てない、04 §7.6)。忘れるの 1 回の追記は、`forget` の行 → 同じ操作で足す `end` の行 → 伏せ字にしたターンの `put` の行、の順に書く。削除の 1 回の追記は、`delete` の行 → 同じ操作で足す `end`・`private` の `put` の行、の順に書く。<br>**組の行** (v0.5、確定、2026-11-26): 忘れる (`forget`・`end`・ターンの `put`) と削除 (`delete`・`end`・`private`) の 1 回の追記の行には、同じ `grp` (組の ID と行数) を持たせる。取り込み (起動時・`restore`・`repair`) は、組の行がすべてそろったときだけ、組をまとめて当てる。ファイルの末尾で組がそろわない (書きかけの追記の途中で止まった) ときは、その組の行を当てずに捨てる (DB にはコミットしていないので、操作は無かったことになる)。末尾でない場所の欠けた組は、当てずに数えて `doctor` が報告する。組の ID は組の最初の行の連番 (組の行は 1 回の追記で、続いた連番で書く)、`n` は組の行の数とする。1 行だけの追記は組にしない (行の単位で書き切るか切り詰めるかなので、そろわないことが無い)。「末尾」は、組の最後の行がすべての読める行の中で最も大きい連番を持ち、組の最初の行が `journal.last_seq` より大きいこと。起動時は、その組の行をファイルから切り詰める (組の行より後ろに、組の行とチェックサムの合わない行しか無いときだけ)。`repair` は `journal.last_seq` を見ないので、末尾で欠けた組も当てない。そろわない組の中の `delete` の行は、削除の行として扱わない (開くときにその ID の記録を消さない)。`grp` が読めない形の行は、新しい版の行として数える。`meta` の行に `import.source`・`import.old_root` を足す (§3.1.1)。`segment`・`proposal`・`unit` は書かない (台帳は `Immediate` と退避で守る、§3.4)。`meta` の行の種類は足すが、操作の種類 (`put`・`delete`・`meta`) は足さない |
| 順序 | 書き手スレッドは、DB のトランザクションで操作を当てて規則 (§4.2 の規則 6 など) を確かめてから、**ジャーナルに書いて書き切り**、`journal.last_seq` を同じトランザクションで進めてコミットする (先書き)。規則で断られた操作はジャーナルにも書かない。連番は単調に増える |
| 突き合わせ | DB の `meta` に、取り込んだ最後の連番を持つ。起動時に、ジャーナルの末尾と比べ、DB に無い分を冪等に取り込む。忘れる・削除で行を抜くので連番の欠けは許し、`journal.last_seq` より大きい行を取り込む。取り込みは通常の書き込みと同じ規則で当てる (新しい `v` の記録と読めない記録は上書きしない)。ターンの改訂の番号 (04 §7.3) を DB の記録より小さくする `put` の行は当てない (伏せ字の前の行で、伏せ字を戻さないため。種類ごとに、単調に増える項目として宣言して当てる。`repair` がジャーナルからターンを戻すときも同じ、§10。確定、2026-11-17)。関係と副索引は封筒から作り直し、上書きする記録から作ったものは消す。削除の行がある ID の `put` の行は当てない (削除の後に書き戻された行を蘇らせない)。削除の行がある ID の記録が DB に残っていれば、開くときに消す (利用者が消したものなので、ほかの記録から指されていても残さない。残すには削除の取り消しをジャーナルにも書く必要があり、規則 0 に反するため)。そのため、古い版で戻したセッションに足した会話は、セッションを失ったターンとして DB とジャーナルに残る。消さずに `doctor` が件数を報告する。開くときに消した ID は、同じトランザクションで退避と索引の整理を待つ印に書き、コアが整理の job にしてから印を消す (04 §7.7 の 2)。DB を読むだけで開いているときは、取り込まず、消さず、ジャーナルにも書かない |
| 失敗 | ジャーナルへの書き込みに失敗したら DB にも書かず、画面に知らせる (発話は入力欄に戻す)。追記が途中で失敗したら、ファイルを追記の前の長さに戻す。ジャーナルにだけある状態は許し、DB にだけある状態を作らない。ジャーナルに書いた後で DB のコミットに失敗したら、それ以後の書き込みを止め、DB を開き直して取り込み直す (§3.4) |
| 削除と忘れる | 削除と忘れるの操作の行を先に書き (順序の行のとおり)、DB をコミットした後に、**書き手スレッドがすぐに**、新しいファイルを書き、書き切ってから入れ替える (一時名 → rename、Unix ではフォルダも書き切る)。忘れるは、伏せ字にしたターンの封筒の `put` の行を、指示の行と同じ追記で新しい連番で書く (今の月のファイルの末尾。書き直しの前に止まっても、伏せ字の後の本文がジャーナルにあるため。確定、2026-11-17)。<br>**除く行** (確定、2026-11-17): (a) チェックサムが合わず、対象の ID の文字列を含む行と、(b) `put` の行のうち、封筒の `id` が対象の ID のもの (削除)、または封筒の `id` が対象のターンで最上位の改訂の番号が伏せ字の後の番号より小さいもの (忘れる)。(b) は、行の版に関わらず `env.id` と最上位の改訂の番号だけを読んで判定する。チェックサムが合っていて読めない (新しい版の) 行は、(b) に当たらなければ残し、数えて `doctor` が報告する。ほかの行の中に ID が文字列として現れても (`reply_to`・`target` など) 除かない。ターンそのものは消さない (伏せ字の後の行と、その後の状態の更新の行は残す)。<br>**書き直すファイル**: 開くときに ID ごとに集めた `put` の行のあるファイル (このプロセスで追記したファイルと、チェックサムの合わない行のあるファイルを足す。壊れた行からは ID を集められないため) から選ぶ (ID の時刻では選ばない。古い版が後の月に足した行もあるため、04 §7.2)。<br>**書き直し方**: 残す行は、読んだバイト列のまま写す (書き直さない)。一時ファイルは同じフォルダに `<元の名前>.jsonl.tmp` の名前で、所有者だけの権限で作る。書き切った後に読み直し、書いたバイト列が残す行のバイト列と一致することを確かめてから入れ替える。開くときに残っている `*.jsonl.tmp` は、元のファイルがあれば消し、元のファイルが無ければ (入れ替えの途中で止まった。一時ファイルは確かめた後のもの) 元の名前に戻す。改訂の番号を読めない対象の `put` の行 (整数でない) は除かずに残し、数えて `doctor` が報告する。<br>**追記との直列**: 書き直しは、試し直しも含めて書き手スレッドの依頼として行い、元のファイルを読み始めてから、入れ替えと追記の取っ手の開き直しを終えるまで、ジャーナルに追記しない。今の月のファイルを入れ替えるときは、このプロセスの追記の取っ手を入れ替えの前に閉じ (追記のたびに開く作りなら、持ち続ける取っ手は無い)、入れ替えた後に開けることを確かめる。共有違反などの一時の失敗は、入れ替えと同じく短く再試行し、それでも開けなければ、それ以後の書き込みを止める (失敗の行と同じ扱い)。過去の月のファイルは追記しないので、開き直しを確かめない。<br>**失敗**: Windows でほかのプロセスが開いていて入れ替えに失敗したら、再試行し、それでも失敗したら、削除は job に残し、忘れるは sleep-time に試し直す (04 §7.2。状態の行と `doctor` で知らせる)。書き直しの依頼で「すべての行を除く」のは、削除の行のある ID だけに当てる (呼び手の誤りで生きている記録の行を消さないため)。除く前に止まったときは、起動時に、削除の行と忘れるの `fact_directive` (v0.5 の根では `directive` の `forget`) から同じ書き直しを当てる (チェックサムの合わない行が残っているときは、すべての削除の ID を当てる) (04 §7.2 の `apply_forget` と「ジャーナルの層の見つけ方」。済んだかどうかの印は持たない) |
| 壊れた行 | チェックサムが合わない行は読み飛ばして数え、`doctor` が報告する。ファイルの最後の行が改行で終わらないとき (書きかけ) だけ、起動時にその行を切り詰める (すべてのファイルについて)。読めない行を切り詰めの理由にしない (新しい形式の行を消さないため) |

- 書き切る手順: Windows は `FlushFileBuffers` (書き込みの権限のあるハンドルが要る。読み取り専用のハンドルでは拒否される)、Linux は `fdatasync`、macOS は `F_FULLFSYNC` (失敗したら `fsync`)。
- 入れ替えの rename: Windows では `MoveFileExW` に `MOVEFILE_WRITE_THROUGH` を付ける (std の `fs::rename` は付けない)。Windows にはフォルダの書き切りが無いので、この旗で代える。Unix では rename の後にフォルダを書き切る。

## 7. 退避

### 7.1 自動の退避

- 1 日 1 回まで、DB の一貫した写しを `backups/daily/` に作る (確定、[ADR-0007](10-decisions.md#adr-0007-自動の退避))。v0.1 は起動時と終了時の空き時間に作る。v0.2 はそれに加えて、日をまたいで動き続けているときは sleep-time の手順として作る (短い利用でも 1 日 1 回の退避を欠かさないため、起動時と終了時の分は残す)。
- **写し方は論理的な写し**: 読み取りのトランザクションを 1 つ開き、すべての表を新しい redb のファイルに写す。一時名に書いて書き切り、rename する。ファイルのバイト列をそのまま写さない (書き手のコミットと競合して一貫しない恐れがあるため、[OQ-15](10-decisions.md#oq-15-退避の方式))。
- 退避の `meta` に、含む最後のジャーナルの連番を書く。`restore` はこの連番より後の行だけを足す。
- 10 万件 (各 1 KB) の論理的な写しは、書き手が止まっていれば 1.2〜1.4 秒、書き手がコミットを続けている間でも 7.0〜11.8 秒で、写しは写し始めの時点と一致した (S-01)。退避の前に、元の DB の大きさ以上の空きがあることを確かめる。
- 保持: 日次 7 世代と週次 4 世代 (週の最初の日次を週次に残す)。
- **v0.5 の根の退避** (確定、2026-11-26): 自動の退避を含むすべての退避 (§7.2 の移行と作り直しの前の退避も) で、単位 (`unit`。その関係・副索引・`blobs` も) と `meta` の `memory.derive_fingerprint`、単位の鍵の埋め込みを写さない (書き出しと同じく、導き直せる派生で、忘れた値の単位を退避に残さないため。restore の後に全件の導出で作り直す)。
- 退避の置き場所は設定 `storage.backup_dir` で変えられる (別のディスクを勧める)。§2.2 の検査を同じく当てる。

### 7.2 移行と作り直しの前の退避

- DB の形式の移行 (§12)、`rebuild`、`repair`、`restore` の前には必ず退避を作る (`backups/pre-op/<日時>-<操作>-v<版>/`)。中身は DB の写しと `config.toml`。新しいものから 3 世代を残す。`rebuild`・`repair` の退避は、書き込みで開いたときの取り込み (ジャーナルの突き合わせ・開くときの削除、§6) を済ませた後の状態を写す (通常の起動と同じ処理なので)。
- 本体の更新で移行が要るときも、この形の退避を作る (12 §7)。

### 7.3 忘れる・削除と退避

- 削除と忘れるの操作をしたら、保持している退避 (日次・週次と §7.2 の退避のすべて) のうち対象の記録を含むものを、対象を除いて写し直す (確定 (ユーザー回答)、[OQ-09](10-decisions.md#oq-09-忘れるの約束の範囲))。忘れるでは、対象のターンを伏せ字にして写す (04 §7.2 の `apply_forget`)。v0.1 で対象になるのはセッションの削除だけ。
- 除く対象には、消した記録の ID だけでなく、そこから派生した記録 (チャンク・ノート・埋め込みとその blob・想起への操作) の ID も入れる (v0.2 から)。退避の表のキーは派生の記録の自分の ID なので、出典の ID だけでは除けないため。§4.2 の規則 12 の突き合わせで消した ID も同じく除く。
- 写し直しは書き手スレッドの依頼として行い、終わるまで状態の行に「退避を整理中」と出す。終わる前に強制終了しても、起動時に続きを行う (job)。
- 写し直しは、操作をコミットした直後に始める (sleep-time のアイドルの判定を待たない。忘れてすぐ終了しても、写し直しを始めていれば済む分が増えるため)。写し直しの間に続けてした操作の対象は、次の 1 回にまとめる。終了のときは止めて job を残し、次の起動で続ける。写すのは、生きている DB ではなく元の退避から、対象を除いて写す (忘れるでは `apply_forget` で伏せ字にして写す)。対象を含まないことを確かめられた退避だけを飛ばす: 退避の記録を引いて (キーと副索引で) 対象の ID がどれも無いとき、または退避の記録の表から求めた ID の最大 (種類ごとの最後の記録。`meta` には持たない。古い版が `meta` を丸ごと写して、記録より古い最大が残ることがあるため) より、対象の ID がすべて大きいとき (時計の時刻では判定しない。時計が戻ることがあるため。確定、2026-11-17)。一時ファイルは写す先と同じフォルダに置く (別のディスクへの rename は原子的でないため)。
- 退避を作る処理と写し直しは、同じ順序で通す (書き手スレッドの依頼にするか、同じロックで直列にする)。削除・忘れるより前に作り始め、写し直しの一覧を作った後に作り終えた退避が、対象を含んだまま残らないため。写し直しの job は、開けない退避があれば消さずに残し、再試行する (04 §7.7 の 5)。写し直しは 1 つの退避の失敗で止めず、残りの退避を写し終えてから失敗を返す。`storage.backup_dir` を指定していても、データ根の `backups/pre-op` も対象にする。強制終了で残った作りかけの退避 (`*.partial`・`*.purging`) は、同じ順序の下で、退避を作る前と写し直しの前に消す。DB の写しの無いフォルダは、空か作りかけのファイルだけのときに限り消す (利用者が置いたものに触れないため)。
- **忘れるの写し直しの job** (確定、2026-11-17): 忘れるの写し直しは、削除の整理の job (`purge_backups`) とは別の手順 `forget_backups` の job にする (§3.3 の `job` の `task`)。忘れるの指示の ID を任意の項目 `directive` に持ち、`ids` には退避から除く ID だけを持つ。退避だけを受け持つ (索引から除くのは `purge_indexes` の job、04 §7.7 の 2)。写しで関係と副索引を落とすのは、`ids` の ID と、判定で除く派生の記録のものだけにする。伏せ字が合わずに写しから除くターンは、記録だけを除き、ほかの記録からそのターンへの関係 (応答の `reply_to`、信号の `target` など。値は ID だけ) は残す (restore の後にジャーナルからターンが戻ったとき、関係が戻らなくなるため)。隔離の記録は、元の記録が写しに無くても、対象の ID のものを除く。操作のコミットと同じ依頼で書き、すべての退避を写し終えるまで消さない。忘れるの当て直しが DB の記録を変えたときにも書く。restore の後、忘れるの指示のあるデータ根を `repair` で直したとき、`last_writer` が 0.3.0 より古いデータ根を開いたときは、`meta` の `forget.recheck` (§3.1.1) を同じコミットで立て、コアがそれを見て、すべての忘れるの指示の job を書く (04 §7.2、§4.2 の規則 12)。
  - **写し方**: 退避の論理的な写し (§7.1) の途中で記録を変え、写し終えたら元の退避の DB を閉じてから入れ替える。変え方は、生きている DB の当て直し (04 §7.2 の「当て直しの一覧」) と同じ規則で、写しの中の記録から求める (操作のときに集めた ID だけに頼らない)。
    - 伏せ字にするターンには、生きている DB から読んだそのターンのすべての忘れるの指示を、指示の ID の順に純粋な核 (04 §7.2 の `apply_forget`) で当てて伏せ字にし (合わなければそのターンを写しから除く)、封筒のチェックサムを計算し直す。
    - 写しの中で、印 (`unblock` の相手でない指示のもの) に当たる事実と、`vks` に当たる検証済みの訂正と、伏せ字にしたターンを `turn` に持つ訂正を消す。印に当たる事実は `Retracted` に書き換えずに消す (v0.4 までの根の規則)。
    - 伏せ字にしたターンを出典とし、出典の改訂の番号が伏せ字の後の番号と合わない派生の記録、取り消した事実から作った検索の鍵とその埋め込み、伏せ字にしないときの `hidden` の範囲を持つ往復のノート、伏せ字にしたターンの `quarantine` の記録を消す。
    - 消す ID の記録と、その ID の関係 (`links`)・副索引 (`lookup`)・`blobs`・`quarantine` の記録を写さない。
    - **v0.5 の根の退避**: 上の事実・訂正・ノートの行の代わりに、次を当てる。
      - 台帳 (`proposal`) は、生きている DB と同じ掃除の純粋な関数 (04 §7.2 の「台帳の掃除」) で、写しの中のすべての台帳を掃除してから写す (伏せ字にしないで忘れたときも)。掃除に使う指示は、生きている DB から読んだ忘れるの指示とする。写しの中の隔離した台帳 (`quarantine`) の記録は写さない。
      - 単位 (`unit`)・`meta` の `memory.derive_fingerprint`・単位の鍵の埋め込みは写さない (§7.1 の「v0.5 の根の退避」。写し直す前の退避にあっても、写し直しで除く)。掃除で除いた区切りの鍵の埋め込みも写さない。
      - 単位の索引 (v0.6、04 §5.5) の記録を DB に持つ版では、その記録も写さない (索引のファイルは退避に入らない、§7.1)。
      - **飛ばす退避**: 台帳は値の鍵で当たるかを要素ごとに確かめないと分からないので、v0.5 の根の忘れるでは、上の「対象を含まないことを確かめられた退避」の判定に、写しの中の台帳を掃除の関数に通して変わらないこと (掃除の要素の数が 0) を足す。
  - **飛ばす退避**: 上と同じく、対象 (伏せ字にするターン・印に当たる事実・`vks` に当たる訂正・`ids`) のどれも含まないことを確かめられた退避だけを飛ばす。
  - 続けてした操作は、上の削除と同じく、短い間 (既定 5 秒) の分をまとめて 1 世代を 1 回の写しで処理する。
  - 古い版 (v0.2.x) は、知らない `task` の job を当てずに残すこと (読み飛ばして消さないこと) を、版をまたぐ試験で確かめる (09 §3.6)。
- `evorag backups purge` で、退避をすべて消せる (v0.3)。消すのは、日次・週次・pre-op の退避 (`storage.backup_dir` とデータ根の `backups/` の両方) と、作りかけの退避 (`*.partial`) だけ。シンボリックリンク・リパースポイントの項目はたどらず消さない。`journal/` かデータ根のロックファイルを持つフォルダ、データ根と同じか、データ根の祖先か子孫に当たるフォルダも消さない (置き場所の設定の誤りで、データ根を消さないため)。消さなかったものは、理由とともに示す。

## 8. 破損への対策

| 起きうること | 対策 |
|---|---|
| 強制終了・電源断 | redb のトランザクションで書きかけを残さない。会話の追記は先にジャーナルに書き切り、DB も書き切る (§3.4、§6) |
| DB のファイルの破損 | 起動時に開けなければ、そのファイルを `broken/<日時>/` へ移し (消さない)、最新の退避とジャーナルから戻すかを尋ねる |
| 記録 1 件の破損 | 派生の種類 (チャンク・ノート・埋め込み・`model_probe`、v0.5 から `unit`) の壊れた記録は、`quarantine` へ移さずに消して作り直す (本体を読めないと出典が分からず、削除が届かないため。作り直せるので失うものは無い)。それ以外の種類で封筒のチェックサムが合わない記録は、1 度読み直して確かめてから、消さずに `quarantine` へ移して数え、他の記録はそのまま使う。ジャーナルにある種類は、ジャーナルから戻す (§6)。チェックサムが合っていて読めない記録 (知らない配置・新しい形) は、新しい版の記録として読み飛ばして数える (隔離しない)。読むだけで開いているときは移さず、数えるだけにする。台帳 (`proposal`) と `segment` は派生だが作り直せないので、消さずに `quarantine` へ移し、その区切りは台帳が無いものとして次の裏の処理で呼び直す (`unit` を消したときは導出の指紋を消して導き直す)。隔離した台帳は中を読んで掃除できないので、忘れるのたびにすべて消す (04 §7.2) |
| 索引のファイルの破損 | ヘッダのハッシュが合わなければ、そのセグメントを捨てて作り直す。その間は残りの索引で答える (05 §2.3) |
| 派生データの誤り | `evorag rebuild` で、会話の本文と明示の操作から作り直す (v0.2)。v0.5 から、単位は台帳と指示から導き直す (LLM を呼ばない) |

| ディスクの空き不足 | 起動時と、移行・作り直し・退避の前に空きを確かめる。足りなければ裏の処理を止めて知らせ、会話の追記だけ続ける。会話の追記のために、データ根に予備のファイル (既定 16 MiB) を確保しておく。空きが尽きたら (redb の `StorageFull`、ジャーナルの書き込みの失敗)、予備のファイルを消し、DB を開き直してから書く |
| 危ない置き場所 | §2.2 |
| 2 つの evorag が同じデータ根を開く | §9 |
| 古い版への巻き戻し | §4 の規則 6 と、12 §7 の巻き戻し |
| 利用者の誤操作 | 消す前に確認する。確認の文言で、消える範囲と、退避からも消えることを示す |

- `broken/` と `quarantine` は、evorag が自動で消すことはない。忘れる・削除の操作は `quarantine` の対象の記録にも当て、`broken/` にファイルがあるときは、消すかを尋ねる (04 §7)。
- redb の空きページに消した記録が残るので、削除と忘れるの後の次の起動時に compact する。空きが足りずに compact できないときは、記録を壊さずに止め、次の起動時にやり直す。それまで `doctor` と状態の行で知らせる (04 §7.8)。
  - **要るかの判定** (確定、2026-11-17): `meta` の `compact.pending` (§3.1.1) で決める。削除・忘れると同じコミットで書くので、コミットの後に強制終了しても次の起動で compact する。印を立てるのは、ジャーナルに書く種類の記録を消した・本文を伏せ字にした (改訂の番号を上げた) とき (操作、開くときの削除、取り込み、忘れるの当て直し、規則 12 の突き合わせのどれでも)。派生の記録だけを消したときは立てない (派生の記録は会話の本文から作り直せるもので、起動のたびの compact を避けるため。派生の記録の中の値は、次に印が立ったときの compact で消える)。
  - **時機** (確定、2026-11-17): 書き込みでデータ根を開いたときの順は、ジャーナルの取り込み → 開くときの削除 (§6) → compact → 書き手を作る → 忘れるの当て直し (04 §7.2) → 照会と命令の受け付け。compact はファイルを置き換えるので、書き手を作る前に行う。当て直しで記録を変えたら印が立ち、次の起動で compact する (当て直しが要るのは、操作の途中の強制終了や restore の後に限られる)。compact の前に空きの検査を当て、DB のファイルの大きさに 16 MiB を足した空きが無ければ compact せずに起動を続け、`compact.pending` を残す (空きを求められないときは試す。写しに失敗しても元のファイルは変わらないため)。終えた写しには印を入れない。restore・repair・rebuild の CLI は compact をせず、印を残して次の起動に任せる。
  - **方式**: redb の compact は解放したページを消す保証が無く、消した記録が残っていないことを確かめられないので使わない。§12.2 と同じ手順 (新しいファイル `evorag.redb.compacting` へすべての表を論理的に写し、行ごとに突き合わせ、元を閉じて 1 回の rename で入れ替える) で作り直す。開くときに `evorag.redb` があれば、残った写しは捨てる。

## 9. ロックと同時に動くコマンド

- データ根の `lock` ファイルに、プロセスが生きている間ずっと OS のロックを持つ。std の `File::try_lock` (Rust 1.89 で安定。Windows は `LockFileEx`、Unix は `flock`) を使い、取れないときは `TryLockError::WouldBlock` で見分ける。強制終了するとロックはすぐに外れる (S-01)。ファイルがあるかどうかでは判定しないので、異常終了の後に残ったファイルで誤判定しない。
- Windows のロックは強制ロックで、ロックを持たれたファイルは他のプロセスから読めない。そのため、動いている evorag の PID はロックのファイルとは別のファイル (`lock.pid`) に書く。
- redb も DB のファイルをロックし、2 つ目の open (読み取り専用を含む) は `DatabaseAlreadyOpen` で失敗する。
- どちらのロックが取れなくても、理由 (分かれば PID) を示して終了コード 2 で終わる。文言は、ほかの evorag か `evorag update` (置き換えの間はデータ根のロックを持つ、12 §7.2) が動いていることを示す。
- ネットワークのファイルシステムではロックが効かないことがある。§2.2 の拒否の理由の 1 つでもある。

| コマンド | TUI が動いているとき |
|---|---|
| `evorag --version`、`evorag setup` (設定だけを書く)、`evorag update check` | 動く |
| `evorag setup` (モデルの記録を書き換える・点検の結果やしきい値を書く、06 §3.2) | 設定だけを書き、DB に書く部分は TUI を閉じてから実行するよう案内する |
| `evorag doctor`、`export`、`restore`、`repair`、`rebuild`、`backups`、`reset`、`import`、`update apply`、`update rollback` | 理由を示して断る (TUI を閉じてから実行する)。`update apply` は書き込みを始めてから (12 §7.2 の apply の 8)、`update rollback` はデータの案内を求めてから、操作の終わりまでデータ根のロックを持つ |

### 10.1 `doctor --deep` (v0.5)

読むだけで、DB・ジャーナル・索引・退避を深く調べる (FR-207)。`doctor` と同じくデータ根のロックを取り、ファイルを 1 つも書き換えない (更新時刻も変えない)。時間がかかるので、置き場所ごとの進み具合を示す。

| 調べること | 中身 |
|---|---|
| 記録の整合 | 全記録のチェックサム、関係の参照先、副索引と記録の食い違い、DB とジャーナルの食い違い (ジャーナルにあって DB に無い記録、改訂の番号の逆転)、出典の無い派生の記録 (§4.2 の規則 12) |
| **導出のし直しの照合** | 今の有効な台帳・指示・辞書・規則の版から、全件の導出を主記憶の中でやり直し (生きている導出と同じ関数。LLM を呼ばない)、保存した単位と比べる。単位の ID の集合と、単位ごとの本体が一致し、指紋 (`memory.derive_fingerprint`) が今の入力と合うことを確かめる。食い違いは、層ごとに「足りない」「余分」「中身が違う」の件数で示す (値は出さない) |
| **忘れた値の残りの走査** | すべての `forget` の指示について、この版の置き場所 (04 §7.9 の一覧のうち v0.5 にあるもの) を走査する。値そのものは持たないので、値の鍵と照合の鍵 (`vks`) と、伏せ字の記録 (範囲・改訂の番号・本文のハッシュ) で確かめる。`unblock` で印を解いた指示まで見るのは (1) 本文・(2) ジャーナル・(7) 退避の本文だけにする (伏せ字は印を解いても戻らないため)。(3)・(4) の当たりは、生きている導出と同じ当て方の述語 (04 §7.5) で判定する (印を解いた後に言い直した値を、残りとして数えないため)。<br>(1) ターンの本文: 伏せ字の記録のターンが伏せ字の後の改訂の番号以上で、その版の本文のハッシュが合う (後の伏せ字があれば、それと矛盾しない)。<br>(2) ジャーナル: 対象のターンの、伏せ字の後の番号より小さい改訂の番号の `put` の行が無い。<br>(3) 台帳: どの選択の台帳も、台帳の掃除の関数 (04 §7.2) に通して変わらない (除く要素が 0)。<br>(4) 単位: 当て方の述語で忘れるの指示に当たる単位と、`anchors` の値の範囲が伏せ字の範囲に掛かる単位が無い。<br>(5) チャンクと索引: 対象のターンのチャンクの `src_rev` が今の改訂の番号と合う。索引の項目が DB のチャンクを指す。<br>(6) `quarantine`: 対象のターンと、その区切りの台帳の記録が無い。読めない台帳の原文は「確かめられない」として数える。<br>(7) 退避: 保持しているすべての退避を読むだけで開き、(1)・(3)・(6) と同じことを確かめる (退避は単位を持たない、§7.3)。開けない退避は「確かめられない」として数える。<br>(8) 古い根: `import.old_root` が `kept` で、取り込みの後に忘れるがあれば、古い根に忘れた値が残りうることを示す (古い根は走査しない。値の平文を持たないため) |
| 示さないもの | 利用者が書き出したファイル・OS のバックアップ・llama-server の主記憶のキャッシュ (約束しない範囲、04)。`broken/` のファイルは、あることだけを示す |

- **終了コード**: 食い違いも残りも無ければ 0。見つかれば 1 で、置き場所ごとの件数と、次にすること (多くは次の起動の当て直しと導き直しで直る。直らなければ `evorag repair`、退避なら `evorag backups purge`、古い根なら `evorag reset --old`) を示す。ロックが取れなければ 2。
- 値・本文はログにも画面にも出さない (ID と件数だけ、NFR-502)。

### 10.2 `reset` (v0.5)

データ根を丸ごと消す (FR-218)。`import-v04` の後の古い根の処分 (`--old`) と、今のデータ根を消すことを、同じ実装で行う ([ADR-0021](10-decisions.md#adr-0021-メモリの新エンジンを段階に分けて入れる) の決定 4)。

| 項目 | 内容 |
|---|---|
| 対象 | `evorag reset`: 今のデータ根 (`--data-root`・`storage.data_root`・既定の順)。`evorag reset --old`: 今の根の `meta` の `import.source` に記録した古い根 (今の根が取り込みで作った根でなければ、何もせずに 1 で終わる) |
| 消すもの | データ根のフォルダの全体 (`evorag.redb`・`journal/`・`index/`・`backups/`・`broken/`・`lock` など) と、`storage.backup_dir` を設定していればその中の、対象の根の退避 (退避の `meta` の `data_root.id` が対象の根の ID と一致するものだけ。ほかの根の退避と、利用者が置いたものには触れない)。設定 (`config.toml`) と状態のフォルダ (ログ・`update/`) は残す |
| 確かめること | 対象が evorag のデータ根である (`evorag.redb` の `meta` の `data_root.id` が読め、`--old` では `import.source` の ID と一致する)。対象が今の根と同じでなく、今の根の祖先でも子孫でもない (`--old`)。`backups purge` と同じく、シンボリックリンク・リパースポイントをたどらない。対象の根のロックが取れる (取れなければ、使っている evorag の版と PID を示して 2 で終わる) |
| 確認 | 消える範囲 (DB・ジャーナル・退避の件数と置き場所) と、元に戻せないこと、OS のバックアップと書き出したファイルには残りうることを示し、y で実行する (`--yes` で省く)。`--old` では、取り込みの後に忘れた値が古い根に残っていることを、件数 (取り込みの後の忘れるの数) で示し、取り込みで除いたターンの件数 (`import.report`) も示す。今の根を消す (`--old` なし) ときに古い根が残っていれば (`import.old_root` が `kept`)、そのパスを示し、一緒に消すことを勧める (確定、2026-11-26) |
| 手順 | (0) `--old` では、今の古い根の `journal.last_seq` とファイルの要約を `import.source` に記録したものと比べ、変わっていれば (取り込みの後に v0.4 で使った) 消さずに、変わった件数 (ジャーナルの行の数) と、取り込み直しの案内を示して 1 で終わる (確定、2026-11-26。取り込みの後の会話を黙って失わないため)。(1) 対象のフォルダを同じ親の `<名前>.deleting-<UTC の日時>` に改名する (原子的。以後、どの版もデータ根として開かない。下の「改名の隙」)。(2) `storage.backup_dir` の中の対象の退避を消す。(3) 改名したフォルダの中身を消し、フォルダを消す。(4) `--old` では、今の根の `import.old_root` を `disposed:<時刻>` にする (DB とジャーナル)。途中で止まったら、次の `reset` (と次の起動の `doctor`) が `*.deleting-*` のフォルダを見つけて続きを示す (中身を消すだけなので、何度当てても同じ)。TUI の画面の処分の操作 (07 §3 の `/forget`・`/delete`) も、`*.deleting-*` が残っていれば続きを行う |
| 終了コード | 0: 消し終えた。1: 確認で y 以外を答えた・対象が条件に合わない・消せないファイルが残った (残ったパスを示す)。2: ロックが取れない |

- **改名の隙** (確定、2026-11-26): 手順の (1) の改名の間に、ほかのプロセスが対象の根を開かないようにする。Unix では、対象の根のロックを持ったまま改名する (ロックはファイルの取っ手に付くので、改名の後も効く)。Windows では、ロックのファイルを開いたままではフォルダを改名できないので、ロックを放す → 改名する → 改名した先でロックを取り直し、改名の前に取った要約 (`data_root.id`・`journal.last_seq`・ファイルの一覧の大きさと更新時刻) が変わっていないことを確かめる。取り直せない・合わないときは、改名を元に戻し、理由を示して 2 で終わる。`import-v04` の入れ替えの改名 (§12.4) も同じ規則にする。
- 今のデータ根を消した後の最初の起動は、新しいデータ根として始める (プロンプトの言語を決め直す、07 §6.1)。
- TUI の中の忘れるの確認 (07 §3 の `/forget`) から古い根を消すときも、この手順を同じ関数で行う (画面は今の根のロックを持ったまま、古い根のロックを取る)。

## 11. 書き出しの形式

- `evorag export <出力先>` は、記録を種類ごとに 1 ファイルの JSON Lines で書き出す (`<kind>.jsonl`)。各行は封筒 (`body` は JSON に写す) で、ファイルの先頭の行に形式名 `evorag-export` と形式の版を書く。
- 封筒の知らない項目は、同じ名前の項目として写す (§4.2 の規則 7)。読むときは、既知の項目以外を知らない項目として保つ。
- JSON にそのまま写せない CBOR の値 (バイト列、タグ、±2^53 を超える整数、NaN と無限大、文字列でない map のキー) は、その値の CBOR を base64 にした `{"$cbor": "<base64>"}` で写し、読むときに元の CBOR に戻す (知らない項目を元の形のまま運ぶため)。ジャーナルの行の `env` も同じ規則で写す。
- 書き出しに含めるもの: v0.1 は会話 (`session`・`turn`)・信号・設定。v0.2 からモデルの記録 (`model_binding`)・しきい値 (`threshold`)・想起への操作 (`recall_feedback`)・ノートも含める (OQ-37 の 9)。v0.3 以降は事実・訂正・事実への指示と、再び覚えない印の鍵 (取り込んだ先でも印が効くように。書き出したファイルは約束しない範囲、04 §7.8)、v0.5 の根からは、指示 (`directive`)・区切り (`segment`)・台帳 (`proposal`。作り直せず、同じものが戻らないため) を含め、事実・訂正・ノートは無い (v0.4 の計画の precept・回帰台帳の事例・提案と判定は作らない、ADR-0021)。`import.source`・`import.old_root` の `meta` の値も書く。学習の記録 (v0.7) とカートリッジ (`.evocart` のまま同梱、v0.9) は、その版で足す。
- 書き出しに含めないもの: 索引、チャンク、埋め込みのベクトル、点検の結果 (`model_probe`)、単位 (`unit`。台帳と指示から導き直せる、v0.5)、`quarantine`、API キー (どれも作り直せるか、外に出さないもの)。出典が DB に無い派生の記録 (§4.2 の規則 12) と、出典の改訂の番号が今のターンと合わない派生の記録 (伏せ字の前の本文から作った古いノートなど、04 §7.7 の 1) も含めない。
- **台帳と忘れる** (v0.5): 台帳は、忘れるの掃除の後の形 (04) のまま書く。private の値は台帳の中に残る (会話の本文と同じく、利用者の持ち出しの経路なので伏せない。private は導出の時点でふるう、04)。
- **private と忘れる** (確定、2026-11-17): private の事実は除かずに、本体の `private` の印のまま書く (利用者が自分のデータを持ち出す経路なので。書き出したファイルは約束しない範囲、04 §7.8)。当て直しの済んでいない忘れる (04 §7.2 の当て直し) か、取り込んでいないジャーナルの行があれば、書き出しを断り、evorag を一度起動して済ませるよう案内する (伏せ字の前の本文を書き出さないため。書き出しは TUI を閉じてから行うので、自分では当て直さない)。
- **派生の記録の確かめ**: 出典の改訂の番号を確かめるのはメモリの層 (04 §7.7 の 1) なので、書き出しはコアを通して派生の記録を確かめる。確かめられない派生の種類は書き出さない (作り直せるため)。
- 書き出しのファイルは所有者だけの権限で作る。
- `evorag import <書き出し>` は、空のデータ根へだけ取り込む (v0.8。書き出しの形式の版 1 と合わせて入れる、ADR-0021)。v0.4 のデータ根からの取り込み (`import-v04`) は書き出しを経ない別の手順 (§12.4)。

## 12. 移行

### 12.1 DB の形式の版

- `meta` の DB の形式の版が、今の evorag が書く形式の版より古ければ、起動時に §7.2 の退避を作ってから移行する。移行に失敗したら、元の DB のまま (読むだけで) 起動し、理由を示す。
- 移行は新しいファイルに書き、`migration.state` を `in_progress:…` にしておく。終えてから `none` にし、件数とチェックサムを突き合わせて入れ替える。起動時に `in_progress` のファイルが残っていれば、それを捨てて元から移行し直す。
- 移行の関数は版ごとに 1 つずつ持ち、順に当てる。移行の試験は、各版の DB の見本から今の版まで当てて行う。
- v0.1〜v0.7 の間 (§4.1) は、移行の関数を直前の版の分だけ持てばよい。v0.5 は在り場所の移行を持たず、v0.4 の形式 (`0.3`) の根を `import-v04` で新しい根へ取り込む (§12.4)。v0.6・v0.7 は直前の版の形式からの在り場所の移行を持つ。v0.8 では、v0.7 の形式から形式の版 `1` への移行を持つ。
- **v0.1 から v0.2** (形式の版 `0.1` → `0.2`): 種類と任意の項目を足すだけなので、記録は書き換えない。`format.version` を `0.2` にし、`format.min_read` と `format.min_write` は `0.1` のままにする (v0.1.2 に戻しても、読み書きできる。新しい種類は v0.1.2 が読み飛ばして残す)。移行の前に §7.2 の退避を作る。移行の後は、`last_writer` が 0.1.x なので、§4.2 の規則 12 の (1) と同じ扱いになる。次を、`last_writer` を書き換えるのと同じコミットで job として登録する。
  1. v0.1 の索引 (`index/memory/lex/`) を消し、チャンクを作って `chunk-lex/` を作る (05 §2.3)。
  2. 埋め込みとノートを作る (裏の処理、04 §4)。進み具合を状態の行に出す。
  - モデルの記録は、job ではなく、起動時の照合 (06 §3.1) で行う (記録が無いので、繋がっているモデルを記録する)。
- **v0.2 から v0.3** (形式の版 `0.2` → `0.3`): 種類 (`fact`・`correction`・`fact_directive`) と任意の項目 (ターンの改訂の番号・派生の記録の `src_rev`) と `meta` のキー (`memory.forget_key`) を足すだけなので、記録は書き換えない。`format.version` を `0.3` にし、`format.min_read` と `format.min_write` は今の値 (`0.1`) のまま据え置く (v0.2.x・v0.1.2 に戻しても読み書きできる。新しい種類は古い版が読み飛ばして残す)。改訂の番号の無いターンは 0 として読む。v0.2.x はジャーナルの `memory.forget_key` の `meta` の行を取り込まずに連番だけを進めるので、v0.3 は鍵をジャーナルの全行から探す (§3.1.1 の `memory.forget_key`)。移行の前に §7.2 の退避を作る。移行の後は、`last_writer` が 0.2.x なので、§4.2 の規則 12 の (1) と同じ扱いになる。
- 移行は、表の構成ごと作り直すときも、記録を 1 件ずつ論理的に写して件数とチェックサムを突き合わせてから入れ替える (§12.2 と同じ手順)。ジャーナルの形式を変えるときは、古いジャーナルを新しい形式で書き直してから入れ替える。

### 12.2 redb のメジャー版を上げるとき

1. 新しい evorag は、古い redb の形式を読む手段 (古い版の redb を別名で依存に持つ、または書き出しを経由する) を 1 つの版の間だけ持つ。
2. 起動時に §7.2 の退避を作り、古い形式から新しい形式のファイルへ、すべての記録を論理的に写す。
3. 写した後に、記録の件数とチェックサムを突き合わせてから入れ替える。

手段の選択は OQ-16。

### 12.3 設定の版

- `config.toml` は `version` のキーを持ち、版ごとの移行の関数で書き換える。書き換える前に元のファイルを `config.toml.bak-v<旧版>` に写す (07 §4)。

### 12.4 v0.4 のデータ根からの取り込み (`import-v04`、v0.5)

v0.5 は記録の種類を組み直す (§3.3) ので、v0.4 のデータ根を在り場所で移行せず、**新しいデータ根へ写す** (確定、[ADR-0021](10-decisions.md#adr-0021-メモリの新エンジンを段階に分けて入れる) の決定 4、提案書 §4.7)。古い根には書かない (会話を失わず、取り込みに失敗しても古い根で v0.4 に戻れるため)。細目のうち PO の確認が要る点は [OQ-54](10-decisions.md#oq-54-v05-の新しいデータ根と古いデータ根の扱い)。
